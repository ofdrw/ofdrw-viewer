# 字体格式推断与适配方案设计

本文件是 [`渲染字体缺省方案设计.md`](./渲染字体缺省方案设计.md) 的补充章节：在「字体来源如何选择」之外，说明**选中一份字节之后，如何把它变成 fontkit 能解析的字体**。

OFD 内嵌的 `FontFile` 并不保证是标准 sfnt。典型情况是扩展名为 `.otf`，内容却是**没有 sfnt 表目录的裸 CFF**，还常常省略 CFF 规范要求的空 String INDEX 与 GlobalSubr INDEX。这类字节被 fontkit 直接拒收为 `Unknown font format`，整份字体的文字退化为 `.notdef` 空心方块。

设计原则：**先结构判定、再按类型适配、最后统一解析**。判定不靠扩展名、不靠首字节猜测；适配器之间互相隔离，任一层失败都回落原有错误路径，行为与「未引入本特性」时一致。

相关文档：[`渲染字体缺省方案设计.md`](./渲染字体缺省方案设计.md)（字体来源优先级与回退链）、[`字体配置方案设计.md`](./字体配置方案设计.md)（UI 字体来源）、[`OFD渲染引擎设计方案.md`](./OFD渲染引擎设计方案.md)（引擎总体分层）、[`警告与错误日志方案设计.md`](./警告与错误日志方案设计.md)（warning 码表与去重）。

## 1. 定位、目标与非目标

### 1.1 定位

字体来源分四层（内嵌 `FontFile`、`FontProvider`、`defaultFonts`、`supplementaryFonts`），由 [`渲染字体缺省方案设计.md`](./渲染字体缺省方案设计.md) 的固定优先级决定。本文件只负责其中**内嵌 `FontFile` 这一层**的字节处理：

- 判定字节的封装类型（`FontKind`）；
- 按类型分派到适配器，产出 fontkit 可解析的归一化字节；
- 裸 CFF 的重建规则及其约束；
- 适配失败时的语义，以及与 `W_FONT_MISSING` 的关系。

`defaultFonts`/`supplementaryFonts` 由宿主提供，字节同样经过本流水线，因此这些来源的裸 CFF 字体也能被正确解析。

### 1.2 目标

1. 让 OFD 生态里真实存在的裸 CFF 内嵌字体能被正常解析，文字不再整体退化为 `.notdef`；
2. 判定过程可解释：类型是显式枚举，而不是隐式的「试一下 fontkit 能不能打开」；
3. 适配器可扩展：新增一种封装类型只需注册一个适配器，不牵动调用方；
4. 不改变既有语义：能解析的字体解析结果不变，不能解析的字体仍走 `OFD_FONT_PARSE`；
5. 不新增运行时依赖，只做结构重排，不解码字形轮廓。

### 1.3 非目标

- 不做字体子集化、压缩、跨轮廓格式转换（如 TrueType → CFF）；
- 不修复字体本身的数据错误（缺字形、cmap 缺失、charcode 越界）；
- 不把裸 CFF 转成真正的矢量字库发布；适配产物只存在于内存，不落盘；
- 不为裸 CFF 合成 `cmap`/`name`/`OS/2`/`post` 表：这些字体只有字形轮廓，文字内容由 `CGTransform` 的显式 GID 决定，cmap 缺失是数据事实而非解析缺陷；
- 不改变 `W_GLYPH_MISSING` 的触发条件。

## 2. 三段流水线

主流程只有一条，位于 `packages/ofdrw-viewer-engine/src/font/pipeline.ts` 的 `normalizeFontBytes()`，由 `packages/ofdrw-viewer-engine/src/font/face.ts` 的 `parseFaces()` 在创建字体面前调用：

```text
原始字节
  │
  ├─[1] 推断层  detectFontKind(bytes)            → FontKind
  │             packages/ofdrw-viewer-engine/src/font/font-kind.ts
  │
  ├─[2] 适配器层 ADAPTERS[kind](bytes)           → 归一化字节（可能为 null）
  │             packages/ofdrw-viewer-engine/src/font/pipeline.ts
  │
  └─[3] 解析    createFontkit(归一化字节)        → fontkit 字体面
                packages/ofdrw-viewer-engine/src/font/face.ts
```

`face.ts` 的调用顺序保证「先归一化、后解析」：

```ts
// packages/ofdrw-viewer-engine/src/font/face.ts
const { bytes } = normalizeFontBytes(toBytes(data));
let parsed: FontkitFaceLike;
try {
  parsed = createFontkit(bytes) as unknown as FontkitFaceLike;
} catch (error) {
  throw toOFDError(error, 'OFD_FONT_PARSE', `字体解析失败${options.fontName ? `（${options.fontName}）` : ''}`);
}
```

三段职责严格分离：

| 阶段 | 负责 | 不负责 |
| --- | --- | --- |
| [1] 推断 | 只看字节结构，给出类型 | 不修改字节、不抛异常 |
| [2] 适配 | 把该类型字节重排为 fontkit 可解析形式 | 不判断「这个字体能不能渲染」 |
| [3] 解析 | 由 fontkit 建立字形与度量 | 不感知原始封装类型 |

## 3. `FontKind` 枚举

定义于 `packages/ofdrw-viewer-engine/src/font/font-kind.ts`：

| `FontKind` | 识别依据 | 适配器 | 说明 |
| --- | --- | --- | --- |
| `sfnt` | 首 4 字节为 `OTTO` / `true` / `\0\1\0\0` | 直通 | TrueType、CFF 轮廓 OpenType、Apple `true` |
| `ttcf` | 首 4 字节为 `ttcf` | 直通 | 字体集合，由 `face.ts` 的 `selectFaceIndex` 选面 |
| `woff` | 首 4 字节为 `wOFF` | 直通 | fontkit 原生支持解压 |
| `woff2` | 首 4 字节为 `wOF2` | 直通 | fontkit 原生支持解压 |
| `bare-cff` | **结构化校验通过**（见 §3.1） | `adaptBareCff` | 无 sfnt 包装的裸 CFF |
| `unknown` | 以上都不满足 | 无（保留原字节） | 交由 fontkit 报错后转 `OFD_FONT_PARSE` |

判定顺序固定为 `ttcf → woff2 → woff → sfnt → bare-cff → unknown`：先匹配明确的 4 字节 magic，再尝试结构化判定；裸 CFF 排在最后，避免吞掉被损坏的 sfnt。

### 3.1 裸 CFF 必须做结构化校验

裸 CFF **没有 magic 值**。文件头就是 `major/minor/hdrSize/offSize` 四个字节，其中 `major=1`、`minor=0`、`hdrSize=4` 组合是最常见的前缀，但一个被截断或损坏的 sfnt（`00 01 00 00` 之后紧接类似字节）也可能满足「首字节看起来像 CFF」。**只看首字节必然误判**，因此 `detectBareCff()` 逐项校验：

| 校验项 | 规则 | 不满足时 |
| --- | --- | --- |
| header 长度 | 至少 `hdrSize + 2` 字节 | 不是裸 CFF |
| `major` | 必须为 1 | 不是裸 CFF |
| `minor` | 必须为 0（CFF1） | 不是裸 CFF |
| `hdrSize` | 必须为 4 | 不是裸 CFF |
| header `offSize` | 必须在 1..4 | 不是裸 CFF |
| Name INDEX | `count` 必须为 1 | 不是裸 CFF |
| Name INDEX 结构 | `measureIndex()` 返回非负结束位置 | 不是裸 CFF |
| TopDICT INDEX | `count` 必须为 1 | 不是裸 CFF |
| TopDICT INDEX 结构 | `measureIndex()` 返回非负结束位置 | 不是裸 CFF |
| 尾部数据 | TopDICT 之后必须还有字节（至少 String INDEX / CharStrings） | 不是裸 CFF |

`measureIndex()` 是共用的一致性检查，对每个 INDEX 校验：

1. 条目数 `count > 0`；
2. `offSize ∈ 1..4`；
3. 偏移表 `offSize × (count + 1)` 完整落在字节内；
4. 偏移值**单调不减**；
5. 首偏移**必须为 1**（CFF 规范：偏移相对数据区起点，最小为 1）；
6. 末偏移算出的结束位置**不越界**。

> 注意：`measureIndex()` 对 `count == 0` **判为不自洽**（`count <= 0` 直接返回 -1）。这不影响判定，因为裸 CFF 的 Name INDEX 与 TopDICT INDEX 按规范必须是 1 条，二者都已单列为必检项；省略了空 String INDEX / GlobalSubr INDEX 的字体属于「这两个块根本不存在」而非「存在但为空」，判定层不会读到这里。

## 4. 适配器注册表与失败语义

`ADAPTERS` 是一张 `Record<FontKind, FontAdapter | null>`，`FontAdapter` 的契约为 `(bytes: Uint8Array) => Uint8Array | null`：

```ts
const ADAPTERS: Readonly<Record<FontKind, FontAdapter | null>> = {
  sfnt: passthrough,
  ttcf: passthrough,
  woff: passthrough,
  woff2: passthrough,
  'bare-cff': adaptBareCff,
  unknown: null,
};
```

失败语义分三层，保证任何适配器异常都不会中断整个渲染：

| 层级 | 失败表现 | 结果 |
| --- | --- | --- |
| 适配器返回值 | `adaptBareCff()` 内部 `parseBareCff()` 抛错或 `numGlyphs === 0` 时 `catch` 后返回 `null` | 保留原始字节继续 |
| `normalizeFontBytes()` | 适配器返回 `null`，或适配器抛出未预期异常 | 同上，原字节继续交给 fontkit |
| `face.ts` | fontkit 仍无法解析 | 抛 `OFD_FONT_PARSE`，由上层转 `W_FONT_MISSING` |

```ts
export function normalizeFontBytes(bytes: Uint8Array): { kind: FontKind; bytes: Uint8Array } {
  const kind = detectFontKind(bytes);
  const adapter = ADAPTERS[kind];
  if (!adapter) return { kind, bytes };
  try {
    return { kind, bytes: adapter(bytes) ?? bytes };
  } catch {
    // 适配器内部异常不应中断整体流程，原样返回让 fontkit 走原有失败路径。
    return { kind, bytes };
  }
}
```

要点：

- **适配失败不等于解析失败，也不产生额外 warning**：只是回到「没有适配器」的旧行为；
- 适配器**不抛异常到调用方**，`adaptBareCff` 的整个函数体包在 `try/catch` 内，返回 `null`；
- 直通类型的开销是零：`passthrough` 原样返回入参，不做拷贝。

## 5. 裸 CFF 适配器做了什么

`adaptBareCff()` 位于 `packages/ofdrw-viewer-engine/src/font/cff-bare.ts`，分四步：解析 → 重建 CFF 表 → 合成 sfnt 必需表 → 打包。

### 5.1 第一步：解析裸 CFF 结构

`parseBareCff()` 建立 `BareCff` 中间结构。除了 §3.1 的 header/INDEX 校验，还会：

- 校验字体名为 1..127 个 ASCII 可打印字符（`0x21..0x7e`）；
- 从 TopDICT 取 CharStrings（op 17）、charset（15）、Encoding（16）、Private（18）、FDArray（1236）、FDSelect（1237）、ROS（1230）；
- 尝试读取 String INDEX 与 GlobalSubr INDEX，但只有**完整落在 CharStrings 之前**时才采信，否则视为省略；
- 校验各数据块偏移不越界、charset 不与 CharStrings 重叠、charset format ∈ 0/1/2 且长度足够；
- 从 `FontMatrix`（op 1207）推出 `unitsPerEm`，取不到时用 1000；
- 从 `FontBBox`（op 5）取包围盒，缺失时用 `0,0,unitsPerEm,unitsPerEm`；
- 由 `.notdef` 的 charstring 估算 `advanceWidth`，估算不出时用 1000。

### 5.2 第二步：重建 CFF 表（`buildCff()`）

输出布局固定为：

```text
HDR(4) | Name INDEX | TopDICT INDEX | String INDEX | GlobalSubr INDEX
       | charset | Encoding | CharStrings | FDSelect | Private | Subrs
       | [每个 FontDict 的 Private + Subrs] | FDArray
```

关键动作：

| 动作 | 原因 |
| --- | --- |
| **补齐空 String INDEX / GlobalSubr INDEX** | 原字体常省略二者，但 fontkit 按标准布局顺序读取后续结构，缺位会让 charset/CharStrings 整体错位 |
| **重写 TopDICT 内所有相对偏移**（charset 15、Encoding 16、CharStrings 17、Private 18、FDArray 1236、FDSelect 1237） | 数据块位置在重建后全部改变 |
| **重写 FontDict 内的 Private 偏移** | 同上，CID 字体的每个 FontDict 各带一份 Private |
| **Private DICT 追加 Subrs 操作符** | Subrs 紧跟 Private 之后，偏移等于 Private 字节长度 |
| **丢弃 fontkit 未定义的操作符** | fontkit 的 DICT 解码器遇到未定义操作符直接抛 `Unknown operator` 并中断整份 CFF；被丢弃的只是可省略的排版提示（如 `CharstringType` 默认 2、`StrokeWidth` 默认 0）。允许集为 `FONTKIT_TOP_DICT_OPERATORS`、`FONTKIT_FONT_DICT_OPERATORS`、`FONTKIT_PRIVATE_DICT_OPERATORS` |
| **两遍定点迭代求解布局** | TopDICT/FontDict 记录的是「相对 CFF 起点」的绝对偏移，而它们的字节长度又取决于偏移的编码长度；反复重算直到长度与位置稳定（上限 8 轮，未收敛则抛错 → 返回 null） |
| **布局自检** | 写完后再按实际写入位置复核一遍，任何一块记录的偏移与实际位置不一致都抛错，避免「把 FDSelect 当 Private DICT 读」这类错位 |

### 5.3 第三步：合成 sfnt 必需表

裸 CFF 没有 sfnt 表目录，fontkit 需要一个 `OTTO` 容器。`buildSfnt()` 只放入解析必需的表：

| 表 | 大小 | 内容来源 |
| --- | --- | --- |
| `CFF ` | 重建产物 | §5.2 |
| `head` | 54 字节 | `unitsPerEm` ← FontMatrix；包围盒 ← FontBBox；`created/modified` 固定为 2000-01-01（自 1904 纪元 3,029,529,600 秒）；`magicNumber = 0x5f0f3cf5` |
| `hhea` | 36 字节 | `ascent = max(bbox.maxY, unitsPerEm)`、`descent = min(bbox.minY, 0)`、`numberOfMetrics = numGlyphs` |
| `hmtx` | `numGlyphs × 4` | 每个字形都用估算出的同一 `advanceWidth`，`leftSideBearing = 0`；没有更好的来源时统一为等宽 |
| `maxp` | **32 字节**，version 1.0 | `numGlyphs` ← CharStrings 条目数 |

不合成 `name`/`cmap`/`OS/2`/`post`：它们只影响命名与码点映射，不影响按显式 GID 取字形轮廓。缺少这些表时 `face.hasCmap === false`，`face.explicitGlyphs` 仍可信任显式 GID（内嵌字体默认 `authoritative: true`）。

表目录的 `checkSum` 写 0：fontkit 不校验，且裸 CFF 无法提供真实校验和。

## 6. 关键约束（踩坑记录）

以下每一条都是「实现过一次、然后在真实文档上失败」的结论，改动相关代码前必须先读。

### 6.1 `maxp` 必须是完整 32 字节的 1.0 版本

fontkit 的 `maxp` 是**固定结构**解码器，会无条件读满 15 个字段共 **32 字节**。而 CFF 字体按规范应使用 `maxp` 0.5 版本——0.5 版只有 `numGlyphs` 一个字段（6 字节）。两者（CFF 规范的最小要求 vs fontkit 的无条件读满）只能取交集：**写 1.0 版本的 32 字节结构**，只填 `version` 与 `numGlyphs`，其余字段留 0。

只写 6 字节会让 fontkit 读到相邻表的字节，症状是随机的度量错误或解析中断。

### 6.2 实数（real）不要 decode → encode 往返

DICT 里的实数用 nibble 编码（`0x1e` 起始、`0xf` 结束）。若先 `parseDict()` 解成 `number`，再用 `encodeNumber()` 重新编码，会引入**精度截断与语义漂移**：`FontMatrix` 的 `0.001` 一旦被改写成 `0.001000` 或 `1E-3`，字形缩放即整体偏移；`toFixed(6)` 还会丢掉更精确的尾部。

因此 `rewriteDict()` 对非偏移操作数**按原始字节原样复制**（`operator.raw[index]`），只有偏移型参数与 `Private size` 用固定 5 字节 `encodeInt32()` 重新编码（保证两遍布局中长度不变）。唯一的例外是空实数 `30 0f`：部分解码器会得到 `NaN`，规范化为整数 `0`（`139`）。

### 6.3 FontDict 的 `Private size` 必须回填实际写入长度

FontDict 的 `Private`（op 18）参数是 `[size, offset]`，其中 `size` 必须等于 **清理（剔除 fontkit 不支持的操作符）后实际写入的 Private DICT 字节数**，而不是原字体记录的值。

原因是重建时会丢弃一部分操作符，Private DICT 因此变短；如果仍写原 `size`，fontkit 会按旧长度继续往后读，越过 Private DICT 读进相邻结构，症状是 `Unknown operator` 或错位的 `defaultWidthX`/`nominalWidthX`。

正确做法：先 `finalizePrivate()` 算出最终字节，再用它的 `.length` 作为 size。实现上通过 `rewriteDict()` 的 `resolveSize` 回调，在每次迭代中重新求值——因为 Private 的长度又影响布局位置，所以必须参与 §5.2 的定点迭代。

### 6.4 CID 字体必须正确处理 ROS / FDArray / FDSelect

`1_dfd.ofd` 的 `font_1`/`font_2`/`font_3` 是 `SSJ-PK7482000000x` 命名的 CID-keyed 字体，代码路径与普通 CFF 不同：

| 项 | 规则 |
| --- | --- |
| ROS（op 1230） | 三个参数必须是整数；`Supplement` **允许非 0**（如 `intro-数科.ofd` 的 `Adobe-GB1 Supplement=4`）；负数才是非法 |
| charset | CID 字体**必须有自定义 charset**（不能是预定义 0/1/2），否则 GID→CID 映射无处存放；缺失直接判为非法 |
| FDArray（op 1236） | 每个 FontDict **必须带 Private DICT**：缺了就取不到 `nominalWidthX`/`defaultWidthX`，charstring 的宽度语义无从解释 |
| FDSelect（op 1237） | 长度按 **format 精确计算**，不要用「下一个块起点减当前起点」推断 |

**FDSelect 长度计算公式**（`measureFdSelect()`）：

| format | 长度 | 组成 |
| --- | --- | --- |
| 0 | `1 + numGlyphs` | format 字节 + 每个字形一个 FD 编号 |
| 3 | `3 + nRanges × 3 + 2` | format(1) + nRanges(2) + nRanges 个 `first(2) + fd(1)` + sentinel(2) |
| 4 | `5 + nRanges × 6 + 4` | format(1) + nRanges(4) + nRanges 个 `first(4) + fd(2)` + sentinel(4) |

用相邻块推断会**差一字节**，导致其后所有块整体错位，进而让 fontkit 把 FDSelect 当成 Private DICT 解析。

### 6.5 Subrs 偏移要限制合理范围

Private DICT 里的 Subrs（op 19）偏移若指向的并非真正的 INDEX（部分私有封装会在 Private 之后接整份字体数据的副本），会把无关数据当成子程序表读入，造成内存爆炸或渲染异常。`readPrivate()` 因此加了合理性上限：条目数不得超过 `max(256, numGlyphs × 64)`，超出即按无 Subrs 处理。

## 7. 失败语义与 warning

### 7.1 完整链路

```text
adaptBareCff() 返回 null
  → normalizeFontBytes() 原样返回原始字节
  → createFontkit() 抛 Unknown font format
  → face.ts 转 OFDError('OFD_FONT_PARSE', '字体解析失败（FontName）')
  → provider.ts loadEmbeddedFace() 捕获并告警
       warn('W_FONT_MISSING', `字体解析失败：${message}`, { resourceId: font.id })
  → 该字体资源无可用字体面 → 主字体选择返回 null → 跳过整个文字对象
```

| 环节 | 行为 |
| --- | --- |
| 适配器内部 | `try/catch` 吞掉所有异常，返回 `null`；**不抛未捕获异常** |
| `normalizeFontBytes()` | 再包一层 `try/catch`，适配器意外抛错时同样原样返回 |
| `createFontFace()` | 抛出 `OFDError`，`code = 'OFD_FONT_PARSE'` |
| `provider.ts` | 捕获后产生 `W_FONT_MISSING`，继续尝试下一层来源（provider/default/supplementary） |
| 渲染侧 | 没有主字体时跳过整个文字对象（`render/object.ts`、`render/text-content.ts`） |

### 7.2 与告警的关系

| 现象 | 告警码 | 含义 |
| --- | --- | --- |
| 裸 CFF 被成功适配 | **无**（连 `W_FONT_MISSING` 都不产生） | 正常路径，不需要提示宿主 |
| 适配失败 / 非 CFF 损坏字体 | `W_FONT_MISSING` | 字体资源无可用字体面，文字对象被跳过 |
| 字体解析成功但某码点无字形 | `W_GLYPH_MISSING` | 只跳过该字形 |
| 显式 GID 无对应字形且不可用替代字体补位 | `W_FONT_MISSING` | 不绘制 `.notdef`，整个文字对象跳过 |

本特性**不新增 warning 码**：适配成功是正常路径，失败复用既有的 `OFD_FONT_PARSE → W_FONT_MISSING` 通道。`W_FONT_MISSING` 在字体库内按 `(code, resourceId, message)` 去重，因此同一字体资源失败只报一次。

## 10. 兼容性与当前边界

| 场景 | 行为 |
| --- | --- |
| 标准 sfnt / TTC / WOFF / WOFF2 | 直通，行为与引入前完全一致 |
| 合法裸 CFF | 适配为 `OTTO` sfnt 后解析，文字正常渲染 |
| 损坏的裸 CFF | 适配返回 `null`，回落 `OFD_FONT_PARSE` → `W_FONT_MISSING` |
| `unknown` 类型 | 不做任何转换，交由 fontkit 报错 |
| 裸 CFF 外的未知私有封装 | 不识别，仍走失败路径 |

当前边界：

- **只处理裸 CFF**：其它私有封装（如带自定义头的 CFF、加密字体）不在覆盖范围；
- **不合成 cmap**：只有轮廓的字体必须依赖显式 GID；若文档只给 TextCode 而不给 GID，仍然取不到字形；
- **度量是估算的**：`advanceWidth` 对所有字形取同一个估算值，`hmtx` 不反映每个字形的真实宽度；字宽优先由文档的 `DeltaX/DeltaY` 决定，因此实际排版一般不受影响，但在 `DeltaX` 缺失的场景下字距可能与原稿有差异；
- **`name`/`OS/2`/`post` 缺失**：字体名、字重等元信息不可用，按名称评分时只能退化为文档声明的 `FontName` 匹配；
- **判定层无独立单测**：`detectFontKind()` 目前由 `bare-cff.test.ts` 的真实样本间接覆盖，缺少针对各 `FontKind` 分支的定向用例。
