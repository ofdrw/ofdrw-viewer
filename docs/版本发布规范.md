# 版本发布规范

本文件规定版本发布时的版本号维护、发布说明撰写与打标签流程。适用于 `@ofdrw/ofdrw-viewer-engine`、`@ofdrw/ofdrw-viewer-crypto`、`@ofdrw/ofdrw-viewer-ui`、`@ofdrw/ofdrw-viewer-cli` 四个发布包，以及根包与演示站。

## 1. 适用范围

以下每次对外发布都必须遵循本规范：

- 四个 npm 发布包的新版本
- 随 tag 生成的 GitHub Release 正文
- CDN 产物与演示站版本

内部测试、CI 验证、本地构建不涉及发布说明。

## 2. 版本号

### 2.1 统一版本

四个发布包、根包与演示站共用同一版本号，不允许各包独立编号。修改版本时必须同时更新以下位置，缺一不可：

| 位置 | 内容 |
| --- | --- |
| `package.json`（根、engine、crypto、ui、cli、demo） | `version` 字段 |
| `packages/*/src/version.ts` | `VERSION` 常量 |
| `packages/ofdrw-viewer-ui/src/licenses.ts` | 许可清单中的三个包版本 |
| `packages/ofdrw-viewer-cli/test/acceptance/sea.acceptance.ts` | SEA 验收的 `--version` 断言 |
| `docs/CONTRACTS.md` §2.1 | 四个发布包版本号说明 |
| CDN 引用示例与 skills 文档 | 版本号引用 |

### 2.2 版本号选择

按语义化版本约定：

- **修订号**（`0.1.8` → `0.1.9`）：只修缺陷，无新增公开能力
- **次版本号**（`0.1.9` → `0.2.0`）：新增向后兼容的公开能力。`0.x` 阶段的次版本号跳跃同样代表有新增能力
- **主版本号**：出现不兼容的公开契约变更时使用

选择依据是**对外可见的变化**，不是提交数量或代码行数。

## 3. 发布说明

发布说明写在 tag 消息中，由 CI 直接作为 GitHub Release 正文。因此撰写质量直接决定用户看到的内容。

### 3.1 核心原则

1. **从用户角度写**。回答"用户会感受到什么变化"，而不是"代码怎么改的"。
2. **不写实现细节**。不出现函数名、类名、参数名、标准条款号（如 `GB/T 33190 §8.3.4`、`表 46`）、内部类型名、提交哈希。
3. **不做承诺**。不写"以后会支持"、"计划优化"等未来内容。
4. **篇幅克制**。每个条目一句话说清，不展开技术论证。用户需要细节时自会去查文档和变更记录。

### 3.2 必须遵守的两条规则

**规则一：未发布的版本不存在"修复"。**

发布说明的比对基线是**上一个实际对外发布的版本**，不是上一个 tag，也不是上一个提交。

若某个版本准备了但未打 tag 发布，其内容要并入下一次发布，且一律按"新增"描述——用户从未拿到过那个版本，就不存在"我们修好了什么"的说法。

> 示例：v0.1.9 只改版本号未发布，随后 v0.2.0 发布。v0.1.8 到 v0.2.0 之间新增的功能全部写入"新增"，不能因为提交信息里标了 `fix` 就写进"修复"。

判断方法：用 `git log <上一个已发布 tag>..HEAD` 取全部提交，逐条问"用户在上一版里见过这个东西吗"。

**规则二：只写用户可感知的内容。**

纯工程改动不进发布说明，包括：测试用例与夹具、CI 配置、构建脚本、代码重构、注释与文档修订、依赖版本微调。除非它改变了用户可见的行为。

> 示例："测试字体改为随仓库提交"属于工程改进，不写；"缩放后文字发虚"用户能看到，要写。

### 3.3 结构

固定三节，按此顺序，没有内容的节直接省略：

```markdown
## 本次更新

<一句话概述本版主题>

### 新增

- **功能名**：用户能做什么，一句话说清

### 修复

- 修复**现象描述**：用户原来遇到什么问题，现在是什么表现

### 优化

- 用户能感知的体验改善

## 安装

（安装命令与产物说明，见 3.5）

## 完整变更

https://github.com/ofdrw/ofdrw-viewer/compare/v<上一版>...v<本版>
```

### 3.4 写作要求

**新增**：说明"用户现在能做什么"，每个条目以加粗的功能名开头。

```markdown
- **文档动作与音视频播放**：支持点击链接跳转、打开网址、跳转书签、播放音频与视频
```

**修复**：说明"用户原来遇到什么问题"，以现象起头，不写根因。

```markdown
- 修复**竖排文字被裁掉**：票据中「购买方」「销售方」等竖排字段现在能完整显示
```

不写：`修复 computeDelta 去掉字体 advance 回退`——这是实现细节。

**优化**：只写用户能感知的体验改善，不写性能数字除非有明确对比。

**破坏性变更**：存在时单列一节，明确写出影响面和迁移方式，不能混在"优化"里。

### 3.5 安装信息

安装章节按当前产物形态写，版本号与本次发布一致：

```markdown
## 安装

npm install @ofdrw/ofdrw-viewer-engine@<版本>
npm install @ofdrw/ofdrw-viewer-crypto@<版本>
npm install @ofdrw/ofdrw-viewer-ui@<版本>
npm install -g @ofdrw/ofdrw-viewer-cli@<版本>

- **CLI 二进制**：`ofdrw-viewer-cli-<版本>-{平台}.tar.gz` 或 `.zip`，解压即用
- **CDN**：`ofdrw-viewer-lib-<版本>.zip`（engine → crypto 顺序加载）
- **演示站**：`ofdrw-viewer-ui-demo-<版本>.zip`，解压即静态站点
```

产物名称由 `.github/workflows/release.yml` 决定，改动产物命名时同步更新本节。

## 4. 发布流程

### 4.1 前置检查

```bash
# 1. 确认自上个已发布 tag 以来的提交范围
git log --oneline v<上一版>..HEAD

# 2. 确认版本号已统一修改
node .github/scripts/check-release-version.mjs v<本版>

# 3. 确认全仓库无残留旧版本号
grep -rn "0\.1\.8" --include=*.json --include=*.ts --include=*.md --exclude-dir=node_modules .

# 4. 跑通构建与测试
pnpm typecheck && pnpm build && pnpm test
```

版本号修改与发布说明建议分成两个提交：`chore(release): 版本号统一升级至 v<本版>` 与常规变更分离，便于回溯。

### 4.2 撰写发布说明

发布说明文件不入库（`.gitignore` 已忽略 `release-notes-*.md`），写在仓库根目录即可。

### 4.3 打标签

```bash
git tag -a v<本版> -F release-notes-v<本版>.md --cleanup=verbatim
```

必须使用注解标签（`-a`）与 `--cleanup=verbatim`：前者让消息随 tag 一起推送，后者保留原文格式不被 git 清理注释符号。

### 4.4 校验后推送

```bash
# 先确认 CI 能正确读取 tag 消息作为发布说明
node .github/scripts/generate-release-notes.mjs v<本版> <本版> /tmp/check.md

# 推送提交与标签
git push origin main
git push origin v<本版>
```

推送 `v*` 标签会触发 `.github/workflows/release.yml` 的完整发布：校验 → 构建 CLI/CDN/演示站 → 部署 Pages → 创建 GitHub Release → 发布 npm。npm 放在最后，因为版本号一经发布不可覆盖。

也可在 Actions 页面手动指定已存在的 tag 重跑，并把 `publish` 关掉只做构建验证。

### 4.5 修订已推送的发布说明

发布说明写在 tag 里，tag 推送后只能重建：

```bash
git tag -d v<本版>
git tag -a v<本版> -F release-notes-v<本版>.md --cleanup=verbatim
git push origin :refs/tags/v<本版>
git push origin v<本版>
```

改动 tag 会重写该 tag 的历史，已拉取过的人需要 `git fetch --tags --force` 才能同步。已生成的 GitHub Release 正文不会自动更新，需要手动编辑或重跑工作流。

## 5. 检查清单

发布前逐项确认：

- [ ] 六个 `package.json` 与三个 `VERSION` 常量版本一致
- [ ] `check-release-version.mjs` 校验通过
- [ ] 全仓库无残留旧版本号
- [ ] 发布说明对照的是**上一个已发布版本**，未发布版本的内容按"新增"处理
- [ ] 发布说明只写用户可感知的内容，无函数名、条款号、提交哈希
- [ ] 存在破坏性变更时已单列说明
- [ ] 安装章节的版本号与产物名正确
- [ ] typecheck、build、test 全部通过
- [ ] tag 为注解标签且使用 `--cleanup=verbatim`
