# 版本发布规范

本文件规定版本号维护、发布说明撰写与打标签流程，适用于四个发布包（engine、crypto、ui、cli）及根包、演示站的每次对外发布。

## 1. 版本号

四个包、根包与演示站共用同一版本号。修改时以下位置缺一不可：

| 位置 | 内容 |
| --- | --- |
| 六个 `package.json` | `version` |
| `packages/*/src/version.ts` | `VERSION` 常量 |
| `packages/ofdrw-viewer-ui/src/licenses.ts` | 三个包版本 |
| `packages/ofdrw-viewer-cli/test/acceptance/sea.acceptance.ts` | `--version` 断言 |
| `docs/CONTRACTS.md` §2.1、CDN 示例、skills 文档 | 版本号文字 |

按语义化版本选择：修订号只修缺陷；次版本号表示有新增的兼容能力（`0.x` 阶段同样适用）；主版本号用于不兼容变更。依据是对外可见的变化，不是提交数量。

## 2. 发布说明

发布说明写在 tag 消息里，CI 直接用它作为 Release 正文。两条硬规则：

**未发布的版本不存在“修复”。** 比对基线是上一个**实际发布**的版本，不是上一个 tag 或提交。准备了但没打 tag 的版本并入下次发布，内容一律按“新增”写。用 `git log <上个已发布 tag>..HEAD` 取全部提交，逐条问“用户在上一版见过它吗”。

**只写用户可感知的内容。** 测试、CI、构建脚本、重构、文档修订、依赖微调都不写。例如“测试字体入库”不写，“缩放后文字发虚”要写。

写法要求：从用户角度描述现象和结果，不出现函数名、参数名、标准条款号、提交哈希；不写未来计划；每条一句话，不展开论证。

结构固定三节，无内容则省略：

```markdown
## 本次更新

<一句话概述本版主题>

### 新增

- **功能名**：用户现在能做什么

### 修复

- 修复**现象**：用户原来遇到什么问题，现在是什么表现

### 优化

- 用户能感知的体验改善

## 安装

npm install @ofdrw/ofdrw-viewer-ui@<版本> 等四条命令
CLI 二进制、CDN、演示站的产物名

## 完整变更

https://github.com/ofdrw/ofdrw-viewer/compare/v<上一版>...v<本版>
```

存在破坏性变更时单列一节，写明影响与迁移方式，不能混进“优化”。

## 3. 发布流程

```bash
# 1. 确认变更范围与版本号一致
git log --oneline v<上一版>..HEAD
node .github/scripts/check-release-version.mjs v<本版>

# 2. 写发布说明（文件不入库，.gitignore 已忽略）
#    放到 release-notes-v<本版>.md

# 3. 打注解标签，--cleanup=verbatim 保留原文格式
git tag -a v<本版> -F release-notes-v<本版>.md --cleanup=verbatim

# 4. 校验 CI 能读到 tag 消息，再推送
node .github/scripts/generate-release-notes.mjs v<本版> <本版> /tmp/check.md
git push origin main
git push origin v<本版>
```

推送 `v*` 标签触发 `.github/workflows/release.yml`：校验 → 构建 → Pages → GitHub Release → npm。也可在 Actions 手动指定 tag 重跑，关掉 `publish` 只构建。

版本号修改建议单独提交为 `chore(release): 版本号统一升级至 v<本版>`。

修订已推送的说明需重建标签：`git tag -d` → 重新 `git tag -a` → 删除远端 → 重推。其他人需 `git fetch --tags --force`，且已生成的 Release 正文不会自动更新。

## 4. 检查清单

- [ ] 六个 `package.json` 与三个 `VERSION` 常量一致，`check-release-version.mjs` 通过
- [ ] 全仓库无残留旧版本号
- [ ] 发布说明对照上一个**已发布**版本，未发布内容按“新增”处理
- [ ] 无函数名、条款号、提交哈希；破坏性变更已单列
- [ ] typecheck、build、test 通过
- [ ] tag 为注解标签且使用 `--cleanup=verbatim`
- [ ] 每个包目录的 `LICENSE` 与仓库根 `LICENSE` 内容一致

## 5. LICENSE 随包发布

仓库根 `LICENSE` 是唯一权威来源，五个发布包目录各存一份相同副本。以下产物必须包含 `LICENSE`，缺失时打包脚本直接报错终止：

| 产物 | 来源 | 保证方式 |
| --- | --- | --- |
| engine、crypto、ui、cli、api-server 的 npm 包 | 各包目录 `LICENSE` | `package.json` 的 `files` 显式列出 |
| cli、api-server 的 SEA 离线压缩包 | 各包目录 `LICENSE` | `package-sea.mjs` 必需校验并复制到压缩包根目录 |
| CDN 资产包 `ofdrw-viewer-lib-<版本>.zip` | 仓库根 `LICENSE` | `package-cdn-assets.mjs` 打包前校验并放入压缩包根目录 |

修改许可协议时，需同时更新根 `LICENSE` 与五个包目录副本；`package-sea.mjs` 与 `package-cdn-assets.mjs` 会在副本缺失时中断发布。
