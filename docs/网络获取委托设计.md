## 1. 背景

engine 目前有两条“自己获取外部资源”的路径：

1. **OFD 文档**：`OFDSource` 的 `url` 变体 → `api/source.ts` 构造 `HttpRangeSource`（`container/byte-source.ts`），内部执行 HEAD/Range 探测、206 校验、`Content-Encoding` 回退整包、416 处理。
2. **字体文件**：`FontInput` 的 `url`/`path`/`filePath` 变体 → `api/document.ts` 的 `createFontInputLoader()`，内部用 `fetch` 读 URL，路径来源在 Web 下不支持；Node 由 CLI 注入 `loadInput` 读取。

这带来几个问题：

- **职责越界**：渲染/解析库承担了网络策略、鉴权、下载进度与平台分支。
- **重复读取**：UI 打开 URL 文档时，crypto 先读一遍检测加密，engine 再用 Range 读一遍；字体也可能被重复读取。
- **平台耦合**：`HttpRangeSource` 的 CDN/gzip 兼容、取消语义、CORS 要求和测试矩阵都被压进 engine。
- **边界模糊**：`node-file`/`wechat-file` 作为未实现占位长期留在公共类型里，容易让人误以为 engine 负责读取本地文件。

因此本设计把“通过网络（或文件系统）获取字节”全部委托给调用方：**engine 只接受已经可读的字节或字节源**。

## 2. 目标与非目标

### 2.1 目标

- engine 源码中不再出现 `fetch`、网络 URL 解析、本地路径读取。
- `OFDSource` 只表达“字节已到手 / 宿主可随机读”。
- `FontInput` 只表达“宿主已读好的字体字节”。
- UI 的对外 API 保持不变：`source` 仍可传 URL 字符串，内部用 `HttpByteSource` 走 Range。
- CLI 现有行为不回退；本地文件仍按需随机读。
- 取消、鉴权头、进度等由宿主自行控制。

### 2.2 非目标

- 不改渲染、解析、ZIP 容器、资源限制逻辑。
- 不在本次实现 UI 的“下载原文件”按钮（另立 P1，见 §5.5）。
- 不改 crypto 包自身的网络策略；但 UI 应把同一个 `ByteSource` 复用给 crypto，避免重复下载。

## 3. 职责边界

| 层 | 负责 | 不负责 |
|---|---|---|
| engine | 解析、渲染、从 `ByteSource` 随机读字节 | 下载、URL 拼接、鉴权、平台文件读取 |
| UI | URL → `HttpByteSource`（Range）、字体 → 字节、下载原文件 | ZIP 解析、渲染 |
| CLI | 本地文件 → `NodeFileByteSource`；字体 → 字节/Provider；未来 URL 输入自行下载 | 渲染与解析 |
| 小程序宿主 | `wx.downloadFile` → 临时文件/字节源；字体读取 | 渲染与解析 |
| crypto | 在宿主提供的来源上检测/解密/验签 | 决定来源如何获取（沿用宿主传入的 `CryptoSource`） |

## 4. engine 侧设计

### 4.1 `OFDSource` 收敛

```ts
// platform/source.ts
export type OFDSource =
  | { kind: 'arraybuffer'; data: ArrayBuffer | Uint8Array }
  | { kind: 'blob'; blob: Blob }
  | { kind: 'custom'; source: ByteSource };
```

删除 `url`、`node-file`、`wechat-file` 三个变体。

`api/source.ts` 的 `openByteSource()` 改为纯适配：

- `arraybuffer`：校验非空，包装 `ArrayBufferSource`；
- `blob`：校验 `Blob` 与大小，包装 `BlobSource`；
- `custom`：校验 `read` 为函数后直接返回；
- 其他：抛出明确迁移提示，例如
  `未知来源类型：url。engine 不再负责网络获取，请宿主下载后传 arraybuffer/blob，或传 custom ByteSource。`

`node-file`/`wechat-file` 的调用方（CLI、小程序）本来就应传 `custom`，不受影响。

### 4.2 `ByteSource` 契约

接口保持不变，补充正式文档（`ready`/`close` 目前是鸭子类型）：

```ts
export interface ByteSource {
  /** 总字节数，单位 byte；异步探测完成前允许为 0。 */
  readonly size: number;
  /** 读取 [offset, offset + length)；越界截断。 */
  read(offset: number, length: number): Promise<Uint8Array>;
  /** 可选：异步探测完成；ZipReader.open 会先等待。 */
  ready?(): Promise<void>;
  /** 可选：释放资源；容器关闭时调用，实现应幂等。 */
  close?(): Promise<void> | void;
}
```

- `ready()` 已在 `ZipReader.open` 中等待（`container/zip-reader.ts`）。
- `close()` 已由 `closeByteSource()` 调用（`api/container.ts`、`container/zip-container.ts`）。
- `size` 为 0 时 engine 会报 `OFD_INVALID_PACKAGE`，因此探测失败应由 `ready()` 抛出真实错误。

### 4.3 删除清单

| 文件 | 删除内容 |
|---|---|
| `platform/source.ts` | `url` / `node-file` / `wechat-file` 变体 |
| `api/source.ts` | `url` 分支、`bindGlobalFetch()`、`HttpRangeSource`/`FetchLike` 引用 |
| `container/byte-source.ts` | `HttpRangeSource`、`FetchLike`、`FetchResponseLike`、`parseContentRange`/`parseContentLength`/`hasContentEncoding` 等仅服务 HTTP 的辅助 |
| `api/types.ts` | `loadInput?: FontInputLoader` 与相关注释；`FontInput` 的 url/path 说明 |
| `api/document.ts` | `createFontInputLoader()`、`fontInputLoader` 字段与 `init.fontInputLoader` |
| `font/provider.ts` | `FontInputLoader` 类型、`FontLibraryOptions.loadInput`、`readInput()` 中的 url/path 分支 |
| `platform/font-provider.ts` | `FontInput` 的 url/path/filePath 变体 |
| `index.ts` | `FontInputLoader` 导出 |

`OFDSource` 的事件字段 `sourceKind` 自动收窄为 `arraybuffer | blob | custom`。

### 4.4 字体委托

`FontInput` 收敛为“只含字节”：

```ts
export interface FontInput {
  /** 字体文件字节。 */
  readonly data: ArrayBuffer | Uint8Array;
  /** 字体族名；用于诊断与别名匹配。 */
  readonly family?: string;
}
```

- `defaultFonts` / `supplementaryFonts` 只接受已读好的 `data`。
- 删除 `FontInputLoader` 与 `loadInput`；engine 不再提供默认 URL/路径读取。
- 需要“按需读取”的宿主使用已有的 `FontProvider`：

```ts
interface FontProvider {
  match(request: FontMatchRequest): Promise<FontInput | FontInput[] | null>;
}
```

`match()` 是异步的，宿主可以在这里读文件、fetch 字体或查缓存，返回 `{ data }`。这是字体按需加载的唯一入口，也天然满足“engine 不联网”。

- CLI 当前用 `{ path }` + `loadInput`；实施时评估过 `NodeFontProvider`，因 TTC 多字体面在 provider 路径产生可见字形漂移，最终改为 CLI 的 `loadFontInputs()` 预读为 `{ data }` 后传 `supplementaryFonts`，删除 `loadInput`，保留 96 MiB 预算与优先级。
- UI 当前没有字体配置；将来若开放字体入口，UI 自己 `fetch` 成 `data` 或实现 `FontProvider`。
- 小程序宿主自行读临时文件为 `data`。

### 4.5 迁移示例

engine 使用者从 URL 改为自读：

```ts
// 旧
const doc = await OFDDocument.open({ source: { kind: 'url', url } });

// 新（浏览器）
const response = await fetch(url);
if (!response.ok) throw new Error(`HTTP ${response.status}`);
const data = await response.arrayBuffer();
const doc = await OFDDocument.open({ source: { kind: 'arraybuffer', data } });

// 新（需要 Range / 复用同一份字节）
const httpSource = new HttpByteSource(url);
const doc = await OFDDocument.open({
  source: { kind: 'custom', source: httpSource },
});
```

字体：

```ts
// 旧
supplementaryFonts: [{ url: '/fonts/a.ttf' }]

// 新
const data = await (await fetch('/fonts/a.ttf')).arrayBuffer();
supplementaryFonts: [{ data }]
```

## 5. UI 侧设计

### 5.1 `HttpByteSource`

位置：`packages/ofdrw-viewer-ui/src/source/http-byte-source.ts`。

职责：把 URL 适配为 engine 的 `ByteSource`，行为与现 `HttpRangeSource` 对齐，并补上 UI 需要的取消与进度能力。

```ts
export interface HttpByteSourceOptions {
  /** 额外请求头；与全局 requestInit.headers 合并，后者优先。 */
  readonly headers?: Record<string, string>;
  /** 是否允许服务器忽略 Range 时整包回退；默认 true。 */
  readonly allowFullDownload?: boolean;
  /** 取消信号；close() 也会中止进行中的请求。 */
  readonly signal?: AbortSignal;
  /** 整包回退时的进度回调；Range 模式不保证总进度。 */
  readonly onProgress?: (loaded: number, total: number | undefined) => void;
  /** 可注入 fetch，便于测试与宿主定制。 */
  readonly fetch?: typeof fetch;
}

export class HttpByteSource implements ByteSource {
  constructor(url: string, options?: HttpByteSourceOptions);
  get size(): number;
  ready(): Promise<void>;
  read(offset: number, length: number): Promise<Uint8Array>;
  close(): Promise<void>;
}
```

**探测流程**（沿用现有策略，避免 CDN 回归）：

| 场景 | 行为 |
|---|---|
| HEAD 成功 + `Content-Length` + 无 `Content-Encoding` | 直接作为 `size` |
| HEAD 响应含 `Content-Encoding`（gzip/br） | 放弃 Range，GET 整包并缓存，按解压后长度设置 `size` |
| HEAD 失败或缺少长度 | `GET Range: bytes=0-0` |
| 206 + `Content-Range` 有总长 | 用总长作为 `size` |
| 206 但总长为 `*` | 用 HEAD 的 `Content-Length` 兜底；仍无则报错 |
| 200（服务器忽略 Range） | 整包读取并缓存；`allowFullDownload=false` 时报错 |
| 416 | `size = 0`，由 engine 报包非法 |

**读取流程**：

| 场景 | 行为 |
|---|---|
| 206 | 校验 `Content-Range` 起点；若含 `Content-Encoding` 或总长与 `size` 不一致 → 整包读取后切片；否则返回响应体（按需截断） |
| 200 | 整包读取并缓存，后续读内存 |
| 416 | 返回空 `Uint8Array` |
| 其他状态 | 抛 `OFDError('OFD_INVALID_PACKAGE', ...)` |

**其他约定**：

- 所有请求带 `signal`；`close()` 触发 `AbortController.abort()`，并置关闭标记；关闭后 `read` 抛 `OFD_CLOSED`。
- `ready()` 缓存探测结果与错误，重复调用不重复请求。
- 整包模式缓存 `Uint8Array`；Range 模式不缓存整包，避免内存翻倍。
- 不打印完整 URL（可能含凭据查询串）。
- 需要服务端允许 `Range` 并暴露 `Content-Range`；跨域时需 `Access-Control-Expose-Headers`，沿用现有约束。

### 5.2 打开流程改造

`document-controller.ts` 的 `normalizeViewerSource()` 目前把字符串/`{url}` 转成 `{ kind: 'url' }`。改为：

1. `ArrayBuffer` / `Uint8Array` / `Blob` → 原样返回；
2. 字符串 / `{ url, headers? }` → 构造 `HttpByteSource`，返回 `{ kind: 'custom', source }`；
3. 同时保留 `origin`（原始 URL、File 名），供文档标题、导出命名、下载原文件使用。

`viewer.open()` 的时序：

```text
open(source)
  ├─ normalizeViewerSource → OFDSource（url 已变成 custom ByteSource）
  ├─ crypto.prepareOpen(source)
  │    ├─ toCryptoSource：url 已不存在；custom → { kind: 'byte-source', source }
  │    ├─ inspect：crypto 用 engine 容器按需读取（不解密时只读需要的条目）
  │    └─ 加密时 decrypt：按需/整包读取后生成明文容器
  ├─ controller.open(source) 或 openContainer(decrypted)
  └─ 保存 origin，供后续命名与下载
```

对外 API 不变：`new OFDViewer({ source: 'https://…/a.ofd' })` 仍然可用。

### 5.3 crypto 集成

UI 的 `toCryptoSource()` 目前只映射 `arraybuffer` / `blob` / `url`；新增：

```ts
case 'custom':
  return { kind: 'byte-source', source: source.source };
```

crypto 的 `openCryptoContainer()` 对 `byte-source` 走 `openZipVirtualContainer`，**按需读取**；`readCryptoSource()` 的整包读取只用于必须整包的场景（如解密）。`isolateByteSource()` 不转发 `close`，因此 crypto 关闭容器不会误关 UI 的 `HttpByteSource`。

效果：URL 文档在“检测加密”阶段不再整包下载，Range 请求与渲染共用同一份字节源。

### 5.4 生命周期

| 场景 | `ByteSource` 归属 | 关闭方 |
|---|---|---|
| 明文文档，`custom`/`arraybuffer`/`blob` | engine 容器拥有 | engine 在 `doc.close()` 时调用 `closeByteSource()` |
| 加密文档（需解密） | UI 创建；crypto 只借用（不转发 close）；engine 打开的是解密容器 | UI 在切换/关闭文档时调用 `httpSource.close()`；解密完成后可提前关闭 |
| 打开失败 | `openZipVirtualContainer` 的 catch 关闭 | engine |

`HttpByteSource.close()` 必须幂等，禁止重复 abort 报错。

### 5.5 下载原文件（P1，后续）

委托后“下载原文件”不再依赖 engine：

- 若 UI 保留了原始 URL，直接 `<a href=url download>`（同源）或 `fetch → Blob`；
- 若 UI 保留了原始 `File`，直接 `downloadBlob(file, filename)`；
- 若只保留了 `HttpByteSource`，可让它提供 `readAll()` 或复用整包缓存；不在本设计范围内展开。

### 5.6 进度与取消

- 取消：`open()` 的 `signal` 直接传给 `HttpByteSource` 的每个请求，`AbortController` 生效；`close()` 兜底中止。
- 进度：`HttpByteSource` 的 `onProgress` 仅在整包回退/整包来源时可用；Range 模式只上报“已读字节”，不承诺百分比。UI 的加载态仍以 `document:open:start/end` 为准。

## 6. CLI 设计

- 本地文件：`NodeFileByteSource` 已是 `custom` 来源，无需改动。
- 字体：最终实现为 `fonts.ts` 的 `loadFontInputs()` 预读 `{ data }`：
  - 构造转换任务时读取 `--font-dir`/系统字体扫描结果的文件字节，以 `FontInput[]` 传给 `supplementaryFonts`；
  - 保留 `MAX_SYSTEM_FONT_BYTES` 预算、排序/realpath 去重与 warning 行为，输出与改造前一致；
  - 未保留 `NodeFontProvider`（TTC 多面路径会产生字形漂移，且会成为死代码）。
- 可选：若未来支持 URL 输入，CLI 自己 `fetch` 到临时文件或内存，再传 `arraybuffer`/`custom`；engine 不参与。

## 7. 小程序宿主

- OFD：`wx.downloadFile` 得到临时路径 → `wx.getFileSystemManager().readFile` 或自定义 `ByteSource` → `custom`/`arraybuffer`。
- 字体：自行读取后传 `data`。
- 不再依赖 `wechat-file` 类型（已删除）。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| `HttpByteSource` 与迁移前 engine HTTP Range 行为漂移 | 把原 HTTP 边界测试迁移到 UI 侧作为基线（HEAD/Range/206/200/416/编码回退/取消） |
| CDN gzip 导致 Range 数据错位 | 保留 `Content-Encoding` 检测与整包回退 |
| 大文件 Range 请求过多 | 先不做缓存；后续可在 UI 增加小页缓存（不改 engine） |
| crypto 与 engine 重复读取 | custom/byte-source 按需读取；解密必须整包属预期 |
| 字体按需读取的异步/预算 | 一次性字体由宿主读成 `{ data }`（CLI 走此路径）；需要按需读取时用 `FontProvider.match()`，保留 warning 与预算 |
| 第三方 engine 用户迁移成本 | 提供 README/API 迁移示例；错误信息带指引 |
| `close()` 竞态 | `HttpByteSource.close()` 幂等，读取前检查关闭标记 |
