# OFD 音视频与动作方案设计

本文是 OFD 音视频（音频/视频）播放与动作（Action）体系的完整设计方案，覆盖 engine、UI、CLI 三个包的职责划分、公共 API、数据模型、渲染叠加、交互与生命周期。**本文只做设计，不描述代码实现进度**；实现阶段的文件路径与落地顺序见第 12 章。

依据标准：GB/T 33190-2016《电子文件存储与交换格式 版式文档》第 12 章（视频）、第 14 章（动作）、7.9（资源）、10（图像）与附录 A.5/A.6 的 XSD 定义。

---

## 1. 定位、范围与非目标

### 1.1 问题

OFD 包内可以嵌入音频、视频，并通过 **Sound / Movie 动作**触发播放。当前引擎只把 `MultiMedias` 下的 `MultiMedia` 当作**图片资源**处理（`model/resource-decode.ts` 的 `decodeImage` 对 `Type != Image` 直接 `return undefined` 丢弃），完全丢弃 `Type=Audio|Video`，也不解析任何 `Actions` 节点。结果是：

- 含音视频的 OFD 在查看器里**没有任何播放入口**；
- 含超链接（URI 动作）、文档打开自动播放（DO 动作）的 OFD，交互全部丢失；
- CLI 无法列出或导出音视频资源，无法把文档携带的附件类素材交付给下游。

### 1.2 设计范围

| 层 | 交付物 |
| --- | --- |
| engine | ① 解析并索引音视频资源（`MultiMedia` 的 Audio/Video）；② 解析并暴露动作（Document / Page / 图元 / 大纲节点上的 `Actions`）；③ 提供**资源字节获取**公共 API（不依赖 DOM）；④ 提供**动作目标与播放区域几何**（OFD 坐标 → 页面像素）计算；⑤ 提供**按事件收集动作**的查询面与动作事件派发。 |
| UI | ① 用 HTML5 `<video>`/`<audio>` 在页面图层之上**按图元区域叠加**播放窗口；② 实现动作执行器（动作队列、同步/异步、循环、暂停/继续/停止）；③ 交互：点击触发 CLICK 动作、打开页面触发 PO、打开文档触发 DO；④ 播放控件、无障碍、i18n、主题、打印/导出时的行为。 |
| CLI | ① `info` 增补动作与音视频资源摘要；② 新增音视频资源导出能力（导出为独立文件）；③ 保持 Node 环境无 DOM 依赖。 |

### 1.3 非目标

- 不实现音视频**解码/转码**。浏览器 `<video>`/`<audio>` 支持什么编解码就用什么；不支持时向宿主报告"不支持"，不做软件解码兜底。
- 不实现**动作编辑**（新增/修改/删除动作），不实现 OFD 写回。
- 不实现**运行时采集/录制**，不实现播放时的 DRM。
- 不实现 `Region`（复杂启动区域）的完整 hit-test 几何求交（见 §5.6，第一版按外接矩形处理，几何能力预留）。
- 不替代 PDF/OFD 阅读器的"演示放映"模式；不做自动播放策略绕过（浏览器的 autoplay 限制由 UI 遵守，见 §7.7）。

### 1.4 事实来源

- 标准原文：`src_material/GBT33190-2016/full.md`。
- 跨包契约：[CONTRACTS.md](./CONTRACTS.md)（错误码、warning 码、公共 API 边界、I/O 委托）。
- 既有相近能力的样板：附件（`getAttachments`/`saveAttachment`/`getAttachmentData`）与字体（`getFontResources`）——音视频资源索引与字节获取**沿用其口径**。

## 2. 标准依据（设计输入）

### 2.1 多媒体资源 `CT_MultiMedia`

资源文件（`PublicRes` / `DocumentRes` / `PageRes`）的 `MultiMedias/MultiMedia`，`ID` 为 `ST_ID`：

| 属性/元素 | 类型 | 必需 | 设计口径 |
| --- | --- | --- | --- |
| `ID`（元素扩展属性） | `ST_ID` | 是 | 资源标识，全资源作用域内唯一 |
| `Type` | `xs:string` | 是 | 取值 `Image`/`Audio`/`Video`（XSD 枚举） |
| `Format` | `xs:string` | 否 | 标准表述为 "BMP、JPEG、PNG、TIFF 及 AVS 等"；**音视频的实际格式（mp3/mp4/avi…）标准未枚举**，实践中以扩展名/MIME 为准 |
| `MediaFile`（子元素） | `ST_Loc` | 是 | 包内相对路径，受资源文件 `BaseLoc` 约束 |

**关键取舍**：`Format` 不可靠。设计上**以 `MediaFile` 扩展名推导格式/MIME 为主，`Format` 仅作覆盖提示**。这与现有图片资源 `inferImageFormat(Format 属性, 路径)` 的优先级（Format 优先）**相反**——图片保留现状不动，音视频不沿用该优先级，理由见 §4.4。

### 2.2 动作 `CT_Action`

`Action` 由 `Event` 触发，`Event` 限定三值：`DO`（文档打开）、`PO`（页面打开）、`CLICK`（区域内单击）。`Action` 内含**一个**动作体（`xs:choice`）：

| 动作体 | 属性 | 语义 | 本方案 |
| --- | --- | --- | --- |
| `Goto` | `Dest` 或 `Bookmark@Name` | 文档内跳转 | ✅ 提供结构化信息，UI 执行 |
| `URI` | `URI`（必填）、`Base`、`Target`（XSD 另有 `Target`，正文表 56 未列） | 打开外部链接 | ✅ 提供结构化信息；UI 先弹确认框，确认后按 `Target` 打开 |
| `GotoA` | `AttachID`、`NewWindow`（默认 true） | 打开包内附件 | ✅ 提供结构化信息 |
| `Sound` | `ResourceID`（必填）、`Volume` 0..100（默认 100）、`Repeat`（默认 false）、`Synchronous`（默认 false） | 播放音频 | ✅ 本方案核心 |
| `Movie` | `ResourceID`（必填）、`Operator` ∈ `Play`/`Stop`/`Pause`/`Resume`（默认 `Play`） | 播放/控制视频 | ✅ 本方案核心 |

`Region`（可选，`CT_Region`）指定复杂启动区域；缺省以所在图元/页面的外接矩形为启动区域。

### 2.3 动作可挂载的位置

| 宿主 | 路径 | 合法事件 | 几何来源 |
| --- | --- | --- | --- |
| 文档 | `Document.xml` → `Actions/Action` | 标准要求 `DO` | 无（整文档） |
| 页面 | `Page.xml` → `Page/Actions/Action`（与 `Content` 同级） | 标准要求 `PO` | 页面区域 |
| 图元对象 | `CT_GraphicUnit/Actions/Action`（所有图元基类都有） | `CLICK` | 图元 `Boundary` |
| 大纲节点 | `CT_OutlineElem/Actions/Action` | 标准未限定 | 无；UI 在大纲项"被激活"时执行 |

**重要**：`Actions` 位于 `CT_GraphicUnit`（**所有图元基类的共同扩展**），因此标准允许文字、路径、图像、复合对象、页面块都挂载动作，不只是 `ImageObject`。设计必须覆盖全部图元，不能只处理图片。

### 2.4 播放窗口规则（第 12 章）

标准原文明确两条：

1. **图元触发的播放，宜使用该图元的外观区域大小作为嵌入式播放窗口**；
2. **其他情况下（文档/页面/大纲触发），宜使用弹出式窗口**。

配套建议：图元触发的视频，宜取视频中某一静态帧做成图像对象，并为该图像对象附加边框与 `Movie` 动作——即"封面帧 + 点击播放"的常见形态。设计必须同时支持这两种呈现（嵌入式 / 弹出式），见 §7.3。

### 2.5 事件与触发时序

标准只定义"何时触发"，不定义"动作队列如何执行"。本设计采用**动作序列顺序执行 + `Synchronous` 阻塞语义**（约定见 §6.3），这是对标准的工程化补充，必须在实现与文档中标注为**本库约定**而非标准要求。

## 3. 总体架构

### 3.1 分层与数据流

```text
                 ┌─────────────────────── UI（浏览器） ───────────────────────┐
                 │  MediaOverlay（<video>/<audio> 叠加在 ofd-page__surface）    │
                 │  ActionService / ActionExecutor / PointerRouter              │
                 │    ↑ 完整设计见《UI动作处理机制设计》                         │
                 └───────────▲────────────────────────────▲───────────────────┘
                             │ MediaResource + 字节/Blob     │ ActionInfo + 几何
                             │                              │
                 ┌───────────┴──────────────────────────────┴───────────────────┐
                 │ engine（平台无关）                                            │
                 │  model/resource-decode  → MediaResource 索引                 │
                 │  model/action-decode    → ActionInfo 索引（文档/页/图元/大纲） │
                 │  api/media.ts           → getMediaResources / getMediaData    │
                 │  api/actions.ts         → getDocumentActions / getPageActions │
                 │                           getObjectActions / getOutlineActions │
                 │  render/geometry.ts     → 动作触发区域 → 页面像素几何          │
                 └───────────▲──────────────────────────────────────────────────┘
                             │ 同一公共 API
                 ┌───────────┴──────────────────────────────────────────────────┐
                 │ CLI（Node）: info 摘要 / 媒体导出（写文件，无 DOM）             │
                 └──────────────────────────────────────────────────────────────┘
```

### 3.2 职责边界（硬约束）

沿用 [CONTRACTS.md](./CONTRACTS.md) §3.1 与 §7.7：

| 事项 | engine | UI | CLI |
| --- | --- | --- | --- |
| 解析 MultiMedia/Activity XML | ✅ 唯一来源 | ❌ 禁止自行解析 | ❌ 禁止自行解析 |
| 音视频**字节**获取 | ✅ 提供（`Uint8Array`，受 `maxMediaBytes` 限流） | ✅ 消费，转 Blob/ObjectURL | ✅ 消费，写文件 |
| ObjectURL / Blob / DOM | ❌ **禁止** | ✅ | ❌ |
| 播放器实例、播放队列 | ❌ | ✅ | ❌ |
| 自动播放策略、静音降级 | ❌ | ✅ | ❌ |
| 几何：动作区域 → 页面像素 | ✅ 计算 | ✅ 再叠加缩放/旋转/翻页变换 | ✅ 用于输出 |
| 网络/本地 I-O | ❌ | ✅（`HttpByteSource`） | ✅（`NodeFileByteSource`） |
| 点击命中测试 | ✅ 提供矩形与区域数据 | ✅ 提供指针事件与坐标 | — |

**engine 不许碰 DOM**：这是本方案的**最重要约束**。engine 内部已有 `Canvas2DLike` 抽象以保持平台无关，音视频新增 API 全部返回**纯数据**（字节、`Uint8Array`、矩阵、毫米/像素数值），任何 `Blob`、`URL.createObjectURL`、`HTMLVideoElement` 都只在 UI 侧出现。

### 3.3 为什么资源字节由 engine 提供而不是 UI 自己读包

UI 侧理论上可以拿 `readSourceBytes()` 拿整包再自解 zip 取文件，但：

1. 违反"UI 不实现 OFD 解析"的包级职责（CONTRACTS §3.1）；
2. 会绕开 engine 的 `ResourceLimits`（`maxEntryBytes` 等）与解压炸弹防护；
3. 无法复用 `BaseLoc` 解析与路径规范化（`resolvePackagePath`）；
4. 加密包（crypto 解密后的 `VirtualContainer`）只有 engine 手里有正确容器句柄。

因此**资源字节必须经 engine 交付**，UI 只负责把字节变成播放器可用的 URL。

## 4. engine 数据模型

### 4.1 新增：`MediaResource`

```ts
/** 音视频多媒体类型。 */
export type MediaKind = 'image' | 'audio' | 'video';

/** 资源文件中 MultiMedias/MultiMedia 的解析结果（音视频专用；图片沿用 ImageResource）。 */
export interface MediaResource {
  /** ST_ID，资源标识（十进制字符串归一化）。 */
  id: ResourceId;
  /** 多媒体类型。 */
  kind: 'audio' | 'video';
  /** 已解析的包内绝对路径（BaseLoc 已展开，去前导 `/`）。 */
  mediaFile: string;
  /** MIME 类型，如 `video/mp4`；无法判定时为 `application/octet-stream`。 */
  mimeType: string;
  /** 声明格式原文（`Format` 属性，trim 后；未声明时省略）。 */
  format?: string;
  /** 字节大小（byte）。未读取内容的资源省略该字段，读取后补齐。 */
  sizeBytes?: number;
  /** 声明来源：public 资源文件 / 文档资源文件 / 页资源文件。 */
  scope: 'public' | 'document' | 'page';
  /** 声明它的资源文件包内路径，便于排障。 */
  declaredIn: string;
}
```

**设计说明**：

- **不复用 `ImageResource`**：`ImageResource` 带 `ImageFormat` 联合类型（`png`/`jpeg`/…）与图片解码语义，混入 audio/video 会污染 `ImageFormat` 与 `decodeImage` 分支。音视频**单独建模**，但**共用同一份资源索引遍历**（`MultiMedias` 一次遍历，按 `Type` 分派：`Image` → `images[]`，`Audio`/`Video` → `media[]`）。这修正了当前 `decodeImage` 里对非 Image 静默 `return undefined` 的行为。
- **`sizeBytes` 可选**：索引阶段**不读字节**（与 `getAttachments` 一致：只读索引，零 IO）。UI 播放前需要知道体积；因此在"索引"与"取字节"之间增加可选的"探测"能力（§6.3 的 `getMediaResourceSize`），或在取字节时回填。
- **`kind` 恒为 audio/video**（`image` 只在 `MediaKind` 联合类型里供 UI 判断使用，`MediaResource.kind` 不会出现 image）。

### 4.2 新增：`ActionInfo`

```ts
/** 动作事件类型，对应 OFD `Action@Event`。 */
export type ActionEvent = 'DO' | 'PO' | 'CLICK';

/** 动作体类型，对应 OFD `CT_Action` 的 xs:choice。 */
export type ActionType = 'goto' | 'uri' | 'gotoa' | 'sound' | 'movie';

/** 动作宿主（动作声明在哪种节点上）。 */
export type ActionOwner =
  | { kind: 'document' }
  | { kind: 'page'; pageIndex: number }
  | { kind: 'object'; pageIndex: number; objectId?: ResourceId }
  | { kind: 'outline'; path: readonly number[] };

/** 动作触发区域（毫米，页面坐标系）。 */
export interface ActionRegion {
  /** 复杂区域声明原文的解析结果（仅支持 Move/Line/贝塞尔组成的路径，见 §5.6）。 */
  areas: ReadonlyArray<ReadonlyArray<ActionRegionPath>>;
  /** 外接矩形（mm），缺省区域时为图元 Boundary 或页面区域。 */
  bbox: Box;
}

/** 动作统一结构；`type` 决定 payload 形状。 */
export interface ActionInfo {
  /** 事件类型。 */
  event: ActionEvent;
  /** 动作类型。 */
  type: ActionType;
  /** 宿主位置。 */
  owner: ActionOwner;
  /** 显式声明的启动区域（`Action/Region`）；缺省时省略。 */
  region?: ActionRegion;
  /** 动作 payload，按 type 区分。 */
  payload: GotoActionPayload | UriActionPayload | GotoAActionPayload | SoundActionPayload | MovieActionPayload;
}

export interface GotoActionPayload {
  type: 'goto';
  /** 目标区域（`Dest`），复用既有 `DocumentDestination`（页索引 + 毫米坐标）。 */
  dest?: DocumentDestination;
  /** 目标书签名称（`Bookmark@Name`）。 */
  bookmarkName?: string;
}

export interface UriActionPayload {
  type: 'uri';
  /** 目标 URI（`@URI`，可能为相对地址）。 */
  uri: string;
  /** 基础 URI（`@Base`）。 */
  base?: string;
  /** 打开方式提示（XSD `@Target`：`_blank` 等）；标准正文未定义语义。 */
  target?: string;
}

export interface GotoAActionPayload {
  type: 'gotoa';
  /** 附件标识（`@AttachID`，xs:IDREF）。 */
  attachId: string;
  /** 是否新窗口打开，XSD 默认 true。 */
  newWindow: boolean;
}

export interface SoundActionPayload {
  type: 'sound';
  /** 音频资源 ID。 */
  resourceId: ResourceId;
  /** 播放音量 0..100，默认 100。 */
  volume: number;
  /** 是否循环；为 true 时 `Synchronous` 无效。 */
  repeat: boolean;
  /** 是否阻塞后续动作，默认 false。 */
  synchronous: boolean;
}

export interface MovieActionPayload {
  type: 'movie';
  /** 视频资源 ID。 */
  resourceId: ResourceId;
  /** 放映参数，默认 `Play`。 */
  operator: 'Play' | 'Stop' | 'Pause' | 'Resume';
}
```

**设计说明**：

- **payload 判别联合**而非可选字段平铺：`ActionInfo` 是跨越四个宿主、五种类型、二十余个字段的宽类型；平铺会让消费方无法穷尽匹配，也会让"不适用字段"到处是 `undefined`。判别联合让 UI 的 `switch (action.type)` 类型完备。
- **`owner` 而非重复携带宿主信息**：UI 执行动作时要区分来源（例如图元触发的 Movie → 嵌入式窗口；文档/页/大纲触发 → 弹出式），`owner.kind` 正是"呈现模式"的判定依据（§7.3）。
- **`region` 与几何分离**：`ActionInfo` 携带**毫米声明**，像素几何由独立的 `getActionGeometry()` 计算（§6.5），因为像素几何依赖 DPI/缩放，而 `ActionInfo` 应按文档缓存。
- **`Goto` 复用 `DocumentDestination`**：`model/navigation.ts` 已有 `decodeDestination`（处理 `XYZ/Fit/FitH/FitV/FitR`、`PageID` → 页索引、`Left/Top/Right/Bottom/Zoom`、warning `W_OUTLINE_TARGET`/`W_BOOKMARK_TARGET`），音视频方案**必须复用它**，新增 warning 码 `W_ACTION_TARGET`，不得再写第二套 Dest 解析。

### 4.3 索引结构

```ts
/** 打开的文档中全部动作与音视频索引（打开阶段构建，缓存到 close()）。 */
export interface ActionMediaIndex {
  /** 全部音视频资源，按 ID 升序。 */
  media: readonly MediaResource[];
  /** 文档级动作（Document.xml）。 */
  document: readonly ActionInfo[];
  /** 页级动作：key 为页索引。 */
  pages: ReadonlyMap<number, readonly ActionInfo[]>;
  /** 图元动作：key 为 `${pageIndex}:${objectId}`。 */
  objects: ReadonlyMap<string, readonly ActionInfo[]>;
  /** 大纲节点动作：key 为节点路径（`"0.2.1"`）。 */
  outline: ReadonlyMap<string, readonly ActionInfo[]>;
}
```

### 4.4 格式与 MIME 判定

`Format` 属性在音视频上不可靠（标准未枚举音视频格式，实际文件常见 `Format="MP4"`、`Format="Video"` 或无此属性）。判定顺序：

1. `MediaFile` 扩展名 → MIME 表（`mp3`→`audio/mpeg`，`mp4`/`m4v`→`video/mp4`，`webm`→`video/webm`，`ogg`/`oga`→`audio/ogg`，`ogv`→`video/ogg`，`wav`→`audio/wav`，`avi`→`video/x-msvideo`，`wmv`→`video/x-ms-wmv`，`flv`→`video/x-flv`，`mov`→`video/quicktime`，`aac`→`audio/aac`，`m4a`→`audio/mp4`，`avs`→`video/x-avs`……）；
2. 若 `Format` 是 **MIME 形态**（含 `/`），采用之；
3. 若 `Format` 是上面表中已知扩展名，采用之；
4. 无法判定 → `application/octet-stream`，并上报 `W_MEDIA_FORMAT`（不阻断）。

注意标准正文提到的 `AVS`（国标音视频编码）在浏览器无原生支持，会落到"浏览器不支持"路径（§7.7），这是能力边界而非缺陷。

### 4.5 资源作用域与查找优先级

OFD 的 `ResourceID` 是 `ST_RefID`（数字），在**页资源 → 文档资源 → 公共资源**三个作用域中查找。与图片一致：

1. `PageRes`（页级，仅该页可见）；
2. `DocumentRes`（文档级）；
3. `PublicRes`（公共级）。

**冲突处理**：同一 ID 在不同作用域声明时，按上述就近优先级取用，**不**报 `W_DUPLICATE_RESOURCE`（这是合法的遮蔽）。同一作用域内 ID 重复时保留先出现者并上报 `W_DUPLICATE_RESOURCE`（与现有资源解码一致）。

**跨页可见性**：`MediaResource` 索引是**文档级**的（`getMediaResources()` 不分页），但页级资源的 `scope='page'` 与 `declaredIn` 能让消费方判断该资源只对某页有效。执行资源解析时必须传入**来源页索引**以施加正确的查找优先级；`getMediaResource(id)` 在无页上下文时按"文档 → 公共"查找，找不到再回退到"任意页资源"并上报 `W_MEDIA_SCOPE_AMBIGUOUS`。

## 5. engine 解析与几何

### 5.1 资源解码改造点

`model/resource-decode.ts` 的 `MultiMedias` 遍历当前形如：

```text
for (group of children(root, 'MultiMedias'))
  for (node of children(group, 'MultiMedia'))
    decoded = decodeImage(node, context)   // 非 Image 直接丢弃
```

改造为**一次遍历、按 Type 分派**：

```text
for (group of children(root, 'MultiMedias'))
  for (node of children(group, 'MultiMedia'))
    switch (normalizeType(attr(node,'Type')))
      case 'image':  images.push(decodeImage(node, context))   // 行为不变
      case 'audio':
      case 'video':  media.push(decodeMedia(node, context, kind))
      default:       emit W_MEDIA_FORMAT（Type 非法），跳过
```

要点：

- **`Type` 缺失**：XSD 要求必填，但实际包可能缺失。缺 `Type` 时**按现状行为保持为 Image**，并上报 `W_MEDIA_FORMAT`。这是 `resource-decode.ts:292` 现有分支（`if (typeRaw !== undefined && != 'image') return undefined`）的**精确等价保留**，不是新语义。
- **`decodeImage` 不再需要 `Type` 判断**，改由调用方分派；其内部对 `Type != image` 的早退分支删除（避免两处分派逻辑不一致）。
- **既有测试是硬约束**：`test/model/resources.test.ts` 造了 `MultiMedia ID=3 Type=Audio`，并断言 `set.images` **不包含**它且**无 warning**。改造后该断言必须**依然成立**——Audio 只进 `media`、不进 `images`、不产生 warning。

**必须同步扩大的索引结构（容易漏，逐层列全）**：

| 层 | 文件 | 改造 |
| --- | --- | --- |
| 解码产出 | `model/types.ts` `ResourceDefinitionSet` | 新增 `media: MediaResource[]` |
| 内部索引 | `resource/types.ts` `ResourceIndex` | 新增 `media: ReadonlyMap<ResourceId, MediaResource>` |
| 页级作用域 | `resource/types.ts` `PageResourceScope` | 新增 `getMedia(id)` |
| 索引构建 | `resource/store.ts` `buildDocumentResourceIndex` / `mergeResourceIndexes` / `createPageScope` | 合并与遮蔽规则同其他资源 |
| 存储 | `resource/store.ts` `ResourceStore` | 新增 `getMedia(id)`（与 `getImage` 同形，先 `normalizeResourceId`） |

漏掉 `resource/types.ts` 的 `ResourceIndex`/`PageResourceScope` 会导致 `createPageScope` 不带 `media`，页级作用域查询静默失效——这正是"页级 `PageRes` 里的音视频找不到"的典型 bug。

### 5.1.1 平台约束：engine 的 tsconfig **不含 DOM lib**

`packages/ofdrw-viewer-engine/tsconfig.json` 的 `lib: ["ES2022"]`（无 `DOM`），`strict: true`。因此 `HTMLVideoElement`、`HTMLAudioElement`、`URL`、`document`、`window` **都不是可用类型**。engine 现有做法是**局部最小结构接口 + `globalThis` 探测**（`api/document.ts` 的 `BrowserImageGlobals`，`renderer/canvas2d.ts` 同法）。

对本方案的硬性影响：

- **`MediaResource.mimeType` 用 `string`，不引入任何 DOM 类型**（§4.1 已如此设计）。
- engine **绝不**新增 `Blob`/`URL.createObjectURL` 相关代码；对象 URL 是 UI 的责任（§7.4）。
- 若将来需要"engine 侧产出可播放 URL"，必须走**宿主注入**（与 `createCanvas`/`encodeImage` 同层级），**不得**在 engine 内直接调用浏览器 API。本方案**第一版不提供**该注入点，保持 engine 零 DOM 依赖。

> 这条约束决定了本方案的分工形态：**engine 交付字节，UI 造 ObjectURL**。若曾考虑"engine 直接给 URL"会更省事，但它会让 engine 在 Node（CLI、golden 测试）下崩溃，不可取。

### 5.2 动作解码（新增模块 `model/action-decode.ts`）

```ts
/**
 * 解码 Actions 节点为 ActionInfo 列表。
 *
 * @param node 承载 Actions 的父节点（Document/Page/图元/OutlineElem）。
 * @param owner 宿主位置。
 * @param context 解码上下文（页索引映射、资源路径解析、warning）。
 * @returns 按 XML 顺序排列的动作列表；无 Actions 时返回空数组。
 */
export function decodeActions(
  node: XmlNode,
  owner: ActionOwner,
  context: ActionDecodeContext,
): ActionInfo[];
```

规则：

| 情形 | 处理 |
| --- | --- |
| 无 `Actions` 节点 | 返回 `[]`，**不 warning**（绝大多数文档没有动作） |
| `Action` 缺 `Event` | 跳过该条，`W_ACTION_INVALID` |
| `Event` 非法（非 DO/PO/CLICK） | 跳过，`W_ACTION_INVALID` |
| `Event` 与宿主不匹配（如页面上的 `CLICK`） | **保留**，`W_ACTION_EVENT_MISMATCH`（标准"应为"而非禁止，且部分真实文档如此写） |
| 无动作体（`xs:choice` 全部缺失） | 跳过，`W_ACTION_INVALID` |
| 动作体多于一个（违反 xs:choice） | 取**第一个**出现者，`W_ACTION_MULTIPLE_BODY` |
| `Sound@ResourceID` / `Movie@ResourceID` 缺省或非数字 | 跳过，`W_ACTION_INVALID` |
| `Sound@Volume` 越界/非法 | 钳制到 `[0,100]`，`W_ACTION_FIELD` |
| `Movie@Operator` 非法 | 回退 `Play`，`W_ACTION_FIELD` |
| `Goto` 的 `Dest` 无效（PageID 不存在 / Type 未知） | 该 `Goto` payload 不含 `dest`，`W_ACTION_TARGET` |
| 引用的 `ResourceID` **在资源索引中不存在** | **保留动作**，`W_ACTION_RESOURCE_MISSING`（执行期才失败，索引期仍可见） |
| `Region` 路径非法 | 丢弃区域但保留动作（外接矩形回退 Boundary），`W_ACTION_REGION` |

**关键决策：动作解码必须"宽容"**。动作是增强信息，任何单个动作解析失败都**不得**影响文档打开、页面渲染、文本层与导出。所有动作解析都发生在**按需加载**路径（`getPage` / `getObjectActions` 首次调用时），不在 `open()` 阶段，避免为一个损坏动作让整包打开变慢。

### 5.3 图元动作的挂载与解码时机

图元动作位于 `Content.xml` 的图元节点。页面模型解析（`model/content.ts` 的 `decodePageBlockNode`）会构建 `TextObject`/`PathObject`/`ImageObject`/`CompositeObject`，**当前不读取 `Actions`**。

两种方案：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A | 在 `GraphicUnitBase` 增加 `actions?: ActionInfo[]`，随页面模型一起解析 | 一次遍历、与图元天然绑定、无二次扫描 | 放大 `PageModel` 内存（大多数页没有动作，空数组开销）；`ActionInfo` 里带 `owner.pageIndex` 造成模型与页索引耦合 |
| **B（选）** | 页面模型**不保存**动作；解析页面时**旁路收集**一份"动作清单"（`{ objectId, actions }[]`）挂到 `PreparedPage`/页缓存 | 不污染图元模型；动作按需可见；不增加逐图元字段 | 需要在块遍历时额外收集（一个数组 push 的成本） |

**选定 B**，理由：① 动作是低频数据，不应进入高频遍历的图元对象；② `PageModel` 被视为"绘制只读模型"（设计文档 §2.4），塞入动作会打破其语义；③ 图元 `Boundary`/`CTM` 已在模型里，动作只需 `objectId` 引用回图元即可算几何。

`objectId` 的来源：图元 `ID`（`CT_GraphicUnit` 的 `@ID` 在所有图元元素上是 `use="required"`）。**但**实践中无 ID 的图元存在，此时图元无法被稳定引用——动作清单退化为按**图元在页内的遍历序号**定位（`{ path: number[] }`，与页块嵌套路径一致），并在 `getObjectActions` 同时支持 `objectId` 与 `path` 两种键。

### 5.4 页面级与文档级动作

- **页面级**：`Page.xml` 的 `Page/Actions/Action`。`PageModel` 已有解析入口，增加一次 `decodeActions(pageNode, { kind: 'page', pageIndex })`，结果放进页缓存而非 `PageModel`。
- **文档级**：`Document.xml` 的 `Document/Actions/Action`。在 `open()` 阶段解析（数据量极小），结果进入文档级 `ActionMediaIndex.document`。**这是唯一在 open 阶段解析的动作**，因为 UI 需要在文档打开后立刻判断是否需要执行 DO 动作（自动播放/自动跳转）。
- **大纲级**：`OutlineElem/Actions`。现有 `model/navigation.ts` 的 `findGoto` 已经在**为了跳转**而扫描 `Actions/Action/Goto`，但只取第一个 `Goto` 且丢弃其余。改造为：大纲解码时调用统一的 `decodeActions` 输出 `ActionInfo[]`，`OutlineNode` 增加可选的 `actions?: readonly ActionInfo[]`；`findGoto` 的既有行为（取第一个 Goto 生成 `dest`）**保持不变**以保证 `getOutline()` 的既有快照兼容。

### 5.5 动作区域几何（`getActionGeometry`）

UI 需要知道"点击哪个像素矩形/路径触发动作""视频播放窗口摆在哪里"。由 engine 提供纯函数式计算：

```ts
/** 动作触发区域的页内像素几何。 */
export interface ActionGeometry {
  /** 页索引。 */
  pageIndex: number;
  /** 外接矩形，页面像素（px，原点页面左上角，y 向下）。 */
  bbox: PixelBox;
  /** 显式 Region 的路径（像素）；无 Region 时省略。 */
  areas?: readonly PixelPath[];
  /** 几何来源：显式区域 / 图元 Boundary / 页面区域。 */
  source: 'region' | 'object' | 'page';
}

/**
 * 计算动作在指定 DPI 下的页内像素几何。
 *
 * @param action 动作信息。
 * @param options 计算参数：dpi（每英寸像素数）、页尺寸（mm）、图元几何、页面旋转。
 * @returns 像素几何；文档级无区域动作返回 undefined。
 */
export function getActionGeometry(action: ActionInfo, options: ActionGeometryOptions): ActionGeometry | undefined;
```

计算链（**复用现有能力，不新写矩阵**）：

```text
图元 Boundary（对象空间 mm）
  → 叠加图元 CTM（模型 `ctm?: Matrix`）
  → 叠加页面坐标系（页面旋转 / 翻转，由页面 CTM 决定）
  → 叠加 dpi 换算（`getPageTransform(area, dpi)`，scale = dpi / 25.4）
  → 页面像素矩形
UI 侧再叠加：缩放比例（--scale-factor）、页盒位移、页盒旋转
```

**与文本层保持同一口径**（关键，否则媒体窗口会与文字错位）：

- engine 的 `toTextPagePx(page, dpi)` 用 `scale = dpi / 25.4` 把 mm 全量换算为 px，并对 `page.area.x/y` 做原点平移——`getActionGeometry` **必须逐字对齐这一算式**。
- `getPageTransform(area, dpi)` 返回 `[scale, 0, 0, scale, -scale*area.x, -scale*area.y]`，与 `toTextPagePx` 的原点处理一致，**直接复用即可**，不要第二次手写 `dpi/25.4`。
- 页面旋转不在 engine 侧施加（文本层也遵循"旋转由宿主容器 transform 承担"），`ActionGeometry` 输出的是**未旋转的页面像素**，旋转交给 UI 的 `surface`。
- `Boundary` 与 `CTM` 的旋转图元（如旋转放置的视频封面）会产生**旋转后的矩形**：`PixelBox` 之外额外给出四角点（`corners: readonly [Point, Point, Point, Point]`），UI 用 `matrix()`/`rotate()` 摆放 DOM 时按四角点还原，避免"包围盒放大导致播放器错位"。

### 5.6 Region（复杂区域）的处理深度

`CT_Region` 是 `Area/Move|Line|QuadraticBezier|CubicBezier|Arc|Close` 组成的**矢量路径集合**，含 `Fill` 规则。完整 hit-test 需要点是否在多边形内的判定（含自交与弧线离散）。

**第一版策略**：

1. **解析**全部路径命令为 `ActionRegionPath`（点坐标 mm），保证数据不丢失；
2. **几何**只输出外接矩形 `bbox` 与折线近似路径（贝塞尔离散为 8 段折线，弧线同样离散）；
3. **命中测试**由 UI 在**外接矩形**上粗判 + 需要时用 `isPointInActionRegion(geometry, point)`（engine 提供，使用 even-odd 规则对离散折线求交）。

不引入曲线细分精度的可配置项（固定 8 段），理由是 Region 在真实 OFD 中极少用于音视频；过度设计不值得。若后续出现精度问题，再在 `ActionGeometryOptions` 增加 `curveSegments`。

## 6. engine 公共 API

所有新增 API 都从**包根导出**，且必须同步登记到 `packages/ofdrw-viewer-engine/skills/API.md` 附录（由 `test/smoke/public-api-doc.test.ts` 检查）。

### 6.1 音视频资源查询

```ts
/** 文档内全部音视频资源，按 id 升序。 */
getMediaResources(options?: { signal?: AbortSignal }): Promise<readonly MediaResource[]>;

/** 按资源 ID 查找音视频资源；仅读资源索引，不读内容。 */
getMediaResource(resourceId: ResourceId, options?: MediaResourceQueryOptions): Promise<MediaResource | undefined>;

/**
 * 取音视频资源原始字节。
 *
 * @param resourceId 资源 ID。
 * @param options 取消信号、大小上限覆盖、来源页（用于页级资源解析）。
 * @returns 原始字节；资源不存在或类型不符时返回 undefined。
 * @throws OFDError `OFD_LIMIT_EXCEEDED`（超过 maxMediaBytes）、`OFD_ABORTED`、`OFD_CLOSED`
 */
getMediaData(resourceId: ResourceId, options?: MediaResourceQueryOptions): Promise<Uint8Array | undefined>;
```

**语义逐条对齐附件口径**（降低学习成本与实现分叉）：

- `getMediaResources()`：首次调用解析全部资源文件并缓存到 `close()`，**零内容 IO**；无音视频返回 `[]`；索引读取失败 warning 后返回 `[]`。
- `getMediaResource(id, options?)`：`options.pageIndex` 用于页级资源的作用域解析（§4.5）。
- `getMediaData(id, options?)`：读取前用中央目录记录的解压大小做**预检**（不需要读数据），超 `limits.maxMediaBytes` 直接抛 `OFD_LIMIT_EXCEEDED`，**不返回部分数据**；资源类型是 image 时返回 `undefined`（不抛错，避免 UI 需要 try/catch 判断类型）。
- **不缓存字节**：engine 侧不保留 `Uint8Array`（与 `getAttachmentData` 一致）。播放期缓存是 UI 的 ObjectURL 责任（§7.4）。
- **不提供分块读取**：`saveMedia()` 已删除。播放与 CLI 导出都走 `getMediaData()` 整块读取，大小由 `maxMediaBytes` 兜底（§7.4 分级策略）。理由见 §11.2。

### 6.2 动作查询

```ts
/** 文档级动作（Document.xml 的 Actions），按 XML 顺序。 */
getDocumentActions(): readonly ActionInfo[];

/** 页级动作（Page.xml 的 Actions）。 */
getPageActions(pageIndex: number): Promise<readonly ActionInfo[]>;

/** 图元动作：按图元 ID 或页内路径定位。 */
getObjectActions(pageIndex: number, target: { objectId: string } | { path: readonly number[] }): Promise<readonly ActionInfo[]>;

/** 大纲节点动作：按大纲路径（如 [0, 2, 1]）定位。 */
getOutlineActions(path: readonly number[]): Promise<readonly ActionInfo[]>;

/** 便捷聚合：取某事件在本页可触发的全部动作（含图元动作），供 UI 一次性准备。 */
getPageActionsByEvent(pageIndex: number, event: ActionEvent): Promise<readonly ActionInfo[]>;
```

**设计说明**：

- **`getDocumentActions()` 同步、`getPageActions()` 异步**：文档级在 `open()` 已解析；页级需要加载 `Page.xml`。这种"同步 vs 异步"的不对称是刻意的——它把"是否有 DO 动作"这一打开期关键决策变成零延迟。
- **`getPageActionsByEvent` 是为了 UI 性能**：页面首次渲染后 UI 需要"本页有哪些 CLICK 动作区域"来铺设交互层。逐图元调用 `getObjectActions` 会产生 N 次解析；按事件聚合一次返回，UI 一次建表。
- **返回 `readonly` 数组且不复制**：与 `getOutline()`/`getAttachments()` 一致（缓存的只读视图）。

### 6.3 `ActionInfo` 与 `MediaResource` 是否进 `DocumentMetadata`

**不进**。`DocumentMetadata` 的定位是"文档属性摘要"（标题/作者/页面尺寸等），动作与音视频是**内容能力**，混入会让 `getMetadata()` 的缓存与 CLI `info` 输出膨胀，且违反 CONTRACTS §7.11"元数据来源唯一"的边界。CLI 通过独立 API 读取并在 `info` 中并列输出（§9.2）。

### 6.4 资源限制

`ResourceLimits` 新增：

| 字段 | 默认 | 单位 | 说明 |
| --- | --- | --- | --- |
| `maxMediaBytes` | 256 MiB | byte | 单个音视频资源读取上限；超限不读内容，UI 转下载提示（§7.4） |
| `maxMediaResourceCount` | 512 | 个 | 音视频资源索引条数上限，超出后忽略多余声明并 `W_MEDIA_LIMIT` |
| `maxActionsPerNode` | 256 | 个 | 单节点 `Actions` 条数上限，防止恶意包构造海量动作 |

`maxMediaBytes` 独立取值而非回退 `maxEntryBytes`（64 MiB）：音视频普遍大于普通条目，回退值会让绝大多数包直接不可播，失去分级意义。256 MiB 与 `maxPackageBytes` 默认值对齐。

### 6.5 事件

`OFDEventBus` 新增（**engine 只广播"动作已被发现"的事实，不执行动作**）：

| 事件名 | 载荷 | 时机 |
| --- | --- | --- |
| `media:index:end` | `{ count: number }` | 首次构建音视频索引完成 |
| `action:page:end` | `{ pageIndex: number; count: number }` | 页级+图元动作解析完成 |
| `action:decode:warning` | `{ warning: OFDWarning }` | 动作解析降级（可选，经由既有 warning 通道已可观测，**默认不新增**） |

**不**新增 `media:play` / `media:ended` 这类**执行语义**事件——播放发生在 UI，UI 侧另建 `ViewerEvent`（§7.6）。engine 事件只管"解析态"。

## 7. UI 方案

### 7.1 DOM 层级

在 `PageView`（`packages/ofdrw-viewer-ui/src/page-view.ts`）的 `.ofd-page__surface` 下，现有层级为：

```text
.ofd-page
└─ .ofd-page__surface            （translate/rotate 承载缩放与旋转）
   ├─ .ofd-page__canvas-wrapper  （overflow: hidden，canvas 位图）
   ├─ .ofd-page__text-layer      （文本选择，z-index: 1）
   ├─ .ofd-page__selection-layer （选区高亮，z-index: 2，pointer-events: none，懒创建）
   ├─ .ofd-page__find-layer      （查找高亮，z-index: 3，pointer-events: none，懒创建）
   └─ .ofd-page__signature-layer （签章，z-index: 2，pointer-events: none，子元素 auto）
```

新增**媒体层**，插入位置：**`text-layer` 之后、`signature-layer` 之前**：

```text
.ofd-page__surface
   ├─ .ofd-page__canvas-wrapper   z-index: auto（无定位层级，在流内最先）
   ├─ .ofd-page__text-layer       z-index: 1
   ├─ .ofd-page__media-layer      z-index: 2  ← 新增（pointer-events: none）
   ├─ .ofd-page__selection-layer  z-index: 2
   ├─ .ofd-page__find-layer       z-index: 3
   └─ .ofd-page__signature-layer  z-index: 2（DOM 序在媒体层之后，故绘制在媒体之上）
```

z-index 取值与现有 CSS 对齐：文本层 `1`，选区层/签章层 `2`，查找层 `3`。媒体层取 `2` 且 DOM 序位于签章层之前，因此：**签章仍绘制在媒体之上**（视频不会遮挡签章），**媒体在文本层之上**（视频可点击）。

**为什么媒体层必须在文本层之上**：文本层是覆盖整个页面的密集透明 span 层（`user-select: text`）。若媒体层在其下，视频区域的点击会被文本 span 吃掉，无法命中播放器；媒体层在其上时，媒体元素区域点击直达 `<video>`，其余空白因 `pointer-events: none` 透传给文本层，文本选择不受影响。

### 7.2 定位方式

媒体元素的定位**必须沿用文本层的既有坐标模型**，不能另起一套。UI 现有约定（`text/geometry.ts` 头部注释、`page-view.ts:400-416`）：

- 文本层统一按 **96 DPI CSS px** 构建，再由页面容器的 `--scale-factor` 整体缩放；
- 缩放时**只改 `--scale-factor` 这一个变量**，不重算逐元素尺寸；
- 页面旋转由 `surface` 的 CSS `transform: rotate()` 承担，坐标不重算。

因此媒体层照抄同一模型：

```css
.ofd-page__media-layer {
  position: absolute; inset: 0;
  transform: scale(var(--scale-factor, 1));   /* 与 .ofd-page__text-layer 一致 */
  transform-origin: 0 0;
  pointer-events: none;
  z-index: 2;
}
.ofd-media { position: absolute; pointer-events: auto; }
```

- 子元素 `left/top/width/height` 直接取 **96 DPI 下的页面像素**（`getActionGeometry({ dpi: 96 })`），**不需要**在任何缩放/旋转后重算——这与文本层完全同构，缩放只需浏览器对容器做一次合成变换。
- 页面旋转由 `surface` 承担，媒体层在其内部，随之旋转，**无需额外变换**。这也是媒体层必须放在 `surface` 内、而不是 `ofd-page` 上的原因。
- **不要**在媒体元素上写 `left/top/width/height` 之外的 `scale`：`<video>` 的位图放缩交给浏览器合成即可；也**不要**在缩放回调里重设尺寸——那会与 `--scale-factor` 机制打架并引入逐页重排。

**旋转图元的四角点**：当图元 `CTM` 带旋转，外接 `bbox` 会大于实际外观。此时对媒体元素改用 `transform: matrix(...)`（由 `ActionGeometry.corners` 推导），`transform-origin: 0 0`；线性部分已含 96 DPI 换算，故**不要再叠加** `scale(var(--scale-factor))`，改由父容器承担缩放。

> 设计取舍记录：媒体层**不使用** `requestAnimationFrame` 逐帧跟随，也不监听 `scroll`/`resize` 手动重定位。整个层随 `--scale-factor` 与 `surface` 变换自动跟随，与文本层、签章层、缩略图共享同一条渲染路径，避免"缩放时视频位置滞后"这类典型缺陷。

### 7.3 两种呈现模式

| 模式 | 触发条件 | 实现 |
| --- | --- | --- |
| **嵌入式 inline** | `owner.kind === 'object'` 且动作是 `movie`（标准 §12："图元对象关联的视频播放时，宜使用图元的外观区域大小作为嵌入式播放窗口"） | 在 `.ofd-page__media-layer` 按图元矩形放 `<video>`，`object-fit: contain`，黑底 |
| **弹出式 popup** | `owner.kind ∈ {document, page, outline}`，或音频动作，或用户点击"全屏" | 在 viewer 根节点（非页面）叠加一个模态浮层 `<dialog>`，含播放器 + 关闭按钮 |

**封面帧优先**：标准建议"取视频静态帧做成图像对象 + 边框 + Movie 动作"。因此**渲染阶段不改动**——页面 canvas 上本来就会绘制那张封面图（它是普通 `ImageObject`），点击封面 → CLICK 动作 → 在封面**同一矩形**上覆盖 `<video>` 播放。播放中封面被视频盖住；结束/停止后移除 `<video>`，封面重新可见。这是最小侵入且完全符合标准的做法。

**弹出式的定位**：弹出式窗口不绑定图元矩形，居中显示；但若 `owner` 是图元（例如音频挂在图标上），仍以触发图元为"锚点"做视觉提示（高亮该图元 `bbox` 边框）。

### 7.4 资源到播放器：分级处理

**只做两档，不做流式**。这是刻意的简化：`MediaSource` 需要分片格式、codec 嗅探与状态机，复杂度不低于主功能本身，而绝大多数 OFD 内嵌音视频在几十 MB 以内。

| 档位 | 条件 | 处理 | 内存 |
| --- | --- | --- | --- |
| **正常** | `sizeBytes ≤ maxMediaBytes`（默认 256 MB） | 整块读入 → `Blob` → `ObjectURL` → 播放 | `Uint8Array` 存活期间占用对应大小，**播完即释放** |
| **超限** | `sizeBytes > maxMediaBytes` | **不读取内容**，直接 `OFD_LIMIT_EXCEEDED`；UI 显示"文件过大，请下载原文件" | 0 |

```text
getMediaResource(id) → sizeBytes
        ├─ ≤ maxMediaBytes ──→ getMediaData → new Blob([bytes], {type: mime})
        │                              → URL.createObjectURL(blob) → video.src
        └─ > maxMediaBytes ──→ 抛 OFD_LIMIT_EXCEEDED → UI 提示 + 下载按钮
```

**超限档复用现有下载路径**：UI 已有完全相同的降级先例（附件超过 `ATTACHMENT_LARGE_THRESHOLD_BYTES = 500 MB` 时不读内容、改为下载整个 OFD 原文件，见 `views/attachments.ts` + `viewer.readSourceBytes()`）。音视频超限**照抄该实现**，不新增下载逻辑。

**生命周期**：

| 项 | 策略 |
| --- | --- |
| ObjectURL | 每个资源一份；播放器实例销毁或文档关闭时 `revokeObjectURL` |
| 缓存范围 | **按页缓存 ObjectURL**，页被缓存淘汰即释放（不做按字节 LRU） |
| `revokeObjectURL` 时机 | 元素 `pause()` + `removeAttribute('src')` + `load()` 之后再 revoke，否则 Safari 会中断正在进行的请求 |
| 错误 | 取字节失败（`OFD_LIMIT_EXCEEDED`/`OFD_ABORTED`/资源缺失）→ Toast + 上报 `ViewerEvent`，不阻塞页面 |

**为什么不把字节 base64 塞进 `src`**：base64 放大 33% 且占用双份内存；`Blob` URL 是浏览器原生最优路径。

**为什么整块读取可以接受**：`Blob` 本身会落到磁盘，真正占内存的只有 `Uint8Array` 的存活窗口——创建 Blob 后即可丢弃引用，由 GC 回收。播放期间内存压力来自 Blob 的磁盘 backing 而非堆内存。

### 7.5 动作执行器

动作执行器是**通用能力**，覆盖全部五种动作（`Goto`/`URI`/`GotoA`/`Sound`/`Movie`），`Sound` 与 `Movie` 只是其中两个 handler。

> **完整设计见 [UI 动作处理机制设计](./UI动作处理机制设计.md)**（模块结构、触发、命中、执行语义、生命周期）。本节只保留与音视频直接相关的约定。

本节与音视频相关的要点：

1. **`Synchronous` 阻塞**：`sound.synchronous=true` 时，后续动作等待该音频播放**结束**（`ended` 或用户停止）后才开始；`repeat=true` 时 `Synchronous` 无效（标准显式规定），立即返回。
2. **`Movie` 不阻塞**：`Movie` 无 `Synchronous` 属性，按标准立即返回，后续动作继续。
3. **`Movie@Operator` 的意义**：
   - `Play`：从当前时刻播放（无实例则从 0 开始）；
   - `Stop`：停止并复位到 0，销毁实例；
   - `Pause`：暂停，保留位置；
   - `Resume`：从暂停处继续。
   因此**同一 `ResourceID` 的播放器实例必须被复用**（按资源 ID 建实例表），否则 `Pause`/`Resume` 无法成立。

### 7.6 自动播放策略

`DO`/`PO` 触发的 `Sound`/`Movie` 属于**自动执行**，受 `ViewerOptions.actions.autoExecuteActions` 控制（与其余动作共用同一开关，默认 `false`）。开关、触发时机与跳过上报的完整规则见 [UI 动作处理机制设计](./UI动作处理机制设计.md) §5。

### 7.7 播放器策略与浏览器限制

| 约束 | 对策 |
| --- | --- |
| **Autoplay 策略**：浏览器禁止有声自动播放 | `actions.autoExecuteActions` 默认 **false**；开启时先 `play()` 尝试，`NotAllowedError` 时若 `muteOnAutoplayBlocked` 则 `muted=true` 重试并在 UI 显示"点此取消静音" |
| **无用户手势**：DO/PO 不在手势上下文 | 与上一条同因；此外 UI 在页面**首次用户手势**后记录"已解锁"，后续 PO 动作可直接播放 |
| **编解码不支持**：`<video>` 的 `error` 事件（`MEDIA_ERR_SRC_NOT_SUPPORTED`） | 显示可读错误（"当前浏览器不支持该视频格式 …"）+ i18n，上报 `ViewerEvent`；不做解码兜底 |
| **音量**：`Sound@Volume` 0..100 | `element.volume = volume / 100`，并参与全局音量设置（用户全局音量 × 动作音量，见下） |
| **iOS Safari** | `playsInline = true`（否则全屏接管）；`<audio>` 无 UI，需要自绘控制条 |
| **多实例**：同页多个视频 | 允许并存，但同一时刻**只允许一个有声播放**（新的 `Play` 自动暂停前一个），避免声音叠加；可在选项里放宽 |

**全局音量模型**：`ViewerOptions.media.masterVolume`（0..1，默认 1）与每动作 `Volume`（0..100）相乘 → `element.volume`。工具栏新增音量按钮与静音开关。

## 9. CLI 方案

### 9.1 设计原则

- **不实现播放**：CLI 无 DOM，不做播放器；只做"发现、摘要、导出"。

```jsonc
      { "id": "12", "kind": "video", "mimeType": "video/mp4", "format": "MP4", "sizeBytes": 1048576, "scope": "document" }
    ],
    "actionSummary": { "document": 1, "pages": 2, "objects": 5, "outline": 0 }
  }
}
```

**边界**：`media[]` 只含**元信息**（不含字节）；`sizeBytes` 为 `undefined` 时**省略**（索引阶段不读内容，与 UI 一致）。若 CLI 需要体积，用 `--media-sizes` 显式开关触发 `stat`-式读取（读容器条目长度，不解压）。

### 9.3 音视频导出

复用既有转图命令的输出机制，新增标志：

```bash
# 导出全部音视频资源到输出目录（文件名 = <id>_<原名>.<ext>）
"$CLI" input.ofd --media -o ./out

# 只导出视频
"$CLI" input.ofd --media --media-kind video -o ./out

# 只导指定资源
"$CLI" input.ofd --media --media-id 12 -o ./out
```

- 输出文件命名：`media-<id>.<ext>`（ext 由 MIME 推导，无法推导时 `bin`），冲突时追加序号。
- **安全**：文件名只使用推导出的安全字符集（复用 `safe-text.ts` 的路径安全策略），不信任包内原始文件名，杜绝路径穿越。
- 实现走 `getMediaData()` 整块读取后 `writeFileAtomic` 写入，与 CLI 现有输出模式一致；单个资源受 `maxMediaBytes` 限制，超限报 `CLI_MEDIA_TOO_LARGE`。
- **认证/凭据**：加密包沿用既有的 `--password`/`--key` 凭据参数，不做新通道。

### 9.4 `verify` 是否受影响

**不受影响**。动作与音视频不属于签名/完整性校验范围（签名覆盖的是 XML 与条目摘要），设计上明确"动作解析结果不参与 `verify` 的 overall 判定"。

### 9.5 CLI 错误码新增

| 码 | 用途 |
| --- | --- |
| `CLI_MEDIA_NOT_FOUND` | 指定的 `--media-id` 不存在 |
| `CLI_MEDIA_UNSUPPORTED_TYPE` | 指定 ID 是图片而非音视频 |
| `CLI_MEDIA_TOO_LARGE` | 单个媒体资源超过 `maxMediaBytes` |
| `CLI_MEDIA_WRITE_FAILED` | 写出音视频文件失败 |

退出码沿用既有映射（用法/参数错误 → 1，文档级失败 → 2）。

| 码 | 语义 |

### 10.2 engine warning 码

| 码 | 语义 |
| --- | --- |

| `W_ACTION_LIMIT` | 单节点动作数超过 `maxActionsPerNode`，多余动作被忽略 |

### 11.2 性能

| 风险 | 设计对策 |
| --- | --- |
| 打开变慢 | 音视频索引与页级动作**全部惰性**（首次查询才解析），只有文档级 `Actions` 在 open 阶段解析 |
| 内存暴涨 | engine 不缓存媒体字节；UI **按页缓存 ObjectURL**，页淘汰即释放；单资源受 `maxMediaBytes`（256 MB）限制，超限不读内容（§7.4 分级）；`Blob` 落磁盘，`Uint8Array` 存活窗口短 |

| 索引扫描开销 | `MultiMedias` 一次遍历分派（不二次遍历）；动作清单按页缓存，随页缓存淘汰 |

### 11.3 安全

| 威胁 | 对策 |
| --- | --- |
| 解压炸弹（超大媒体） | `maxMediaBytes`（回退 `maxEntryBytes`）+ 容器既有解压限制；超限抛错不返回部分数据 |
| 恶意 URI 动作 | 协议白名单**仅 `http(s)`**；**执行前弹确认框**展示完整 URL 与主机名，用户确认后才打开；新窗口强制 `noopener,noreferrer`。详见 [UI 动作处理机制设计](./UI动作处理机制设计.md) §8.3 |
| 自动播放骚扰 | `actions.autoExecuteActions` 默认 false；即使开启，同页同时只允许一个有声播放 |
| 动作死循环（Goto 自我跳转） | `maxActionDepth`（默认 4）+ 同页 PO 连续触发计数 |
| 海量动作 | `maxActionsPerNode`（256/节点）+ `maxMediaResourceCount`（512） |
| 路径穿越（媒体 `MediaFile`） | 复用 `resolvePackagePath` 规范化，禁止 `..` 越出包根；CLI 导出文件名不使用包内原名 |
| 未解密包 | engine 返回 `OFD_ENCRYPTED`，与既有行为一致；音视频不绕过 crypto |

### 与设计的差异（实现后回填）

1. **`saveMedia` 分块接口未实现**，仅提供整块 `getMediaData`（§12.4 已声明不做）。
2. **`ActionRegion.areas` 为三层嵌套**（Area → 子路径 → 命令）：设计 §4.2 的两层无法表达 `CT_Region` 的 `Area` 分组语义，实现采用三层。
3. **`ActionMediaIndex`（§4.3）未落地**：实现改用 `PageEntry` 上的分片缓存，动作按需分页加载，扁平索引会强制全量解析，与惰性原则冲突。
4. **ZIP 容器 `maxEntryBytes` 语义调整**：原实现在中央目录解析阶段按 `maxEntryBytes` 拒绝条目，导致 `maxMediaBytes`（256 MiB）永远无效、>64 MiB 媒体使整包打不开。现改为**打开阶段不按单条目大小拒绝，读取时按 `maxBytes` 限制**；`maxTotalUncompressedBytes`（512 MiB）与 `maxCompressionRatio` 仍在打开阶段生效。安全边界已用 `test/api/zip-limits-security.test.ts` 固化。
5. **CLI `actionSummary` 只统计 `document` 与 `outline`**：`pages`/`objects` 需要逐页加载 `Page.xml`，会使 `info` 从轻量查询退化为全文档扫描（实测 89 页与 2 页耗时均为 ~0.27s，证明省略后成本与页数无关）。

### 已知限制

- 内联/弹出播放器、URI 确认框等交互路径的**真实浏览器端到端验证未完成**：本机无头 Chrome 环境下首次渲染耗时极不稳定（同一样本有时 24 秒渲染完成、有时 48 秒仍在 `queued`），且该现象在 demo 自带的两个**不含音视频**的样本上同样出现，与本功能无关。结构性验证（媒体层 DOM 位置、`z-index`、`pointer-events`、`transform: scale(var(--scale-factor))`、尺寸换算）已在真实浏览器中实测通过；交互逻辑由 UI 侧 1088 个单测覆盖。
- 图元所在图层被隐藏时，其 `CLICK` 动作仍参与命中（`ActionInfo` 不含图层信息，反推不可靠）。
- `Region` 曲线按固定 8 段离散，不做可配置精度。
