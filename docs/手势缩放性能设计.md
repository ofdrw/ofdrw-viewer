# 手势缩放性能设计

本文件定义 `@ofdrw/ofdrw-viewer-ui` 中触摸捏合与 Ctrl+滚轮缩放的性能模型：为什么旧实现会卡顿、视觉缩放与内容重绘如何解耦、透明文字层如何始终与画面像素对齐、提交时机与阈值，以及验证方式。

渲染队列与画布预算见 [`OFD渲染引擎设计方案.md`](./OFD渲染引擎设计方案.md)；文字层几何见 [`text-content-api.md`](./text-content-api.md)；UI 状态与事件见 [`packages/ofdrw-viewer-ui/skills/API.md`](../packages/ofdrw-viewer-ui/skills/API.md)。

## 1. 问题

### 1.1 现象

移动端浏览器双指捏合缩放时页面严重卡顿、不跟手：手势与画面明显脱节，缩放过程呈跳跃式，停止后才恢复正常；放大后文字层与画面出现可见偏移，选区与查找高亮落点不准。

### 1.2 根因

旧实现把“视觉缩放”与“内容重绘”绑在同一个调用里，每次手势事件都同步执行完整重绘链路：

```text
pointermove（触摸约 60–120 次/秒）
  └→ applyScale()
       ├─ layout.setScale()        重算全部页布局
       ├─ reflow()                 重排所有页面 DOM
       ├─ cancelAllPageTasks()     取消所有进行中的渲染
       ├─ renderVisible(true)      强制全部可见页重绘 canvas  ← 主因
       └─ commit()                 状态更新 + 派发事件
```

`renderVisible(true)` 的 `force` 参数是关键：它绕过 `pageView.renderedKey === key` 的缓存判断，**每一帧都让可见页以新 DPI 重绘**。一张 A4 页在移动设备上重绘需要几十到上百毫秒，事件回调被阻塞，帧率降到个位数。

还有两条隐藏路径：

1. 缩放时调整滚动位置会触发滚动回调，而 `handleScroll()` 内部同样调用 `renderVisible()`，于是滚动补偿也间接触发重绘；
2. 文字层与查找高亮层的尺寸取自“构建时的页面 DPI”，而 `--scale-factor` 在缩放时改变；版心、页边距被 `textLayer` 的 `overflow: hidden` 裁掉，且 DPI 非 96 时（含 `page-actual` 模式下 `surfaceWidth ≠ 96 DPI 页宽`）文字层自身的 scale 与容器比例不一致，表现为逐页累积错位。

### 1.3 目标

1. 手势期间帧率不受文档复杂度影响，画面严格跟随手指；
2. 手势期间不改变布局尺寸，滚动条不跳动、不出现重排抖动；
3. 手势结束后以最终倍率正式重排并重绘一次，恢复高清；
4. 全过程中透明文字层的位置、选区、查找高亮和签章热区都与可见像素严格对齐；
5. 不改变既有缩放语义（倍率范围、缩放模式、`scalechanging` 事件）。

### 1.4 非目标

- 不改变 canvas 渲染管线与 DPI 计算；
- 不做 pdf.js 式的细节画布（detail canvas）与分块/部分重绘；
- 不引入第三方手势库；
- 工具栏 ± 按钮、双击缩放的触发路径不变（二者直接改布局，不需要预览）。

## 2. 参考实现：pdf.js 的三段式

pdf.js 的缩放由“容器 CSS 倍率 + 页面 CSS 尺寸 + canvas 变换”三处分别承担，值得直接借鉴的有四点：

| pdf.js 做法 | 位置 | 对本项目的含义 |
| --- | --- | --- |
| 容器写 `--scale-factor`，所有图层（canvas/文本/注释）用同一 CSS 倍率缩放 | `pdf_viewer.js` `#setScaleUpdatePages`、`pdf_page_view.js` `#setDimensions` | 文字层与画面必须共用**同一个**缩放来源，不能各自换算 |
| 更新时先 `cssTransform()` 立刻改视觉（canvas 用 transform 拉伸），视情况 `postponeDrawing` | `pdf_page_view.js` `update()` | 视觉缩放与重绘分离；重绘被推迟时不派发 `pagerendered` |
| 推迟重绘期间**隐藏文字层**（`hideTextLayer`），重绘完成后重建 | `pdf_page_view.js` `cssTransform()` | 拉伸中的旧文字层不可用于选择，避免错位选区 |
| 延迟重绘由定时器触发第二次 `refresh()`（`drawingDelay`），不逐帧重绘 | `pdf_viewer.js` `#setScaleUpdatePages` | 手势结束才重绘一次，正是本项目 §2 的两阶段模型 |
| `reset()` 后图层重新挂载，`textLayer.div` 始终按 viewport 尺寸重建 | `pdf_page_view.js` `reset()` / `draw()` | 布局尺寸变化时文字层必须按新尺寸重建，而不是沿用旧尺寸 |

本项目已按 §2 的方式改造：页面尺寸由单一缩放变量推导、视觉缩放与重绘分离、延迟重绘、文字层同源对齐、锚点一次性重设，均与 pdf.js 对齐。

## 3. 核心模型：单一缩放变量 + 延迟重绘（对齐 pdf.js）

> 本节为 v2 实现。早期版本采用“合成层 `transform: scale()` 预览 + 提交时改布局尺寸”的
> 两段式，缩放结束瞬间需要撤销合成层并重建布局，实测会出现画面跳动；现已按 pdf.js 的
> `#setScaleUpdatePages()` / `setLayerDimensions()` 模型重写。

### 3.1 一次缩放步进只做四件事

| 顺序 | 动作 | 作用 |
| --- | --- | --- |
| 1 | 写页盒宽度/高度与 `--scale-factor` | 所有页盒在同一帧按新倍率重排 |
| 2 | 写 `surface` 尺寸与缩放变量 | canvas / 文字层 / 高亮层按同一倍率换算 |
| 3 | 按锚点内容坐标重设滚动位置 | 缩放中心的内容停在原处 |
| 4 | 安排一次延迟重绘（180 ms 停顿） | 手势期间只拉伸旧位图 |

实现见 `OFDViewer#applyScale()`；滚轮（`scheduleZoom`）与捏合（`previewPinch`）都走
这一条路径，不再区分“预览”“提交”两套几何。

### 3.2 页面尺寸由倍率推导

`PageLayout` 同时给出 96 DPI 的**单位尺寸**（`unitWidth` / `unitHeight`）与实际尺寸；
`PageView#setLayout()` / `#setScaleVariable()` 只写“单位尺寸 × 倍率”：

```css
/* 单页元素上的内联值，由 PageView 写入 */
--page-unit-width: 793.7px;
width: calc(var(--page-unit-width) * var(--scale-factor));
--scale-factor: 1.5938;
```

`--scale-factor` 是唯一缩放来源：页盒宽高、`surface` 宽高、文字层与查找高亮层的
`transform: scale(var(--scale-factor))` 都由它推导，因此四者在任何倍率下都严格同步。

canvas 始终 `width/height: 100%`，旧位图由浏览器拉伸到新尺寸，按新倍率绘制完成后原子替换
（`commitPendingCanvas`），因此缩放过程中不会出现白屏或中间尺寸。

### 3.3 文字层同源缩放

文字层按 96 DPI 构建、坐标与显示倍率无关；`applyLayerScale()` 用与页盒相同的倍率放大，
因此缩放时文字层与 canvas 始终重合，无需重建 span。

### 3.4 重绘节流

`handleScroll()` 只更新状态、不重绘；重绘只由 `finishScaleGesture()`（延迟计时器或松手）
触发一次。这与 pdf.js 的 `drawingDelay` + `setTimeout(refresh)` 等价。

### 3.5 取整与亚像素补偿

- 倍率按两位小数取整，未用尽的余量结转到下一格（对齐 pdf.js `_accumulateFactor`），
  连续小幅缩放不会因截断而“滚很多下没变化”。
- 写入滚动位置时记录被浏览器截断的亚像素余量，下次写入补回（对齐 pdf.js `#panPosition`）。

## 4. 锚点保持

缩放与 pdf.js 一致：**每步只有一次几何变更**，因此锚点换算不需要再区分“预览/提交”。

| 场景 | 锚点 | 锚点偏移 |
| --- | --- | --- |
| 桌面端滚轮/按钮/双击 | 本轮手势开始时的可视窗口中心内容（纵、横双向） | 可视高度的一半 / 可视宽度的中点 |
| 移动端两指捏合 | 两指中点（上一帧中点，避免 `(ratio−1)×位移`），纵、横双向 | 两指中点相对可视区顶部的偏移 |
| 两指整体移动 | 不改倍率，直接平移滚动位置（`panBy`） | — |

**设备分工**：触摸手势（捏合缩放、双指平移）只在触屏主设备上接管，判定见
`detectTouchPrimary()`——以 `(pointer: coarse)` 为准，`(pointer: fine)` 为假时按桌面处理。
桌面端（含带触摸屏的笔记本、触控笔）一律不接管指针事件，也不做鼠标拖拽平移：缩放与滚动
只由滚轮与滚动条控制，`touch-action` 保持 `auto`。

**锚点换算**：锚点里的页内位置存的是“页索引 + 页内像素”，横向存的是内容坐标，都是当前布局
下的 CSS 像素。缩放后按新页高/内容宽度比例一次性换算（`offsetForContentPoint()` /
`leftForContentPoint()`），不做比例夹取，避免连续缩放逐帧累积误差。捏合过程中锚点必须在
本帧缩放**之后**重新捕获，否则下一帧会重复计入上一帧的缩放量。

滚动位置 = 锚点内容坐标（新布局） − 锚点偏移；内容不足一屏时固定为 0（页面居中）。

**横向**采用 pdf.js 的居中布局（`.page { margin: 0 auto }`）：页面始终水平居中，放大后两侧
均分负偏移，所以“锚点内容距页面左边缘的距离”在屏幕上保持不变，左侧内容不会被推出可滚动
范围（`translateX(-50%)` 方案会把左半边推到不可滚动的负坐标）。

**页边界容差**：`getPageAtOffset()` 为“整数 scrollTop 不回落上一页”保留 1px 容差；锚点已改为
“页索引 + 页内像素”的精确表达，剩余误差来自浏览器只保留整数 `scrollLeft`/`scrollTop`，连续
多帧捏合实测约 7px（倍率 2976px 宽时比例漂移 0.0023）。

## 5. 重绘时机与阈值

### 5.1 规则

| 条件 | 行为 |
| --- | --- |
| 手势进行中 | 每次步进只改布局尺寸与滚动位置，重置重绘计时器 |
| 手势静止 **180 ms** | 以当前倍率重绘可见页 |
| 双指全部抬起 | 立即重绘，不等计时器 |
| 本次步进未改变倍率 | 不安排重绘 |

`PREVIEW_COMMIT_DELAY_MS = 180` 是手感与清晰度的折中：

- 太小（如 50 ms）：手指微停即触发重绘，重绘抢占主线程造成二次卡顿；
- 太大（如 300 ms）：停止后画面模糊时间过长，观感拖沓；
- 180 ms 约等于三次触摸帧的间隔，能跨过捏合过程中的自然停顿，又不会让人感到延迟。

### 5.2 为什么会“重绘高清”

三件事共同保证重绘后画面清晰：

1. 步进把 `state.view.scale` 改成新倍率，`renderKey()` 随之改变，`renderPage()` 认为缓存失效；
2. `finishScaleGesture()` 调用 `cancelAllPageTasks()` 后 `renderVisible(true)` 重绘可见页；
3. `computeCanvasSize()` 按 `96 * renderScale * dpr` 重算 DPI，受 `maxCanvasPixels` 限制时逐级下调（最多 8 次），超限会发 `W_CANVAS_LIMIT`；若浏览器分配不下画布，再按 `CANVAS_RETRY_PIXEL_STEPS` 逐级收紧预算重试。

若新倍率仍低于 `minRenderScale()`（画布保底 `MAX_CANVAS_BASE_DPR = 2` 倍 DPR），有效渲染倍率不变，`renderPage()` 命中缓存直接跳过——旧位图本来就更清晰。新位图绘制完成后由 `commitPendingCanvas()` 原子替换，旧位图在整个手势期间保持可见。

### 5.3 渲染口径：按设备像素比 1:1，不做超采样

渲染 DPI = `96 × 有效渲染倍率 × DPR`，默认超采样倍率为 1，即画布后备像素与屏幕物理像素一一对应。

曾试过固定 2× 超采样来改善普通屏的锐度，结论是**不可取**：像素数按平方增长，单页画布从 12MB 涨到 47MB（1440px 视口）、滚动与缩放明显卡顿。DPR=1 的屏幕上，1 个物理像素就是清晰度的上限，再多的采样在缩小显示时会被平均掉，收益远小于代价。

因此默认策略是「适配设备像素比」：

| 场景 | 有效渲染倍率 | 后备/CSS | 单页画布（1440px 视口） |
| --- | --- | --- | --- |
| DPR=1、适宽 1.81× | 1.81 | 1.00 | 12MB |
| DPR=2、适宽 1.81× | 1.81 | 2.00 | 47MB |

需要更高抗锯齿过渡的宿主（投影、导出截图）可显式传 `supersample: 1.5` 或 `2`，默认值与上限分别由 `DEFAULT_SUPERSAMPLE` 与 `maxCanvasPixels` 控制。

### 5.4 高倍率下的画布预算

画布像素数随倍率平方增长，A4 在 DPR=1 下：800% 约 57MP、1600% 约 228MP、2500% 约 557MP。`maxCanvasPixels` 默认桌面 256MP、移动 32MP，实测各倍率的后备/CSS 像素比：

| 倍率 | CSS 宽 | 后备宽 | 后备/CSS | 单页像素 |
| --- | --- | --- | --- | --- |
| 100% | 794 | 794 | 1.00 | 0.9MP |
| 400% | 3175 | 3175 | 1.00 | 14MP |
| 800% | 6350 | 6350 | 1.00 | 57MP |
| 1200% | 9524 | 9525 | 1.00 | 128MP |
| 1600% | 12699 | 12700 | 1.00 | 228MP |
| 2000% | 15874 | 11906 | 0.75 | 201MP |
| 2500% | 19843 | 11162 | 0.56 | 176MP |

2500% 要完全 1:1 需要 557MP、单页约 2.2GB 显存，超出浏览器可稳定分配的范围；256MP 已把该倍率从 0.24 提升到 0.56。移动端沿用 32MP 换取稳定性。

已渲染页还受总像素预算 `pageCachePixelBudget`（默认 512MP）约束：`trimCache()` 在缓存页数超限或总像素超预算时，先释放离可见区最远的页，可见页始终保留，避免高倍率下多张画布叠加撑爆内存。

## 6. 透明文字层的位置准确性

### 6.1 坐标模型

文字层按 **96 DPI CSS px** 构建：`buildTextLayerSpecs()` 用 `k = 96 / content.dpi` 把引擎输出（页面 px）归一到 96 DPI，`cssLinearOf()` 再把 `TextItem.transform`（mm 线性部分）除以 `dpi / 25.4` 得到 CSS 矩阵。文字层自身是

```text
视觉尺寸 = span 坐标（96 DPI） × --scale-factor（当前倍率）
```

（实现上由 `applyLayerScale()` 写成“布局框 = 纸面尺寸 / 倍率 + `transform: scale(倍率)`”，与上式等价。）
canvas 是 `width:100%` 铺满 `surface`，`surface` 尺寸为 `页 mm × 96/25.4 × 当前倍率`，设备像素由 `96 × renderScale × dpr` 决定。两者能不能对齐，取决于三处比例是否相等。

### 6.2 缺陷与修正

最初的设计假设是“把文字层改成 `width:100%` 铺满纸面”。该假设经浏览器人工核对**被证伪**：`surface` 尺寸本身已含布局倍率（`surfaceWidth = mm × 96/25.4 × scale`），若文字层再以 100% 铺满并叠加 `transform: scale(--scale-factor)`，倍率会被乘两次。实测 2 倍缩放时文字层宽 3174.8px、canvas 仅 1587.4px，偏差恰好 100%。

正确模型是：**span 坐标是 96 DPI 基准（不含倍率；`buildTextLayerSpecs` 以 `96/content.dpi` 归一，与布局倍率无关），所以图层布局框必须等于“纸面尺寸 / 布局倍率”**，再由显式 `scale(布局倍率)` 放大回来。

| # | 缺陷 | 表现 | 修正 |
| --- | --- | --- | --- |
| T1 | 文字层宽高取构建时 `getPageInfo` 的 96 DPI 尺寸，不随倍率更新 | 提交重排后文字层盒子与纸面不一致 | 布局框改由纸面尺寸换算：`applyLayerScale(layer, surfaceWidth, surfaceHeight, scale)` |
| T2 | 文字层尺寸与 `surface` 的倍率耦合口径不一致 | 非 100% 倍率下文字层错位 | 同上；纸面尺寸取 `PageView.surfaceWidth/surfaceHeight`（已含倍率），再除以倍率 |
| T3 | 提交重排后文字层盒子不更新 | 缩放后文字层与 canvas 尺寸不一致 | `refresh()` 对已建好的页调用 `syncPageTextLayerGeometry()` 重算盒子，span 不重建 |
| T4 | 文字层与查找高亮层各写一份缩放逻辑 | 两层口径漂移 | 统一走 `applyLayerScale()` |
| T5 | 手势进行中旧文字层仍参与命中测试 | 缩放中拖选命中错位文本 | 文字层与页盒共用同一缩放变量，几何恒同步，无需隐藏 |
| T6 | 高亮层尺寸取 `getPageInfo` 且只在创建时算一次 | 布局变化后高亮与文字错位 | `syncFindLayerGeometry()` 在创建与复用时都按纸面尺寸重算 |

> 结论由 `test/unit/text/text-layer.test.ts` 的 `it.each([0.5, 1, 1.25, 2, 4])` 用例锁定：布局框恒为 96 DPI 基准尺寸，`transform` 恒为 `scale(倍率)`，两者相乘即纸面尺寸。

### 6.3 对齐公式

任一图层（canvas / 文字 / 查找高亮 / 签章）的显示宽度必须满足：

```text
显示宽度 = 纸面宽 = 页面 mm 宽 × (96 / 25.4) × 当前倍率
```

- canvas：`100%` 铺满 `surface`，设备像素由 `dpr × renderScale` 决定；
- 文字层 / 查找高亮：布局框 = `纸面尺寸 / 当前倍率`，`transform = scale(当前倍率)`；
- 签章层：`100%` 铺满 `surface`，坐标由 `mmToCssPx` 生成；
- 以上图层都挂在 `surface` 内，当前倍率只有 `--scale-factor` 一个来源。

只有这四条同时成立，选区、高亮、印章热区才能和像素完全对齐。

## 7. 代码结构

| 位置 | 职责 | 状态 |
| --- | --- | --- |
| `viewer.ts` `applyScale(nextScale, zoomMode, anchor?, anchorOffset?)` | 唯一缩放入口：改倍率 → 写页面尺寸 → `reflow()` → 按锚点重设滚动 → 安排延迟重绘 | v2 重写 |
| `viewer.ts` `scheduleZoom(nextScale)` | Ctrl/⌘+滚轮入口：每个手势只在开始时钉一次锚点（`pinnedZoomAnchor`） | v2 |
| `viewer.ts` `previewPinch(nextScale, anchor, anchorOffset)` | 捏合入口：用**上一帧**两指中点作为锚点 | v2 |
| `viewer.ts` `accumulateScale(currentScale, factor)` | 两位小数取整 + 余量结转（§3.5） | v2 |
| `viewer.ts` `anchorScrollTo(point, offset)` / `panBy(dx, dy)` | 按内容坐标重设/平移滚动位置，含亚像素余量补偿 | v2 |

## 8. 已完成改造

1. **统一图层缩放入口**：`applyLayerScale(layer, surfaceWidth, surfaceHeight, scaleFactor)`，布局框取 `纸面尺寸 / 倍率`，`transform` 取显式 `scale(倍率)`；文字层与查找高亮层共用。
2. **图层盒子跟随布局**：`PageView` 暴露 `surfaceWidth/surfaceHeight/layoutScale`；`textLayer.refresh()` 对已建好的页调用 `syncPageTextLayerGeometry()`，查找到高亮层由 `syncFindLayerGeometry()` 在创建与复用时重算。
3. **单帧单次几何变更**：`applyScale()` 在一个同步块里完成“倍率 → 尺寸 → 滚动位置”，不再有“合成层预览 + 提交”两套几何，缩放结束瞬间没有撤销动作，因此不跳动。
4. **居中布局 + 横向锚点**：页盒 `margin: 0 auto`，`mainScrollLeftAnchored()` 按“锚点内容距页左边缘的距离”反解 `scrollLeft`；放大后左侧内容始终可滚动到。
5. **DPI 重建经核实无需实现**：`textContentOptions()` 固定 `dpi: 96`，引擎文本坐标始终 96 DPI 输出，不存在“缩放导致 DPI 变化”的场景；倍率变化只改盒子与缩放，不重建 span。

## 10. 已知边界

- 手势期间显示的是旧位图按新倍率拉伸的结果，停手 180 ms 内略糊；倍率越大越明显，这是用清晰度换流畅度的取舍；
- 手势期间布局高度按新倍率实时变化，滚动条长度会随之改变（与 pdf.js 一致）；
- `getPageAtOffset()` 为“整数 scrollTop 不回落上一页”保留 1px 容差，连续多帧捏合可能累计数像素的页内偏移；后续可改为“页索引 + 页内像素”的精确锚点表达；
- 文字层与高亮层的布局框依赖 `PageView.surfaceWidth/surfaceHeight`；页视图尚未布局时回退到 `getPageInfo` 的 96 DPI 尺寸，若此时倍率非 1，盒子会在首次 `reflow()` 后才校正；
- `features.zoom = false` 时 `touch-action: auto` 交还浏览器页面缩放，此时由 `visualViewport` 变化（停 `BROWSER_ZOOM_SETTLE_MS = 120` ms）重新锚定，期间不做自定义缩放；
- 桌面端不支持鼠标/触摸拖拽平移（`touch-action: auto`，不注册指针接管），只保留滚轮与滚动条；
- 移动端连续多帧捏合的锚点仍有约 7px 累计漂移，源于整数滚动位置量化；
- 不做 pdf.js 的 detail canvas：超过 `maxCanvasPixels` 时仍只降低整体 DPI，而不是局部高刷。代价是 2500% 一类极端倍率下仍有可见锯齿（0.56 个后备像素/CSS 像素），要彻底消除需要按可视区局部高分辨率渲染。
