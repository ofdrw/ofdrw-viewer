# 手势缩放性能设计

本文件定义 `@ofdrw/ofdrw-viewer-ui` 中触摸捏合与 Ctrl+滚轮缩放的性能模型：为什么旧实现会卡顿、视觉缩放与内容重绘如何解耦、锚点如何保持、提交时机与阈值，以及验证方式。

渲染队列与画布预算见 [`OFD渲染引擎设计方案.md`](./OFD渲染引擎设计方案.md)；UI 状态与事件见 [`packages/ofdrw-viewer-ui/skills/API.md`](../packages/ofdrw-viewer-ui/skills/API.md)。

## 1. 问题

### 1.1 现象

移动端浏览器双指捏合缩放时页面严重卡顿、不跟手：手势与画面明显脱节，缩放过程呈跳跃式，停止后才恢复正常。

### 1.2 根因

旧实现把“视觉缩放”与“内容重绘”绑在同一个调用里，每次手势事件都同步执行完整重绘链路：

```text
pointermove（触摸约 60–120 次/秒）
  └→ applyScale()
       ├─ layout.setScale()        重算全部页布局
       ├─ reflow()                 重排所有页面 DOM
       ├─ cancelAllPageTasks()     取消所有进行中的渲染
       ├─ renderVisible(true)      强制全部可见页重绘 canvas  ← 主因
       └─ commit()                 状态更新 + 派发事件
```

`renderVisible(true)` 的 `force` 参数是关键：它绕过 `pageView.renderedKey === key` 的缓存判断，**每一帧都让可见页以新 DPI 重绘**。一张 A4 页在移动设备上重绘需要几十到上百毫秒，事件回调被阻塞，帧率降到个位数。

还有一条隐藏路径被忽略：缩放时调整滚动位置会触发滚动回调，而 `handleScroll()` 内部同样调用 `renderVisible()`，于是滚动补偿也间接触发重绘。

### 1.3 目标

1. 手势期间帧率不受文档复杂度影响，画面严格跟随手指；
2. 手势期间不改变布局尺寸，滚动条不跳动、不出现重排抖动；
3. 手势结束后以最终倍率重绘一次，恢复高清；
4. 缩放锚点准确：指针下的内容在缩放前后保持不动；
5. 不改变既有缩放语义（倍率范围、缩放模式、`scalechanging` 事件）。

### 1.4 非目标

- 不改变 canvas 渲染管线与 DPI 计算；
- 不做渐进式/分块重绘；
- 不引入第三方手势库；
- 不改变双击缩放、工具栏缩放按钮的行为（二者直接改布局，不需要预览）。

## 2. 核心模型：视觉缩放与内容重绘解耦

### 2.1 两阶段

| 阶段 | 改变什么 | 代价 | 帧率 |
| --- | --- | --- | --- |
| **手势中（预览）** | 仅 CSS `scale` 变量与滚动位置 | 合成层缩放，无重排无重绘 | 稳定 60 fps |
| **停止后（提交）** | 布局倍率 + canvas 重绘一次 | 一次完整 `applyScale` | — |

预览期间 `state.view.scale`（布局倍率）**保持不变**，它驱动渲染键与 DPI，一旦变动就会触发重绘。视觉倍率由独立字段 `previewScale` 承载，并通过 CSS 变量作用到页盒。

### 2.2 视觉缩放的实现

页盒 `.ofd-page` 保持布局尺寸不变，叠加一层纯视觉缩放：

```css
.ofd-page--preview {
  scale: var(--preview-scale, 1);
  will-change: scale;
}
```

选择 `scale` 而非改写 `transform` 的原因：`.ofd-page` 已有一层 `transform: translateX(-50%)` 用于水平居中，直接覆盖 `transform` 会丢失居中；`scale` 是独立属性，与 `transform` 相乘而不冲突。

`will-change: scale` 让浏览器提前提升为合成层，避免首次缩放时创建层带来的卡顿。预览结束时移除该类，避免长期占用合成层内存。

文字层的 `--scale-factor` 作用于自身 `transform`，canvas 通过 `width: 100%` 跟随页盒；两者都在页盒缩放范围内，因此预览时文字与画布同步放大，不会错位。

### 2.3 重绘抑制

预览期间必须同时挡住两条触发路径：

| 触发点 | 处理 |
| --- | --- |
| `previewZoom()` 本身 | 只调用 `pageView.setPreviewScale(ratio)`，不调用 `applyScale` |
| `handleScroll()` | `if (this.previewScale === null) this.renderVisible()` |

`handleScroll` 的抑制是必需的：预览时保持锚点会改写滚动位置，滚动回调会在下一帧调度渲染；若不禁用，滚动补偿仍会触发重绘。

## 3. 锚点保持

### 3.1 预览阶段（视觉缩放）

CSS `scale()` 以页盒中心为原点，而页间间距与页盒的垂直偏移**不参与缩放**，因此不能把滚动位置整体线性折算。按几何关系求解：

设指针所在页在滚动内容中的中心坐标为 `c`，指针相对滚动视口顶部的偏移为 `offset`，指针下的内容坐标为 `y = scrollTop + offset`，预览比例为 `r`。

缩放后该内容点的视觉位置变为：

```text
visual = c + (y - c) * r - scrollTop'
```

令其仍等于 `offset`，解得：

```text
scrollTop' = c + (y - c) * r - offset
```

该式对页内任意位置都成立，因为页盒中心 `c` 在整个预览过程中保持不变。

### 3.2 提交阶段（布局换算）

提交时布局倍率真正改变，页盒高度按 `r` 缩放，页顶偏移与页间间距不变。此时**不能**用 `y * r` 折算内容坐标（那样会把页顶偏移也乘进去），而应保持“指针所在的页内比例”不变：

1. 用旧布局求锚点：`anchor = layout.getAnchor(y)` → 页索引与页内比例 `ratio`；
2. 设置新倍率并 `reflow()`；
3. 新滚动位置 `= layout.getOffsetForAnchor(anchor) - offset`。

`getOffsetForAnchor` 内部即 `box.top + ratio * box.height`，页顶偏移使用新布局的真实值，因此换算精确。

### 3.3 验证数据

以 3 页 A4、`scrollTop = 100`、指针偏移 400、捏合 1.0 → 2.0 为例：

| 指标 | 数值 |
| --- | --- |
| 缩放前页内比例 | 0.4240 |
| 缩放后页内比例 | 0.4240 |
| 误差 | 0 |

## 4. 提交时机与阈值

### 4.1 规则

| 条件 | 行为 |
| --- | --- |
| 手指移动中 | 重置计时器，持续预览 |
| 手指静止 **180 ms** | 按当前 `previewScale` 提交 |
| 双指全部抬起 | 立即提交，不等计时器 |
| 预览倍率回到已提交倍率 | 撤销预览，不重绘 |

`PREVIEW_COMMIT_DELAY_MS = 180` 是手感与清晰度的折中：

- 太小（如 50 ms）：手指微停即触发重绘，重绘抢占主线程造成二次卡顿；
- 太大（如 300 ms）：停止后画面模糊时间过长，观感拖沓；
- 180 ms 约等于三次触摸帧的间隔，能跨过捏合过程中的自然停顿，又不会让人感到延迟。

### 4.2 倍率的对外可见性

`getScale()` 返回 `previewScale ?? state.view.scale`，即调用方读到的始终是**用户当前看到的倍率**。`state.view.scale` 只在提交时更新，保证渲染键与状态变更严格对应一次重绘。

`scalechanging` 事件仅在提交时派发一次，不随手势高频触发——否则监听方（如自适应控件）也会被高频回调拖累。

## 5. 适用范围

| 交互 | 是否走预览 | 原因 |
| --- | --- | --- |
| 触摸双指捏合 | 是 | 高频事件，单帧重绘代价高 |
| Ctrl / Cmd + 滚轮 | 是 | 触控板双指缩放同为高频输入 |
| 工具栏 ± 按钮 | 否 | 单次离散操作，重绘一次即可 |
| 双击缩放 | 否 | 单次操作 |
| `setScale()` 公共 API | 否 | 调用方明确要求某个倍率，应立即生效 |

## 6. 代码结构

| 位置 | 职责 |
| --- | --- |
| `viewer.ts` `previewZoom(nextScale, origin?)` | 手势入口：记录 `previewScale`、保持锚点、下发视觉缩放、重置提交计时器 |
| `viewer.ts` `keepPointerAnchor(origin, ratio)` | 预览阶段的几何锚定（§3.1） |
| `viewer.ts` `schedulePreviewCommit()` | 180 ms 防抖计时 |
| `viewer.ts` `commitPreviewScale()` | 移除预览类，按页内比例锚定执行一次 `applyScale` 等价流程（§3.2） |
| `viewer.ts` `handleScroll()` | 预览期间跳过 `renderVisible()` |
| `page-view.ts` `setPreviewScale(scale)` | 写入 `--preview-scale` 与 `ofd-page--preview` 类 |
| `style.css` `.ofd-page--preview` | 合成层缩放样式 |

## 7. 测试

单元测试（`test/unit/core/viewer.test.ts`）：

| 用例 | 断言 |
| --- | --- |
| 连续手势不重绘 | 连续 8 次 Ctrl+滚轮后 `clearRect` 调用次数不变；页面带 `ofd-page--preview`；停止后类被移除且重绘发生 |
| Ctrl+滚轮锚点 | 预览立即反映在 `getScale()`；提交后指针下的页内比例偏差 < 0.002 |
| 双指捏合锚点 | 1.0 → 2.0 后页内比例偏差 < 0.003；松手释放 pointer capture |

注意：断言滚动位置时应读 `elements.main.scrollTop`，而不是 `state.view.scrollTop`——后者经 rAF 合并更新，预览期间落后于实际滚动位置。

真机验证要点：

1. 捏合是否跟手（手势与画面同步）；
2. 静止 180 ms 后由“模糊放大”切换为“清晰”的观感是否可接受；
3. 捏合过程中指针下的内容是否稳定不漂移。

## 8. 已知边界

- 预览期间画面是低清放大，倍率越大越明显；这是用清晰度换流畅度的必然取舍；
- 预览不改变布局高度，因此捏合过程中滚动条长度保持不变，松手提交后才更新；
- 若文档包含大量页，`setPreviewScale` 会对每个页视图写一次 CSS 变量；页数极多时仍为 O(页数) 的样式写入，但无重排，实测不构成瓶颈；
- 不处理 `visualViewport` 层面的输入法/工具栏变化。
