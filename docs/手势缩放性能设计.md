# 手势缩放性能设计

本文件定义 `@ofdrw/ofdrw-viewer-ui` 中触摸捏合与 Ctrl+滚轮缩放的性能模型：为什么旧实现会卡顿、视觉缩放与内容重绘如何解耦、透明文字层如何始终与画面像素对齐、提交时机与阈值，以及验证方式。

渲染队列与画布预算见 [`OFD渲染引擎设计方案.md`](./OFD渲染引擎设计方案.md)；文字层几何见 [`text-content-api.md`](./text-content-api.md)；UI 状态与事件见 [`packages/ofdrw-viewer-ui/skills/API.md`](../packages/ofdrw-viewer-ui/skills/API.md)。

## 1. 问题

### 1.1 现象

移动端浏览器双指捏合缩放时页面严重卡顿、不跟手：手势与画面明显脱节，缩放过程呈跳跃式，停止后才恢复正常；放大后文字层与画面出现可见偏移，选区与查找高亮落点不准。

### 1.2 根因

旧实现把“视觉缩放”与“内容重绘”绑在同一个调用里，每次手势事件都同步执行完整重绘链路：

```text
pointermove（触摸约 60–120 次/秒）
  └→ applyScale()
       ├─ layout.setScale()        重算全部页布局
       ├─ reflow()                 重排所有页面 DOM
       ├─ cancelAllPageTasks()     取消所有进行中的渲染
       ├─ renderVisible(true)      强制全部可见页重绘 canvas  ← 主因
       └─ commit()                 状态更新 + 派发事件
```

`renderVisible(true)` 的 `force` 参数是关键：它绕过 `pageView.renderedKey === key` 的缓存判断，**每一帧都让可见页以新 DPI 重绘**。一张 A4 页在移动设备上重绘需要几十到上百毫秒，事件回调被阻塞，帧率降到个位数。

还有两条隐藏路径：

1. 缩放时调整滚动位置会触发滚动回调，而 `handleScroll()` 内部同样调用 `renderVisible()`，于是滚动补偿也间接触发重绘；
2. 文字层与查找高亮层的尺寸取自“构建时的页面 DPI”，而 `--scale-factor` 在缩放时改变；版心、页边距被 `textLayer` 的 `overflow: hidden` 裁掉，且 DPI 非 96 时（含 `page-actual` 模式下 `surfaceWidth ≠ 96 DPI 页宽`）文字层自身的 scale 与容器比例不一致，表现为逐页累积错位。

### 1.3 目标

1. 手势期间帧率不受文档复杂度影响，画面严格跟随手指；
2. 手势期间不改变布局尺寸，滚动条不跳动、不出现重排抖动；
3. 手势结束后以最终倍率正式重排并重绘一次，恢复高清；
4. 全过程中透明文字层的位置、选区、查找高亮和签章热区都与可见像素严格对齐；
5. 不改变既有缩放语义（倍率范围、缩放模式、`scalechanging` 事件）。

### 1.4 非目标

- 不改变 canvas 渲染管线与 DPI 计算；
- 不做 pdf.js 式的细节画布（detail canvas）与分块/部分重绘；
- 不引入第三方手势库；
- 工具栏 ± 按钮、双击缩放的触发路径不变（二者直接改布局，不需要预览）。

## 2. 参考实现：pdf.js 的三段式

pdf.js 的缩放由“容器 CSS 倍率 + 页面 CSS 尺寸 + canvas 变换”三处分别承担，值得直接借鉴的有四点：

| pdf.js 做法 | 位置 | 对本项目的含义 |
| --- | --- | --- |
| 容器写 `--scale-factor`，所有图层（canvas/文本/注释）用同一 CSS 倍率缩放 | `pdf_viewer.js` `#setScaleUpdatePages`、`pdf_page_view.js` `#setDimensions` | 文字层与画面必须共用**同一个**缩放来源，不能各自换算 |
| 更新时先 `cssTransform()` 立刻改视觉（canvas 用 transform 拉伸），视情况 `postponeDrawing` | `pdf_page_view.js` `update()` | 视觉缩放与重绘分离；重绘被推迟时不派发 `pagerendered` |
| 推迟重绘期间**隐藏文字层**（`hideTextLayer`），重绘完成后重建 | `pdf_page_view.js` `cssTransform()` | 拉伸中的旧文字层不可用于选择，避免错位选区 |
| 延迟重绘由定时器触发第二次 `refresh()`（`drawingDelay`），不逐帧重绘 | `pdf_viewer.js` `#setScaleUpdatePages` | 手势结束才重绘一次，正是本项目 §2 的两阶段模型 |
| `reset()` 后图层重新挂载，`textLayer.div` 始终按 viewport 尺寸重建 | `pdf_page_view.js` `reset()` / `draw()` | 布局尺寸变化时文字层必须按新尺寸重建，而不是沿用旧尺寸 |

本项目已实现 §2 的手势预览与 §4 的提交时机；与 pdf.js 相比，**未做**的是“文字层随缩放同步对齐”和“提交后按最终倍率正式重排”。这两点是本文后续改造的主体。

## 3. 核心模型：视觉缩放与内容重绘解耦

### 3.1 两阶段

| 阶段 | 改变什么 | 代价 | 帧率 |
| --- | --- | --- | --- |
| **手势中（预览）** | 仅 CSS `scale` 变量与滚动位置 | 合成层缩放，无重排无重绘 | 稳定 60 fps |
| **停止后（提交）** | 布局倍率 + canvas 重绘一次 | 一次完整 `applyScale` | — |

预览期间 `state.view.scale`（布局倍率）**保持不变**，它驱动渲染键与 DPI，一旦变动就会触发重绘。视觉倍率由独立字段 `previewScale` 承载，并通过 CSS 变量作用到页盒。

### 3.2 视觉缩放的实现

页盒 `.ofd-page` 保持布局尺寸不变，叠加一层纯视觉缩放：

```css
.ofd-page--preview {
  scale: var(--preview-scale, 1);
  will-change: scale;
}
```

选择 `scale` 而非改写 `transform` 的原因：`.ofd-page` 已有一层 `transform: translateX(-50%)` 用于水平居中，直接覆盖 `transform` 会丢失居中；`scale` 是独立属性，与 `transform` 相乘而不冲突。

`will-change: scale` 让浏览器提前提升为合成层，避免首次缩放时创建层带来的卡顿。预览结束时移除该类，避免长期占用合成层内存。

**文字层对齐依赖两点**：文字层与查找高亮层都挂在 `surface` 内（页盒子节点），因此预览缩放对其同样生效；文字层自身的 `transform: scale(var(--scale-factor))` 使用与页盒布局同一倍率，二者相乘后仍等于“显示倍率 / 文字层构建 DPI”。只要这两条成立，预览期间文字层无需任何改动即随画面同步放大——这正是 pdf.js 用容器统一 `--scale-factor` 达到的效果。

### 3.3 重绘抑制

预览期间必须同时挡住两条触发路径：

| 触发点 | 处理 |
| --- | --- |
| `previewZoom()` 本身 | 只调用 `pageView.setPreviewScale(ratio)`，不调用 `applyScale` |
| `handleScroll()` | `if (this.previewScale === null) this.renderVisible()` |

`handleScroll` 的抑制是必需的：预览时保持锚点会改写滚动位置，滚动回调会在下一帧调度渲染；若不禁用，滚动补偿仍会触发重绘。

## 4. 锚点保持

### 4.1 预览阶段（视觉缩放）

CSS `scale()` 以页盒中心为原点，而页间间距与页盒的垂直偏移**不参与缩放**，因此不能把滚动位置整体线性折算。按几何关系求解：

设指针所在页在滚动内容中的中心坐标为 `c`，指针相对滚动视口顶部的偏移为 `offset`，指针下的内容坐标为 `y = scrollTop + offset`，预览比例为 `r`。

缩放后该内容点的视觉位置变为：

```text
visual = c + (y - c) * r - scrollTop'
```

令其仍等于 `offset`，解得：

```text
scrollTop' = c + (y - c) * r - offset
```

该式对页内任意位置都成立，因为页盒中心 `c` 在整个预览过程中保持不变。

### 4.2 提交阶段（布局换算）

提交时布局倍率真正改变，页盒高度按 `r` 缩放，页顶偏移与页间间距不变。此时**不能**用 `y * r` 折算内容坐标（那样会把页顶偏移也乘进去），而应保持“指针所在的页内比例”不变：

1. 用旧布局求锚点：`anchor = layout.getAnchor(y)` → 页索引与页内比例 `ratio`；
2. 设置新倍率并 `reflow()`；
3. 新滚动位置 `= layout.getOffsetForAnchor(anchor) - offset`。

`getOffsetForAnchor` 内部即 `box.top + ratio * box.height`，页顶偏移使用新布局的真实值，因此换算精确。

### 4.3 验证数据

以 3 页 A4、`scrollTop = 100`、指针偏移 400、捏合 1.0 → 2.0 为例：

| 指标 | 数值 |
| --- | --- |
| 缩放前页内比例 | 0.4240 |
| 缩放后页内比例 | 0.4240 |
| 误差 | 0 |

## 5. 提交时机与阈值

### 5.1 规则

| 条件 | 行为 |
| --- | --- |
| 手指移动中 | 重置计时器，持续预览 |
| 手指静止 **180 ms** | 按当前 `previewScale` 提交 |
| 双指全部抬起 | 立即提交，不等计时器 |
| 预览倍率回到已提交倍率 | 撤销预览，不重绘 |
| 提交完成后再次手势 | 以新的 `state.view.scale` 为基准开启下一轮预览 |

`PREVIEW_COMMIT_DELAY_MS = 180` 是手感与清晰度的折中：

- 太小（如 50 ms）：手指微停即触发重绘，重绘抢占主线程造成二次卡顿；
- 太大（如 300 ms）：停止后画面模糊时间过长，观感拖沓；
- 180 ms 约等于三次触摸帧的间隔，能跨过捏合过程中的自然停顿，又不会让人感到延迟。

### 5.2 为什么会“重绘高清”

三件事共同保证提交后画面清晰：

1. 提交把 `state.view.scale` 改成最终倍率，`renderKey()` 随之改变，`renderPage()` 认为缓存失效；
2. `renderAfterScaleChange()` 发现有效渲染倍率变化（`effectiveRenderScale()` = `max(scale, minRenderScale())`），先 `cancelAllPageTasks()` 再 `renderVisible(true)` 强制重绘；
3. `computeCanvasSize()` 按 `96 * renderScale * dpr` 重算 DPI，受 `maxCanvasPixels` 限制时逐级下调（最多 8 次），超限会发 `W_CANVAS_LIMIT`。

若缩放后的倍率仍低于 `minRenderScale()`（画布保底 `MAX_CANVAS_BASE_DPR = 2` 倍 DPR），有效渲染倍率不变，此时**只改 CSS 尺寸不重绘**——因为旧画布本来就更清晰。

### 5.3 渲染口径：按设备像素比 1:1，不做超采样

渲染 DPI = `96 × 有效渲染倍率 × DPR`，默认超采样倍率为 1，即画布后备像素与屏幕物理像素一一对应。

曾试过固定 2× 超采样来改善普通屏的锐度，结论是**不可取**：像素数按平方增长，单页画布从 12MB 涨到 47MB（1440px 视口）、滚动与缩放明显卡顿。DPR=1 的屏幕上，1 个物理像素就是清晰度的上限，再多的采样在缩小显示时会被平均掉，收益远小于代价。

因此默认策略是「适配设备像素比」：

| 场景 | 有效渲染倍率 | 后备/CSS | 单页画布（1440px 视口） |
| --- | --- | --- | --- |
| DPR=1、适宽 1.81× | 1.81 | 1.00 | 12MB |
| DPR=2、适宽 1.81× | 1.81 | 2.00 | 47MB |

需要更高抗锯齿过渡的宿主（投影、导出截图）可显式传 `supersample: 1.5` 或 `2`，默认值与上限分别由 `DEFAULT_SUPERSAMPLE` 与 `maxCanvasPixels` 控制。

## 6. 透明文字层的位置准确性

### 6.1 坐标模型

文字层按 **96 DPI CSS px** 构建：`buildTextLayerSpecs()` 用 `k = 96 / content.dpi` 把引擎输出（页面 px）归一到 96 DPI，`cssLinearOf()` 再把 `TextItem.transform`（mm 线性部分）除以 `dpi / 25.4` 得到 CSS 矩阵。文字层自身是

```text
视觉尺寸 = span 坐标（96 DPI） × --scale-factor（布局倍率） × 页盒预览 scale（手势倍率）
```

而 canvas 是 `width:100%` 铺满 `surface`，`surface` 尺寸为 `页 mm × 96/25.4 × 布局倍率`，设备像素由 `96 × renderScale × dpr` 决定。两者能不能对齐，取决于三处比例是否相等。

### 6.2 缺陷与修正

最初的设计假设是“把文字层改成 `width:100%` 铺满纸面”。该假设经真实浏览器实测**被证伪**：`surface` 尺寸本身已含布局倍率（`surfaceWidth = mm × 96/25.4 × scale`），若文字层再以 100% 铺满并叠加 `transform: scale(--scale-factor)`，倍率会被乘两次。实测 2 倍缩放时文字层宽 3174.8px、canvas 仅 1587.4px，偏差恰好 100%。

正确模型是：**span 坐标是 96 DPI 基准（不含倍率，实测 span `left=56.69px` 与倍率无关），所以图层布局框必须等于“纸面尺寸 / 布局倍率”**，再由显式 `scale(布局倍率)` 放大回来。

| # | 缺陷 | 表现 | 修正 |
| --- | --- | --- | --- |
| T1 | 文字层宽高取构建时 `getPageInfo` 的 96 DPI 尺寸，不随倍率更新 | 提交重排后文字层盒子与纸面不一致 | 布局框改由纸面尺寸换算：`applyLayerScale(layer, surfaceWidth, surfaceHeight, scale)` |
| T2 | 文字层尺寸与 `surface` 的倍率耦合口径不一致 | 非 100% 倍率下文字层错位 | 同上；纸面尺寸取 `PageView.surfaceWidth/surfaceHeight`（已含倍率），再除以倍率 |
| T3 | 提交重排后文字层盒子不更新 | 缩放后文字层与 canvas 尺寸不一致 | `refresh()` 对已建好的页调用 `syncPageTextLayerGeometry()` 重算盒子，span 不重建 |
| T4 | 文字层与查找高亮层各写一份缩放逻辑 | 两层口径漂移 | 统一走 `applyLayerScale()` |
| T5 | 手势预览中旧文字层仍参与命中测试 | 缩放中拖选命中错位文本 | 预览期加 `data-preview` 隐藏，提交后移除 |
| T6 | 高亮层尺寸取 `getPageInfo` 且只在创建时算一次 | 布局变化后高亮与文字错位 | `syncFindLayerGeometry()` 在创建与复用时都按纸面尺寸重算 |

> 实测数据（Chrome，站点 `samples/ofd-viewer-ui-showcase.ofd`，修正后）：0.5×/1×/2×/4× 四档倍率下文字层与 canvas 外框尺寸偏差均为 **0**；首个 `ofd-text-item` 相对纸面的位置在 1×/2×/4× 下完全一致（`relLeft=0.07142`、`relTop=0.02693`）。

### 6.3 对齐公式

任一图层（canvas / 文字 / 查找高亮 / 签章）的显示宽度必须满足：

```text
显示宽度 = 纸面宽 = 页面 mm 宽 × (96 / 25.4) × 布局倍率 × 预览倍率
```

- canvas：`100%` 铺满 `surface`，设备像素由 `dpr × renderScale` 决定；
- 文字层 / 查找高亮：布局框 = `纸面尺寸 / 布局倍率`，`transform = scale(布局倍率)`；
- 签章层：`100%` 铺满 `surface`，坐标由 `mmToCssPx` 生成；
- 页盒预览 `scale` 对以上所有图层统一生效（都挂在 `surface` 内）。

只有这四条同时成立，选区、高亮、印章热区才能和像素完全对齐。

## 8. 已完成改造

1. **统一图层缩放入口**：`applyLayerScale(layer, surfaceWidth, surfaceHeight, scaleFactor)`，布局框取 `纸面尺寸 / 倍率`，`transform` 取显式 `scale(倍率)`；文字层与查找高亮层共用。
2. **图层盒子跟随布局**：`PageView` 暴露 `surfaceWidth/surfaceHeight/layoutScale`；`textLayer.refresh()` 对已建好的页调用 `syncPageTextLayerGeometry()`，查找到高亮层由 `syncFindLayerGeometry()` 在创建与复用时重算。
3. **固定提交时序**：`reflow()` 写完纸面尺寸后**同步**刷新文本层，使文字层与 canvas 处于同一次样式计算；`commitPreviewScale()` 与 `setRotation()` 都经由 `reflow()`，时序统一。
4. **预览期隐藏文字层**：`setPreviewScale()` 写/移除 `data-preview`，CSS `visibility: hidden`，提交后恢复。
5. **DPI 重建经核实无需实现**：`textContentOptions()` 固定 `dpi: 96`，引擎文本坐标始终 96 DPI 输出，不存在“缩放导致 DPI 变化”的场景；布局倍率变化只改盒子与缩放，不重建 span。

4. 放大到 400% 后选中页面右下角文字，选区是否贴合；查找高亮是否与文字重合。

## 10. 已知边界

- 预览期间画面是低清放大，倍率越大越明显；这是用清晰度换流畅度的必然取舍；
- 预览不改变布局高度，因此捏合过程中滚动条长度保持不变，松手提交后才更新；
- 若文档包含大量页，`setPreviewScale` 会对每个页视图写一次 CSS 变量；页数极多时仍为 O(页数) 的样式写入，但无重排，实测不构成瓶颈；
- 预览期隐藏文字层意味着手势进行中不可复制文本，这是与 pdf.js 一致的取舍；
- 文字层与高亮层的布局框依赖 `PageView.surfaceWidth/surfaceHeight`；页视图尚未布局时回退到 `getPageInfo` 的 96 DPI 尺寸，若此时布局倍率非 1，盒子会在首次 `reflow()` 后才校正；
- 不处理 `visualViewport` 层面的输入法/工具栏变化；
- 不做 pdf.js 的 detail canvas：超过 `maxCanvasPixels` 时仍只降低整体 DPI，而不是局部高刷。
