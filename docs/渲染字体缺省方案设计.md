# 渲染字体缺省方案设计（D-FONT-DEFAULT）

- 状态：设计定稿（按评审意见修订：**engine 不做自动发现；CLI 自动发现系统字体**）。
- 范围：engine 缺省字体配置项、解析优先级、CLI 系统字体发现、warning 与兼容性。
- 结论：engine 只消费用户配置的默认字体，自身不做任何字体发现；CLI 作为应用层默认扫描系统字体并注入 `supplementaryFonts`，可用 `--no-system-fonts` 关闭。不内置、不下载字体。

## 1. 背景

现状（r11）字体来源三层：

| 层级 | 来源 | 行为 |
|---|---|---|
| 1 | 内嵌 `FontResource.FontFile` | 最高优先级，可信任显式 GID |
| 2 | 宿主 `FontProvider.match()` | 按 FontName/FamilyName/Charset 等匹配 |
| 3 | `supplementaryFonts` | 用户注入的补充字体池，参与缺字/缺字体回退 |

三层都没命中时，[provider.ts](../packages/ofdrw-viewer-engine/src/font/provider.ts:320) 返回 `null` 并报 `W_FONT_MISSING`；绘制侧 [object.ts](../packages/ofdrw-viewer-engine/src/render/object.ts:568) 跳过整个文字对象，页面出现空白文字。

这是刻意设计（用于区分"引擎缺陷"和"宿主没喂字体"），但实际使用中，用户往往只想要一句"没有字体就用这个"，而不是去理解 `FontProvider`/`supplementaryFonts` 的分工。样本统计中约 35% 的文字对象没有内嵌字体；`999.ofd` 在不传 `--font-dir` 时产生 698 条 `W_FONT_MISSING`、正文空白。

CLI 目前明确"默认不扫描系统字体"（[CLI设计方案 §7.4](./CLI设计方案.md)），终端用户必须自己找到并传入字体目录，这是本次要解决的主要痛点。

## 2. 目标与非目标

### 2.1 目标

1. engine 提供**一个参数**（`defaultFonts`）解决"文档字体缺省时显示什么字"；不传时行为与 r11 完全一致。
2. CLI 默认自动使用操作系统字体，用户 `--font-dir` 作为**扩充**而非替代。
3. 用户提供的默认字体优先于 `supplementaryFonts`。
4. 替代字体必须走 cmap，不能误用文档的显式 GID。
5. 不新增运行时依赖，不改变"文字只走字形轮廓、不调用 `fillText`"的约束。

### 2.2 非目标（明确不做）

- **engine 公共 API 不做自动字体发现**：不扫描系统字体目录、不调用 `queryLocalFonts`、不提供 `EnvironmentFontSource` 适配器。自动发现只作为 CLI 应用层行为存在。
- 不内置、不打包、不下载字体。
- 不做字体子集化、格式转换。
- 不改变缺字形时的逐字形回退语义。
- 不改变 `W_GLYPH_MISSING` 触发条件。

### 2.3 为什么 engine 不做自动发现

| 原因 | 说明 |
|---|---|
| 平台差异大 | Node 可读文件系统，浏览器不能枚举系统字体，小程序无本地字体；一套自动发现无法跨端一致 |
| 结果不可预期 | 同一文档在不同机器会选到不同字体，版式与黄金图基线不可复现 |
| 成本高 | 目录扫描 + 字体解析有性能与内存成本，还会引入字体授权、隐私（`queryLocalFonts` 权限）问题 |
| 用户可控性差 | 用户无法预知"为什么用了这个字体"，出问题时难以复现 |

结论：engine 的字体来源由用户显式配置，engine 只负责按住固定优先级消费。

CLI 是例外，但属于**应用层策略**而非 engine 能力：CLI 运行环境固定（Node + 本机文件系统），输出可被 `--no-system-fonts` 关闭，来源可通过日志说明，因此由 CLI 自己做系统字体发现是合理的（见 §7）。

## 3. 术语

| 术语 | 含义 |
|---|---|
| **文档字体** | OFD `Res.xml` 声明的 `FontResource`，可能带或不带 `FontFile` |
| **精确来源** | 能证明"就是文档要的字体"：内嵌 `FontFile`、`FontProvider` 按名称命中的字体 |
| **默认字体** | 用户通过 `defaultFonts` 显式配置的缺省替代字体 |
| **补充字体** | 用户通过 `supplementaryFonts` 配置的逐字形补充池 |

## 4. 方案

### 4.1 固定优先级

```
主字体选择（一次解析，结果缓存）
  1. 内嵌 FontFile                        [精确, authoritative]
  2. FontProvider.match() 最优候选         [精确]
  3. defaultFonts 最优候选                 [替代, 用户配置]
  4. supplementaryFonts 最优候选           [替代, 用户配置]
  5. 全部失败 → null + W_FONT_MISSING      [保持现状]

逐字形回退链（primary 之后）
  provider 其余候选 → defaultFonts 其余 → supplementaryFonts
```

规则：

1. **精确来源优先**：内嵌字体或 provider 命中时，绝不使用默认字体。
2. **默认字体优先于补充字体**：`defaultFonts` 是"缺省替代"的专用策略，`supplementaryFonts` 是"补缺字"的通用池。
3. **替代字体不可信任显式 GID**：`defaultFonts` 创建的字体面固定 `substitute: true`，`CGTransform` 的 GID 被忽略，必须走 cmap（复用 [trustsExplicitGlyphs](../packages/ofdrw-viewer-engine/src/font/provider.ts:119) 的判定）。
4. **替代只补位，不覆盖**：主字体存在但缺某个字形时，才逐字形落到回退链。
5. **多字体按评分选择**：`defaultFonts` 与 `supplementaryFonts` 都不简单取第一个，统一用 [scoreFace](../packages/ofdrw-viewer-engine/src/font/provider.ts:87)（精确 family 200 分、别名 100 分、bold/italic 加 10/5 分）。

### 4.2 `defaultFonts` 与 `supplementaryFonts` 的分工

| | `defaultFonts` | `supplementaryFonts` |
|---|---|---|
| 目的 | 文档字体完全缺省时的替代字体 | 主字体存在但缺字时补齐 |
| 优先级 | 高于 supplementary | 低于 default |
| 典型用法 | 传一个通用中文字体，保证"至少能看" | 传业务专用字体包，补齐生僻字 |
| 不传时 | 行为与 r11 一致 | 行为与 r11 一致 |

两者都传时：主字体优先取 `defaultFonts`；逐字形仍依次尝试两者。只想要简单兜底的用户只传 `defaultFonts` 即可。

## 5. API 增量

### 5.1 打开选项

在 [OFDOpenBaseOptions](../packages/ofdrw-viewer-engine/src/api/types.ts:175) 增加一个可选字段（兼容增量）：

```ts
export interface OFDOpenBaseOptions {
  // ...既有字段不变

  /**
   * 用户默认字体；文档字体缺省时使用，优先级高于 supplementaryFonts。
   *
   * 仅作替代来源，不可信任显式 GID；多个来源按 FontName/FamilyName/别名评分选主字体。
   * 支持 data/url/path/filePath 四种 FontInput。
   */
  readonly defaultFonts?: readonly FontInput[];
}
```

约束：

- 默认值无（`undefined`），不传时完全不加载、不产生任何额外开销。
- 每个来源仍经既有 `loadInput` 读取非 `data` 字节，受 `limits.maxFontBytes`（默认 64 MiB/字体）约束。
- TTC/OTC 自动展开全部字体面，参与评分。
- 结果按文档实例缓存，`FontLibrary.clear()`/`dispose()` 一并清理。

### 5.2 使用示例

```ts
// Node / Electron 主进程：传本地字体文件
await OFDDocument.open({
  source,
  defaultFonts: [{ path: '/opt/fonts/SourceHanSerifSC.otf', family: 'Source Han Serif SC' }],
  loadInput: createNodeFontInputLoader(),
});

// Web：传同源字体 URL
await OFDDocument.open({
  source,
  defaultFonts: [{ url: '/assets/fonts/noto-serif-sc.otf', family: 'Noto Serif CJK SC' }],
});

// 已知字体字节（小程序、内存字体包）
await OFDDocument.open({
  source,
  defaultFonts: [{ data: fontBytes, family: 'Noto Serif CJK SC' }],
});
```

## 6. 解析流程

### 6.1 主字体选择

改造 [FontLibrary.resolveUncached](../packages/ofdrw-viewer-engine/src/font/provider.ts:297)，在 provider 与 supplementary 之间插入 default：

```
async resolveUncached(font, key):
  embedded ← this.embedded.get(key)
  providerFaces ← embedded ? [] : await loadProviderFaces(font)   // 既有
  defaultFaces ← await loadDefaultFaces()                          // 新增
  supplementaryFaces ← await loadSupplementaryFaces()              // 既有

  primary ← embedded
         ?? pickBest(providerFaces)
         ?? pickBest(defaultFaces)
         ?? pickBest(supplementaryFaces)

  if !primary:
    warn(W_FONT_MISSING, ...); return null

  fallbacks ← dedupeByKey(
    provider 其余 → default 其余 → supplementary
  )
  return { primary, fallbacks }
```

`loadDefaultFaces()` 与 `loadSupplementaryFaces()` 同构：

- 按 `defaultFonts` 顺序遍历，`readInput` 读字节，`createFontFaces` 展开 TTC/OTC；
- 创建选项固定 `substitute: true`、`authoritative: false`，`family` 取 `input.family ?? default-<index>`；
- 结果按顺序缓存，单个来源失败只 warning，继续下一个。

### 6.2 显式 GID 与 advance

- `defaultFonts` 的字体面 `explicitGlyphs=false`，`resolveGlyph` 走 cmap 分支；
- `DeltaX/DeltaY` 存在时以文档 Delta 为准；缺失时回退到实际命中字体的 advance（现有 `fallbackAdvance` 已按 face 计算，无需改动）；
- 替代字体与文档字体度量不同会导致字宽变化，属于可接受降级，不做补偿。

### 6.3 缓存与生命周期

| 项 | 行为 |
|---|---|
| 字体面缓存 | 与 supplementary 一致，按来源顺序惰性加载一次 |
| 解析结果缓存 | 沿用 `FontLibrary.resolved`（按字体资源键） |
| `registerEmbedded` | 已注册内嵌字体时清掉旧的 null/回退缓存（现有逻辑） |
| `clear()` / `dispose()` | 同时清理 `defaultFaces` 与补充字体缓存 |

## 7. 各端配置方式

| 端 | 默认行为 | 用户补充 |
|---|---|---|
| CLI | 自动发现系统字体 | `--font-dir` 追加，优先级更高 |
| Node / Electron 主进程 | 无（需显式配置） | `defaultFonts: [{ path }]` + `loadInput` |
| Web | 无 | `defaultFonts: [{ url }]` 或 `{ data }` |
| 微信小程序 | 无 | `defaultFonts: [{ data }]` |

### 7.1 CLI 字体策略

**系统字体是默认基底，`--font-dir` 是用户扩充；两者合并后注入 `supplementaryFonts`，engine 无需任何改动。**

```
CLI 字体来源（按优先级）
  1. --font-dir 扫描结果        [用户显式，排前]
  2. 系统字体发现结果            [默认基底]
  → realpath 去重 → 取前 N 个 → supplementaryFonts
```

| 场景 | 行为 |
|---|---|
| 不传 `--font-dir` | 只用系统字体 |
| 传 `--font-dir` | 用户目录在前，系统字体继续作为扩充，不丢弃 |
| `--no-system-fonts` | 关闭系统字体，仅用 `--font-dir`（回到 r11 行为） |
| 系统目录不存在/不可读 | 输出一条 info 日志，不报错 |

### 7.2 系统字体发现（CLI 内部实现）

目录白名单（只读，不跟随白名单外路径）：

| 平台 | 目录 |
|---|---|
| Linux | `/usr/share/fonts`、`/usr/local/share/fonts`、`~/.fonts`、`~/.local/share/fonts` |
| macOS | `/System/Library/Fonts`、`/Library/Fonts`、`~/Library/Fonts` |
| Windows | `%WINDIR%\Fonts`、`%LOCALAPPDATA%\Microsoft\Windows\Fonts` |
| 其他 | 空（不发现） |

实现要点：

- 只用 `node:fs`，不调用 `fc-list`/注册表，不新增依赖；
- 扩展名过滤 `.ttf/.otf/.ttc/.otc`，`realpath` 去重，扫描文件数上限 `maxFonts=2000`；
- **注入数量受限**：系统字体按优先级排序后最多注入 `maxSystemFonts=6` 个，并限制总字节预算 `maxTotalBytes=96 MiB`（TTC/OTC 按整个文件字节计），扫描累计超出即停止。原因是 engine 的 `loadSupplementaryFaces` 会读取并解析每个补充字体，把上千个 CJK 字体全量注入不可接受。2026-10 实测（Linux，Noto CJK 等）：旧的 16 个上限注入 126.4 MiB 字体，999.ofd RSS 中位数 512 MB / 1.55 s，关闭系统字体 140 MB / 0.66 s；调整为 6 个 + 96 MiB 后 RSS 中位数 426 MB / 1.21 s，RSS 差距由 +372 MB 降至 +286 MB，剩余差距主要来自 4 个 Noto CJK TTC（约 89 MB）被 engine 展开全部字体面；
- 优先级：文件名命中 CJK 关键字（`cjk`/`noto`/`sourcehan`/`simsun`/`simhei`/`msyh`/`pingfang`/`fangsong`/`kaiti` 等）的排前，其次常见西文衬线/无衬线；同优先级按路径字典序，保证结果稳定可复现；
- **符号链接安全**：目录项为符号链接且指向目录时跳过；文件符号链接取 `realpath` 后必须仍位于某个白名单根的 `realpath` 之下，否则跳过，防止逃逸白名单；
- 扫描结果本次进程内缓存，一次 `convert` 只扫描一次；
- 日志：`logger.detail`（stderr）输出"自动发现系统字体 N 个（扫描 M 个文件）"，不污染 stdout。

### 7.3 为什么不需要 engine 新接口

CLI 自动发现的结果就是一组 `FontInput`（`{ path }`），直接并入现有 `supplementaryFonts`（[convert.ts](../packages/ofdrw-viewer-cli/src/convert.ts:129)）。engine 侧的字形选择、别名匹配、逐字形回退、TTC 展开全部复用，无需新增 `EnvironmentFontSource` 或平台接口。

## 8. warning

现有 [`W_FONT_MISSING`/`W_GLYPH_MISSING`](../packages/ofdrw-viewer-engine/src/warnings.ts:10) 语义保持不变：

- 配置了 `defaultFonts` 并成功替代：**不报** `W_FONT_MISSING`（字已显示）；
- 未配置或全部来源失败：仍报 `W_FONT_MISSING` 并跳过文字对象。

可选增强（需评审）：新增 info 级 `W_FONT_SUBSTITUTED`，在替代成功时提示"原字体名 → 实际使用的默认字体"，便于诊断。默认不加，避免公共 warning 码表变更。

## 9. 兼容性

### 9.1 engine

| 场景 | 行为 |
|---|---|
| 不传 `defaultFonts` | 与 r11 完全一致（Web/Node 不变） |
| 内嵌字体或 provider 命中 | 不作为主字体，但仍加载并进入逐字形回退链（内嵌字体缺字时可用默认字体补字） |
| 只传 `supplementaryFonts` | 与 r11 完全一致 |
| 同时传 `defaultFonts` + `supplementaryFonts` | 主字体优先 defaultFonts，逐字形依次回退 |

- 公共 API：仅新增一个可选字段，无破坏性变更。
- engine 测试与黄金图基线不受影响（engine 默认值不变）。

### 9.2 CLI

- 不传 `--font-dir` 时默认行为变化：从"空白 + 数百条 `W_FONT_MISSING`"变为"使用系统字体、文字可读"，这是本次需求的预期变化；
- 传 `--font-dir` 时，输出可能比 r11 更完整（系统字体作为扩充参与回退）；
- `--no-system-fonts` 可完全复现 r11 行为；
- 受影响基线：`BUG-999验证报告.md`、黄金图无字体组、CLI e2e 中"无字体 → 空白"的断言需重定口径。

## 10. 安全

- 字体来源由用户显式提供，engine 不访问文件系统、不联网；
- CLI 只读 §7.2 白名单目录，不写、不下载、不访问网络；路径经 `realpath` 规范化后再读取；
- 字节读取沿用既有 `loadInput` 与 `maxFontBytes` 上限；
- 字体解析异常全捕获，不执行字体内任何数据；
- warning/日志消息只含路径、数量、ID，不含字体字节。

## 13. 待确认事项

1. **engine 参数命名**：`defaultFonts` 是否合适？备选 `fallbackFonts`（与设计方案早期命名冲突，不推荐）、`defaultFont`（单数）。
2. **是否需要 `W_FONT_SUBSTITUTED`**：不加则替代成功时无任何提示，加了便于诊断但需变更公共码表。
3. **CLI 系统字体注入上限**：已定为 `maxSystemFonts=6` + `maxTotalBytes=96 MiB`（TTC 按整个文件字节计，超出即停止）。实测（Linux/Noto CJK）：16 个 / 126.4 MiB 时 999.ofd RSS 中位数 512 MB、墙钟 1.55 s；6 个 / 96 MiB 时 426 MB、1.21 s；`--no-system-fonts` 为 140 MB、0.66 s。RSS 差距 +372 MB → +286 MB，剩余主要来自 4 个 Noto CJK TTC（约 89 MB）被展开全部字体面。若后续仍需降低，可另立任务评估“每家族只取一个字体面”或更低字节预算。
4. **CLI 默认开启的接受度**：不传 `--font-dir` 时输出会变化（预期变化），是否需要在发布说明中显著提示。
5. **engine 参数是否保留**：如果 CLI 已自动发现系统字体，engine 的 `defaultFonts` 主要服务于 Web/小程序宿主；若认为优先级不高，可只做 CLI 本期，engine 参数延后。
