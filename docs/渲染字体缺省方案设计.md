# 渲染字体缺省方案设计

本文件定义 OFD 渲染中字体来源的选择与回退规则，以及 CLI 作为 Node 宿主如何提供系统字体。它覆盖 engine 的 `defaultFonts`/`supplementaryFonts` 语义、主字体与逐字形回退顺序、替代字体的显式 GID 限制，以及 CLI 的系统字体发现算法与安全边界。

公共 API 签名见 [`packages/ofdrw-viewer-engine/skills/API.md`](../packages/ofdrw-viewer-engine/skills/API.md)；CLI 参数与用法见 [`packages/ofdrw-viewer-cli/skills/SKILL.md`](../packages/ofdrw-viewer-cli/skills/SKILL.md)；CLI 渲染流程见 [`CLI设计方案.md`](./CLI设计方案.md)；跨包职责与 warning 注册表见 [`CONTRACTS.md`](./CONTRACTS.md)；测试矩阵见 [`测试方案.md`](./测试方案.md)。

## 1. 定位、目标与非目标

### 1.1 定位

字体来源分四层：文档内嵌 `FontFile`、宿主 `FontProvider`、用户默认字体 `defaultFonts`、补充字体 `supplementaryFonts`。本文件负责以下内容：

- 四层来源的固定优先级与跨层选择规则；
- 主字体评分、逐字形回退链、替代字体的显式 GID 判定；
- TTC/OTC 展开、字体面缓存与字节上限；
- CLI 系统字体发现的目录白名单、扫描规则、注入限额与符号链接安全；
- 缺字体/缺字形时的 warning 口径。

engine 只负责按这些规则消费宿主提供的字体字节；CLI 只负责把自己的用户字体与系统字体整理成 `supplementaryFonts`。

### 1.2 目标

1. 给宿主一个明确参数（`defaultFonts`）回答“文档没有可用字体时显示什么”；
2. 让 CLI 默认使用操作系统字体，使用户不必手工寻找字体目录；`--font-dir` 是扩充而非替代；
3. 用户显式提供的默认字体优先于补充字体池；
4. 替代字体必须走 cmap，不能误用文档原字体的显式 GID；
5. 不新增运行时依赖，不改变“文字只走字形轮廓、不调用 `fillText`”的渲染约束。

### 1.3 非目标

- engine 公共 API 不做自动字体发现：不扫描系统字体目录、不调用 `queryLocalFonts`、不提供 `EnvironmentFontSource` 适配器；自动发现只作为 CLI 应用层行为存在。浏览器本机字体由 UI 层按文档声明定向查询（默认关闭、需宿主配置与用户授权），engine 只新增只读的 `document.getFontResources()` 暴露文档声明，见 [`本地字体加载方案设计.md`](./本地字体加载方案设计.md)；
- 不内置、不打包、不下载字体；
- 不做字体子集化、格式转换或字体文件重写；
- 不改变缺字形时的逐字形回退语义；
- 不改变 `W_GLYPH_MISSING` 的触发条件。

### 1.4 为什么发现策略放在 CLI

| 原因 | 说明 |
| --- | --- |
| 平台差异大 | Node 可读文件系统，浏览器不能枚举系统字体，小程序无本地字体；同一套发现逻辑无法跨端一致 |
| 结果不可预期 | 同一文档在不同机器会选到不同字体，版式与黄金图基线难以复现 |
| 成本高 | 目录扫描与字体解析有性能与内存成本，还会引入字体授权与隐私问题 |
| 用户可控性差 | 用户无法预知“为什么用了这个字体”，出问题时难以复现 |

因此 engine 的字体来源一律由宿主显式配置；CLI 运行环境固定（Node + 本机文件系统），输出可通过 `--no-system-fonts` 关闭，来源可通过日志说明，所以由 CLI 自己做系统字体发现。

## 2. 术语与优先级

### 2.1 术语

| 术语 | 含义 |
| --- | --- |
| 文档字体 | OFD `Res.xml` 声明的 `FontResource`，可能带或不带 `FontFile` |
| 精确来源 | 能证明“就是文档要的字体”：内嵌 `FontFile`、`FontProvider` 按名称命中的字体 |
| 默认字体 | 用户通过 `defaultFonts` 显式配置的缺省替代字体 |
| 补充字体 | 用户通过 `supplementaryFonts` 配置的逐字形补充池 |
| 替代字体 | 非精确来源、用于补位或补字的字体面；其显式 GID 不可信任 |

### 2.2 固定优先级

```text
主字体选择（一次解析，结果按字体资源缓存）
  1. 内嵌 FontFile                        [精确, authoritative]
  2. FontProvider.match() 最优候选         [精确]
  3. defaultFonts 最优候选                 [替代, 用户配置]
  4. supplementaryFonts 最优候选           [替代, 用户配置]
  5. 全部失败 → null + W_FONT_MISSING      [文字对象跳过]

逐字形回退链（primary 之后）
  无内嵌字体：provider 其余候选 → defaultFonts 其余 → supplementaryFonts
  有内嵌字体：defaultFonts → supplementaryFonts
```

规则：

1. 精确来源优先：内嵌字体或 provider 命中时，绝不使用默认字体作为主字体；
2. 层间优先于层内评分：没有精确来源时，`defaultFonts` 的主字体资格高于 `supplementaryFonts`，即使补充字体名称更匹配也不反超；
3. 层内按评分选择：`defaultFonts` 与 `supplementaryFonts` 都不取第一个，统一按字体名/别名评分；
4. 替代只补位，不覆盖：主字体存在但缺某个字形时，才逐字形落到回退链；
5. 默认字体不可信任显式 GID：`defaultFonts` 创建的字体面固定 `explicitGlyphs=false`，`CGTransform` 的 GID 被忽略，必须走 cmap；provider/补充字体的判定见“显式 GID 与替代字体”。

### 2.3 `defaultFonts` 与 `supplementaryFonts` 的分工

| | `defaultFonts` | `supplementaryFonts` |
| --- | --- | --- |
| 目的 | 文档字体完全缺省时的替代字体 | 主字体存在但缺字时补齐，也用于完全无字体时兜底 |
| 优先级 | 高于 `supplementaryFonts` | 低于 `defaultFonts` |
| 典型用法 | 传一个通用中文字体，保证“至少能看” | 传业务专用字体包，补齐生僻字 |
| 不传时 | 不加载、不产生额外开销 | 不加载、不产生额外开销 |

没有精确来源时，两者都传则主字体优先取 `defaultFonts`；逐字形先尝试 provider 其余候选（如有），再按 `defaultFonts → supplementaryFonts` 回退。只想要简单兜底的宿主只传 `defaultFonts` 即可。

## 3. `defaultFonts` API 语义

`OFDOpenOptions.defaultFonts` 是可选字段；字段类型、默认值与签名见 [engine API：`OFDDocument.open`](../packages/ofdrw-viewer-engine/skills/API.md#31-ofddocumentopenoptions-ofdopenoptions--ofdopenfromcontaineroptions-promiseofddocument) 与 [字体接口](../packages/ofdrw-viewer-engine/skills/API.md#81-字体)。

语义与约束：

- `defaultFonts` 的主字体优先级高于 `supplementaryFonts`；有内嵌字体或 provider 精确命中时不抢主字体，但仍进入逐字形回退链；
- 每个来源只接受已读好的 `data` 与可选 `family`；engine 不读取字体 URL、本地路径或文件系统；
- `defaultFonts` 创建的字体面固定 `explicitGlyphs=false`，显式 GID 被忽略，必须按 cmap 命中；
- 每个字体字节受 `limits.maxFontBytes`（默认 64 MiB）约束，超限来源被忽略并产生 `W_FONT_MISSING`；
- TTC/OTC 自动展开为多个字体面参与评分；
- 字体面按文档实例缓存，随文档关闭释放，不跨文档共享；
- 不传时行为与未引入该参数时一致，不加载、不额外解析。

使用示例：

```ts
// Node / Electron 主进程：宿主读取字体字节
const nodeFont = await readFile('/opt/fonts/SourceHanSerifSC.otf');
await OFDDocument.open({
  source,
  defaultFonts: [{ data: nodeFont, family: 'Source Han Serif SC' }],
});

// Web：宿主 fetch 成字节
const webFont = await (await fetch('/assets/fonts/noto-serif-sc.otf')).arrayBuffer();
await OFDDocument.open({
  source,
  defaultFonts: [{ data: webFont, family: 'Noto Serif CJK SC' }],
});

// 已知字体字节（小程序、内存字体包）
await OFDDocument.open({
  source,
  defaultFonts: [{ data: fontBytes, family: 'Noto Serif CJK SC' }],
});
```

需要按需读取（网络、URL、宿主字体库）时，实现 `FontProvider` 并在 `match()` 内读取，返回 `{ data }`；见“Node、Web 与小程序”与 [`网络与文件获取委托设计`](./网络获取委托设计.md)。

CLI 当前不使用 `defaultFonts`：它把 `--font-dir` 与系统字体都并入 `supplementaryFonts`（用户字体在前），由 engine 按统一规则评分与回退；`defaultFonts` 主要服务于 Node/Web/小程序宿主。

## 4. 解析与回退流程

### 4.1 主字体选择

`FontLibrary.resolve(font)` 按字体资源缓存 `Promise<FontFaceSet | null>`，首次解析时：

1. 查已登记的内嵌字体；
2. 无内嵌字体时调用 `FontProvider.match()`，按 provider 返回顺序创建字体面，并按评分降序排列；
3. 加载 `defaultFonts` 的全部字体面；
4. 加载 `supplementaryFonts` 的全部字体面；
5. 依次从内嵌、provider、default、supplementary 中选第一个非空集合的最优字体面作为主字体；
6. 全部为空时产生 `W_FONT_MISSING`，返回 `null`。

评分规则（`scoreFace`）：

- 字体名或 PostScript 名与请求名称归一化后完全相等：200 分；
- 通过内置/宿主别名表匹配：100 分；
- bold 与请求一致：+10；
- italic 与请求一致：+5；
- 同分时保留先出现的候选（provider 按返回顺序、default/supplementary 按配置顺序与 TTC 展开顺序）。

默认字体面固定 `substitute: true`、`authoritative: false`，并在创建时使用 `input.family ?? default-<index>` 作为诊断名；TTC 展开后的真实 family 参与评分。

### 4.2 逐字形回退链

主字体确定后，按固定顺序构造回退链：

- 无内嵌字体：provider 其余候选（移除已选主字体，保持评分顺序）→ 全部 `defaultFonts` 字体面 → 全部 `supplementaryFonts` 字体面；
- 有内嵌字体：全部 `defaultFonts` 字体面 → 全部 `supplementaryFonts` 字体面；
- 按字体面 `key` 去重，主字体自身不重复进入回退链。

逐字形解析（`resolveGlyph`）：

1. 主字体可信任显式 GID 且调用方提供 GID 时，先尝试显式 GID；
2. 否则在主字体 cmap 中查码点；
3. 主字体缺失该字形时，按回退链顺序逐个查 cmap；
4. 全部失败返回 `null`，渲染侧产生 `W_GLYPH_MISSING` 并跳过该字形，同一文本对象的其余字形继续绘制。

回退字体只通过 cmap 命中，不使用显式 GID。

### 4.3 显式 GID 与替代字体

- 内嵌字体（`authoritative`）始终可信任显式 GID；
- `defaultFonts` 字体面固定 `explicitGlyphs=false`，即使 family 与请求同名也不重新信任；
- provider 与 `supplementaryFonts` 的字体面在成为主字体时重新判定：归一化 family/PostScript 名完全相等时可信任；仅当名称包含非 ASCII 字符（例如“仿宋”与 `FangSong`）时才放宽到别名匹配；纯西文别名替代（如 Times New Roman → Nimbus Roman）不可信任显式 GID；
- 不可信任时 `CGTransform` 的 GID 被忽略，改走 cmap；
- 字宽优先取文档的 `DeltaX/DeltaY`；缺失时回退到实际命中字体面的 advance；
- 替代字体与文档原字体的度量可能不同，字宽随之变化；当前不做度量补偿。

### 4.4 TTC/OTC、字节上限与缓存

- TTC/OTC 展开为文件内的全部字体面，每个字体面独立参与评分与回退；
- 每个 `FontInput.data` 的字节数按整个文件计，超过 `maxFontBytes`（默认 64 MiB）时整个来源被忽略并产生 `W_FONT_MISSING`；
- `defaultFonts`/`supplementaryFonts` 的字体面按配置顺序惰性加载一次，同一文档内复用；
- 解析结果按 `fontFile + 字体名 + bold/italic` 缓存；重新登记内嵌字体会清掉旧的失败/回退结果；
- `clear()`/`dispose()` 清空内嵌字体、解析结果、默认/补充字体面与 warning 去重集合。

### 4.5 缺字体与缺字形

- 字体资源没有任何可用字体面时：engine 产生 `W_FONT_MISSING`，渲染侧跳过整个文字对象；空间文本侧跳过对应文本项；
- 字体存在但某个码点无字形时：`W_GLYPH_MISSING`，只跳过该字形，同一文本对象的其余字形继续绘制；
- `W_FONT_MISSING` 在字体库内按 `(code, resourceId, message)` 去重；`W_GLYPH_MISSING` 由文本布局按文本对象去重，最终收集键为 `(code, pageIndex, objectId)`，同一文本对象最多上报一次；
- `--text` 导出不改变上述行为：缺字体页面仍输出图片，只是文本项可能减少。

## 5. 各端配置

### 5.1 Node、Web 与小程序

| 端 | 默认行为 | 宿主补充方式 |
| --- | --- | --- |
| Node / Electron 主进程 | 无字体来源 | `defaultFonts`/`supplementaryFonts: [{ data }]`（宿主 `readFile`），或 `FontProvider` |
| Web | 无字体来源 | `defaultFonts`/`supplementaryFonts: [{ data }]`（宿主 `fetch`），或 `FontProvider` |
| 微信小程序 | 无字体来源 | `defaultFonts`/`supplementaryFonts: [{ data }]`（宿主读取本地字体字节） |

- 浏览器不能枚举系统字体，也不应依赖 `queryLocalFonts` 做默认渲染；
- Web：UI 层可用 `fonts.default`/`supplementary` 的 `url` 直接配置，读取由 UI 完成（见 [`字体配置方案设计.md`](./字体配置方案设计.md)）；此外 UI 支持可选的浏览器本机字体来源（`FontSource` 的 `{ local }`，默认关闭、需宿主 `fonts.localFonts` 配置与用户授权、只按文档声明定向查询），注入顺序为「宿主配置在前、本机字体在后」，见 [`本地字体加载方案设计.md`](./本地字体加载方案设计.md)；engine 侧不涉及该能力，只新增只读的 `document.getFontResources()` 供宿主读取文档字体声明；
- `FontProvider.match(request)` 是宿主按需提供字体的唯一入口，请求字段为 `fontName`、`familyName?`、`charset`、`bold`、`italic`、`serif`、`fixedSize`；返回一个/多个 `{ data }` 或 `null`；
- engine 不联网、不读文件；网络与文件策略由宿主实现，见 [`网络与文件获取委托设计`](./网络获取委托设计.md)。

### 5.2 CLI 默认系统字体发现

CLI 把两类字体合并后以 `supplementaryFonts` 注入 engine：`--font-dir` 的用户字体在前，系统字体在后；两者都先规范化 realpath，再按路径去重，重复项保留先出现者。engine 按字体名评分选择主字体，同分时保留先出现者，因此用户字体在同名同分时优先。

系统字体目录白名单（只读，不跟随白名单外路径）：

| 平台 | 目录 |
| --- | --- |
| Linux | `/usr/share/fonts`、`/usr/local/share/fonts`、`~/.fonts`、`~/.local/share/fonts` |
| macOS | `/System/Library/Fonts`、`/Library/Fonts`、`~/Library/Fonts` |
| Windows | `%WINDIR%\Fonts`（未设置时用 `%SystemRoot%\Fonts`）、`%LOCALAPPDATA%\Microsoft\Windows\Fonts` |
| 其他 | 空（不发现） |

发现规则：

- 只用 `node:fs`，不调用 `fc-list`、不读注册表、不联网；
- 扩展名过滤 `.ttf/.otf/.ttc/.otc`（大小写不敏感）；
- 目录不存在或不可读时静默跳过该目录，不影响其他目录，也不报错；
- 不跟随目录符号链接；文件符号链接允许，但 realpath 必须仍位于某个白名单根的 realpath 之下，否则跳过；
- 目录遍历顺序按名称排序，保证同目录内结果稳定；
- 收集的字体文件数上限 `maxFonts=2000`，达到上限后停止收集；
- 候选按优先级排序：文件名命中 CJK 关键字（`cjk`、`noto`、`sourcehan`、`simsun`、`simhei`、`msyh`、`pingfang`、`fangsong`、`kaiti` 等）排前；其次命中常见西文衬线/无衬线关键字；其余最后；同优先级按路径字典序；
- 排序后才应用限额：最多注入 `maxSystemFonts=6` 个，总字节不超过 `maxTotalBytes=96 MiB`（TTC/OTC 按整个文件计）；单个字体放不下时跳过并继续尝试后续字体，避免因超大文件提前结束选择；
- 发现结果按“目录列表 + 限额”在本进程内缓存，一次转换只扫描一次；
- 启用发现时，日志通过 stderr 输出一行：`自动发现系统字体 N 个（扫描 M 个文件）`，不污染 stdout；
- `--no-system-fonts` 完全关闭发现，只使用 `--font-dir`。

`--font-dir` 的扫描与系统扫描是两套规则：

- 用户目录扫描是严格模式：目录不存在、不是目录、不可读取分别产生 `CLI_FONT_DIR_INVALID`/`CLI_FONT_DIR_UNREADABLE`，退出 1；
- 用户目录允许跟随符号链接目录，并以 realpath 防止目录环；文件按 realpath 去重；
- 结果按路径字典序排列；目录内没有字体时产生 `W_FONT_DIR_EMPTY` 并继续。

扫描完成后，CLI 通过 `loadFontInputs()` 在转换开始前读取全部字体字节；单个文件读取失败产生 `W_FONT_MISSING` 并跳过，其余字体照常注入。engine 只接收 `{ data }`，不接收路径。

## 6. warning 与安全边界

### 6.1 warning

字体相关 warning 只有两个公共码：

| 码 | 触发 | 影响 |
| --- | --- | --- |
| `W_FONT_MISSING` | 字体资源无可用字体面；来源缺少 `data`、解析失败、超过 `maxFontBytes`；CLI 字体字节读取失败 | 跳过整个文字对象/文本项，或忽略单个字体来源 |
| `W_GLYPH_MISSING` | 主字体与回退链都没有该码点的字形 | 跳过该字形，其余文本继续绘制 |

- CLI 另产生 `W_FONT_DIR_EMPTY`（用户字体目录为空）；系统目录缺失或不可读不产生 warning；
- warning 消息只含字体名、资源 ID、路径与数量，不包含字体字节；
- CLI 打印 engine warning，有页号时附页号，结束时按 code 汇总，不改变退出码。

### 6.2 安全边界

- engine 不访问文件系统、不联网、不读取字体 URL/路径；字体字节由宿主提供；
- CLI 只读白名单系统目录与用户显式指定的 `--font-dir`，不写、不下载、不访问网络；
- 路径先 `realpath` 规范化再读取；系统扫描拒绝逃逸白名单根的文件符号链接，拒绝目录符号链接；
- 字体解析异常全部捕获，不执行字体文件中的任何数据；
- 每个字体来源受 `maxFontBytes` 限制，CLI 系统字体另受 6 个/96 MiB 预算限制，避免一次解析全部系统字体；
- 用户可用 `--no-system-fonts` 关闭自动发现；关闭后仅使用 `--font-dir`（可为空）；
- 不自动安装字体、不修改系统字体目录。

## 7. 兼容性与当前边界

| 场景 | engine/CLI 行为 |
| --- | --- |
| 不传 `defaultFonts` | 不加载默认字体；主字体仍来自内嵌/provider/supplementary，行为与未引入该参数时一致 |
| 传 `defaultFonts` | 仅在没有精确来源时作为主字体；有内嵌/provider 命中时不抢主字体，但仍进入逐字形回退链 |
| 只传 `supplementaryFonts` | 行为不变；完全无字体时仍用它兜底 |
| 同时传两者 | 无精确来源时主字体优先 `defaultFonts`；逐字形先 provider 其余（如有），再回退 `defaultFonts → supplementaryFonts` |
| CLI 默认 | 自动注入白名单系统字体；未内嵌字体的文档文字可读性提高，输出可能与无字体环境不同 |
| CLI `--no-system-fonts` | 关闭系统字体，仅用 `--font-dir`；用于复现无系统字体环境的渲染结果 |
| CLI `--font-dir` | 用户字体排在系统字体前；系统字体继续作为扩充参与回退 |
| 字体超过限制 | 单个来源超过 `maxFontBytes` 被忽略；系统字体超过 6 个/96 MiB 预算的候选不注入 |
| TTC/OTC | 展开全部字体面参与评分；预算与上限按整个文件字节计 |
| 替代成功 | 不产生专用 warning；只有缺字体/缺字形产生 warning |
| 文本导出 | 缺字体时文本项减少，JSON 结构不变 |

当前边界：

- 不做字体子集化、压缩或格式转换，不重写字体文件；
- 系统字体发现按文件名关键字排序，不解析字体内部 family 后再排序；
- 注入上限是“整个文件”粒度，TTC 内多个字体面共享同一文件预算；
- 不提供单独关闭“用户字体”的开关；`--font-dir` 省略即只使用系统字体。

## 8. 验证方式

字体优先级与回退断言（engine）：

- 无内嵌、无 provider 时 `defaultFonts` 作为主字体；
- `defaultFonts` 优先于 `supplementaryFonts`，即使补充字体名称更匹配；
- 内嵌字体或 provider 命中时 `defaultFonts` 不作主字体；
- 多个 `defaultFonts` 按评分选择，而非取第一个；
- TTC/OTC 展开全部字体面并分别参与评分；
- `defaultFonts` 的 `explicitGlyphs=false`：显式 GID 被忽略、按 cmap 命中；
- 来源缺 `data`、解析失败、超过 `maxFontBytes` 时只 warning 并继续后续来源；
- 内嵌字体命中时 `defaultFonts` 仍进入逐字形回退链；
- 不传 `defaultFonts` 时保持既有行为；无任何来源时返回 `null` 并产生 `W_FONT_MISSING`；
- `clear()` 后默认字体重新解析。
