## 1. 重新定位问题

### 1.1 旧方案的路径

旧方案的三步走：

```text
第一步：统一缓存骨架   PageView 增加文字层释放 API，trimCache 增加节点预算维度
第二步：删除节点上限   移除 5000 截断与 truncated 链路
第三步：生命周期与调度 三级状态、rAF、settle 延后
```

其中第一步**必须改动 canvas 缓存**（`viewer.ts` 的 `trimCache()`、`releaseCachedPage()`），牵涉页级缓存的既有语义与全部相关测试。

### 1.2 真正要解决的问题只有两个

回顾原始诉求，用户实际关心的是：

| 诉求 | 旧方案的应对 |
| --- | --- |
| 第 2 页文字超过 5000 被截断，无法选中 | 删除上限（第二步） |
| 高速滚动、频繁上下滑动卡顿 | 缓存复用（第一步 + 第三步） |

其中“卡顿”的根源在旧实现里是**每次滚动都整页重建文字层 DOM**。旧方案用“保留已建好的页”来避免重建。但还有一条更直接的路：**不要一次建那么多**。

### 1.3 关键前提：span 坐标恒定

`createTextSpan()` 写入的坐标是 **96 DPI 绝对坐标**，缩放由页面容器的 `--scale-factor` 承担，旋转由容器 CSS transform 承担。这意味着：

- span 一旦创建，**坐标永不失效**；
- 缩放、旋转都不需要重建 span；
- 因此“分块按需创建”在坐标层面没有任何额外成本，不需要考虑“块的内容随缩放变化”。

旧方案的复杂度很大一部分来自缓存管理，而这个前提说明：**问题可以退化成一个纯粹的“该建哪些 span”问题。**

## 2. 核心思路：按需构建

### 2.1 一句话

**只构建可见区域内实际会显示的文字 span，其余部分不创建 DOM。**

### 2.2 为什么可行

- **画面上能看到的只有可视区内的文字**：一页纸在屏幕上只露出多少，就只需要多少 span。通常不到整页的 30%，双栏/缩放场景更低。
- **文字层是透明覆盖层**：不参与视觉绘制，只服务于选中、复制、查找高亮。看不到的部分没有任何用户价值。
- **构建成本与 span 数成正比**：少建 70%，构建耗时与 DOM 节点数同样下降 70%。

### 2.3 与旧方案的本质区别

| | 旧方案（缓存复用） | 本方案（按需构建） |
| --- | --- | --- |
| 策略 | 建整页 → 保留不销毁 | **永远只建看得见的部分** |
| 峰值 DOM | 缓存窗口内所有页的整页 span | 仅可视区内的 span |
| 复用方式 | 保留 DOM 避免重建 | 不重建的原因是**它本来就没被删** |
| 改动范围 | `viewer.ts` + `page-view.ts` + `text-layer.ts` | **仅 `text-layer.ts` + `geometry.ts`** |
| 5000 截断 | 删除上限 | 自然消失（不再按页全量构建） |

**关键洞察**：只要“可见区”稳定，同一块内容的 DOM 就不会被反复创建；滚动时才增减块。这与“频繁上下滑动”是相容的，因为滑回同一区域命中的是同一批块。

## 3. 具体设计

### 3.1 可见区判定

需要每页在滚动容器中的**实际可见矩形**，现有 `visiblePageRange` 只有页级信息，不够。

计算方式：

```text
viewportRect = 滚动容器的可见矩形
pageRect     = pageView.element.getBoundingClientRect()
intersect    = 两者求交
```

- 相交为空 → 该页不建任何 span；
- 有交集 → 把交集矩形换算到该页的 96 DPI 坐标系，得到 `visibleTop` / `visibleBottom`。

换算要点：`getBoundingClientRect()` 返回的是含缩放、旋转的屏幕坐标，需要逆向换算回 96 DPI 基座。项目已有 `layoutScale` 与旋转状态，换算公式需要与 `applyLayerScale()` 对偶。

**实现口径（已落地）**：行按页内 `y` 分组（行划分主轴水平），因此可见区只换算为**页内 y 区间**：

- 旋转 0°：交集四角映射回页内后取 y 的 min/max；
- 旋转 180°：同样取四角映射后的 y 包围盒（屏幕上部对应页内下部，方向自然反转）；
- 旋转 90°/270°：屏幕纵向对应页内 `x`，行（按页内 y 分组）没有可见边界，**该页按整页构建**。这是已知限制——按 x 裁剪需要把行改为“列”分组，与行差量模型不一致，不纳入本方案。

页元素或滚动容器不可测量（宽/高为 0）时同样退化为整页构建。

**布局框**：文字层是 `overflow: hidden` 的覆盖层，框外内容不可见也不可选，因此框高取“纸面高”与“当前 DOM 中全部已建行并集下沿”的较大者，既不会把 HOLD 窗口内保留的上部行挡在框外，也不会随滚动单调膨胀到整页。

### 3.2 分块粒度

**以行为块**，而不是以 span 为单位：

1. 按 `TextSpanSpec.y`（或旋转后的主轴）把 span 分组成“行”；
2. 每行对应一个 span 集合；
3. 只构建与 `[visibleTop - margin, visibleBottom + margin]` 相交的行。

**为什么按行而不是按 span**：选中是行内连续的，按 span 切会让一行内的 span 分布不均，且行内判定的边界条件多得多。按行分块，判定只需一次区间比较。

`margin` 是上下预渲染带，建议 **1~2 行高**，用于容纳轻微滚动和选区边缘。

### 3.3 构建与增减

```text
滚动提交（rAF）
  ├→ 计算各页可见矩形
  ├→ 对每页：
  │    目标行集合 = 与可见矩形相交的行
  │    ├→ 已在 DOM 中的行：保留（不动）
  │    ├→ 新增的行：创建 span 并插入
  │    └→ 离开的行：移除 span
  └→ 无变化的页：跳过，不做任何 DOM 操作
```

**关键：只做差集，不做全量替换。** 现在的实现是 `replaceChildren(layer, fragment)`，每次都是整页重建；改为按行差量后，滚动一个小距离几乎不产生 DOM 操作。

### 3.4 行 ID 与幂等

每行需要稳定标识，否则无法判断“这个行是否已存在”：

- 行 ID 由该行内 span 的 `itemIndex` 集合（或首个 `itemIndex` + 行序号）派生；
- 用 `Map<rowId, HTMLElement[]>` 在页内维护已建行；
- 同一行重复进入可见区时直接命中，不重复创建。

### 3.5 文字数据缓存

`buildTextLayerSpecs(content)` 需要完整 `TextContent` 才能分行。因此：

- `getTextContent()` 的结果**按页缓存**（内存对象，不含 DOM），页记录保留在 `Map<pageNumber, TextContent>` 中；
- 这是**纯数据缓存**，成本远低于 DOM，可以保留全部已访问页，无需 LRU 淘汰 DOM；
- `buildTextLayerSpecs()` 对缓存的 `TextContent` 只做一次，结果也缓存为“行划分表”。

`TextContent` 本身在引擎侧已有按页 mm 布局缓存，UI 层的这份缓存是 DPI 换算后的结果，仍然值得保留。

### 3.6 调度

- 滚动 `scroll` → rAF 合并（与现有 `scheduleScrollUpdate` 一致）；
- 分块计算与差量 DOM 操作在 rAF 内完成，**不再使用 `runMicrotask`**；
- 缩放进度中（手势未结束）不做重建，与现有手势缩放策略一致。

## 5. 风险与应对

### 5.1 选区完整性（主要风险）

**风险**：用户从可见区开始拖选，鼠标移到可视区外时，浏览器会尝试扩展选区到未构建的 span，导致选区在可见区边缘被截断。

**应对**：

1. `margin` 预渲染带取 1~2 行，覆盖轻微越界；
2. 选区操作进行中（`selectionchange` 且选区非空）时，**临时提升 margin 到整页**，即构建全页 span，选区结束后恢复；
3. 极端情况下（用户长距离拖选出屏幕），以“停止拖选后补建”为准，允许拖选过程中可见区外无法选中。

这是本方案**最主要的体验取舍**，需要在实现前用真实交互验证。

### 5.2 查找高亮的定位

**风险**：`scrollToMatch()` 依赖在文字层中 `querySelector` 找到目标 span 再 `scrollIntoView`。若目标 span 尚未构建，查找会失败。

**应对**：查找定位改为基于**页坐标**跳转（`goToPage` + 页内偏移），不依赖 span 存在；高亮框绘制在独立的高亮层（现有 `ofd-page__find-layer`），本就与文字层分离，不受影响。

### 5.3 旋转页面的坐标换算

**风险**：`getBoundingClientRect()` 在页面旋转 90°/180°/270° 时，`top/bottom` 与文字的阅读主轴不对应。

**应对**：换算时按旋转状态映射到文字主轴；四个旋转角度需要分别验证。这是实现中最容易出错的部分。

### 5.4 滚动中的创建频率

**风险**：快速滚动时行在边界反复进出，可能反复创建/删除同一批行。

**应对**：

- 采用**滞后窗口**：已建行在离开可见区后保留 `HOLD_LINES`（建议 5~10 行）的缓冲，滚动回扫时直接命中；
- 这本质是“行级小缓存”，比旧方案的页级缓存轻得多，且不需要与 canvas 同步。

### 5.5 页内全部构建的退化

**风险**：页面很短（一屏可见整页）时，等价于构建全部，与现状相同。

**应对**：这是可接受的退化。此时 span 数本就在可视范围内，不构成问题。

新增内部结构（示意）：

```ts
/** 文字行：与可见区判定的最小构建单位。 */
interface TextRow {
  /** 稳定行标识；由行内首个 itemIndex 与行序号派生。 */
  readonly id: string;
  /** 行在 96 DPI 坐标系中的上下边界，单位 px。 */
  readonly top: number;
  readonly bottom: number;
  /** 该行的 span 描述。 */
  readonly spans: readonly TextSpanSpec[];
}

/** 页文字层状态：只记录数据与已建行，不记录整页生命周期。 */
interface PageTextState {
  /** 引擎文本内容；构建分行表后仍保留，供后续行按需取用。 */
  content: TextContent | null;
  /** 行划分结果；`null` 表示尚未划分。 */
  rows: readonly TextRow[] | null;
  /** 已建行：行 ID → span 元素。 */
  built: Map<string, HTMLSpanElement[]>;
  /** 生成代次，用于丢弃迟到的异步结果。 */
  generation: number;
  /** 取消信号。 */
  abort: AbortController | null;
}
```

## 7. 实施步骤

### 第一步：行划分与差量构建

- `geometry.ts` 新增行划分函数（按阅读主轴分组，输出 `TextRow[]`）；
- `text-layer.ts` 用行差量替换 `replaceChildren` 全量替换；
- 先**不做可见区裁剪**，只把“整页构建”改成“按行构建”（行为等价，验证差量逻辑正确）。

验证：

- 整页构建结果与现状一致（span 数、位置、顺序）；
- 滚动时不再出现全页 `replaceChildren`。

### 第二步：可见区裁剪

- 实现可见矩形计算与坐标逆换算（含 4 个旋转角度）；
- 只构建与可见区相交的行；
- 加入 `margin` 预渲染带与 `HOLD_LINES` 滞后窗口。

验证：

- 长页面只构建可视区内的行，DOM 节点数显著下降；
- 上下滚动时行在边界不抖动（同一行不被反复创建）；
- 旋转 90°/180°/270° 下行判定正确。

### 第三步：删除上限与选区/查找适配

- 按第 4.1 节删除 `maxNodes` / `truncated` / `W_TEXT_LAYER_LIMIT`；
- 选区进行中临时提升 margin 的适配；
- `scrollToMatch` 改为基于页坐标定位。

验证：

- 第 2 页不再出现“5000 已截断”告警，且该页文字可完整选中；
- 从可见区拖选到边界时有 1~2 行的余量；
- 查找跳转在任意页均能正确定位。

## 8. 待确认

1. **选区边缘的取舍是否可接受**：第 5.1 节的“临时提升 margin”会在拖选时重建全页，与“按需构建”的初衷有冲突。是否接受、还是宁可牺牲拖选体验换取稳定性能？
2. **行划分的主轴判定**：竖排文字、逐字旋转文字的主轴与横排不同，`shouldSplitChars()` 已区分字符级 span，行划分需要复用该判断。是否有已知的复杂排版需要纳入验证？
3. **是否保留 `HOLD_LINES` 滞后窗口**：它引入了轻量的行级缓存，与“完全按需”略有偏离，但对频繁上下滑动有效。默认建议保留。

## 10. 已知限制（交付版）

以下为按需构建方案落地后的最终限制与口径，供宿主与后续维护参考。前三条是**产品行为**，后三条是**验证与测试口径**。

1. **旋转 90°/270° 时文字层按整页构建**（路线 A）：行按页内 `y` 分组，这两个角度下屏幕纵向对应页内 `x`，行没有可见边界，因此该页不做行级裁剪、整页构建。已在本文 §3.1、`skills/API.md` 功能开关段、`skills/SKILL.md`「查找与选中」与 [`text-layer.ts`](../packages/ofdrw-viewer-ui/src/text/text-layer.ts) / [`geometry.ts`](../packages/ofdrw-viewer-ui/src/text/geometry.ts) 的注释中登记。按 `x` 裁剪需把行改为“列”分组，与行差量模型不一致，不纳入本方案。
2. **`HOLD_LINES = 8` 的滞后缓冲属实现细节**：已建行滚出构建窗口后最多再保留 8 行高的范围（拖选整页期间不删行），用于避免边界抖动。该取值与保留行为**不构成对外承诺**，宿主与外部测试不得依赖具体行数。
3. **几何不可测量时退化为整页构建**：页元素或滚动容器 `getBoundingClientRect()` 宽/高为 0（jsdom、未布局、容器被隐藏）时，该页按整页构建；jsdom 单测因此与“整页构建”等价。
4. **e2e 旋转用例 180° 分支无显式上界**：`test/e2e/text-layer.spec.ts` 的 180° 断言为“页尾行已建、整页标题被移除、构建范围整体下移”（下界与相对方向），没有对“最多构建多少行”给出显式上界；裁剪上界由 0° 分支（页尾标记不在 DOM）与 90°/270° 分支（整页构建）承担。属测试口径限制，非产品行为。
5. **e2e 行数辅助断言按“每 item 一行”夹具口径**：`countBuiltRows()` 用 DOM 中已建 span 的 `data-item-index` 集合去匹配行 ID 的 `itemIndex` 前缀，在 e2e 夹具（每行恰好一个文本 item）下即“已建行数”；若真实排版存在一个 item 跨多行，同一 item 的多个行会被同时计为已建、结果偏大。因此它只作**辅助**断言（首屏已建行 < 整页真实行数的 50%，主断言是同页“已建行覆盖高度 / 整页高 < 0.5”的几何比例），整页分母本身用产品同源 `buildTextRows()` 计算；行划分正确性由单测覆盖（横排多行、竖排、逐字旋转、item+char 混排、四向旋转）。
6. **文字层文本基于引擎逐页读取缓存**：每页 `getTextContent()` 结果与行划分表按页保留在内存（纯数据，不含 DOM），页离开可见列表（可见页范围上下各 1 页预取）时才连同已建行一起清理；不按 LRU 淘汰 DOM。查找侧另有独立的按页文本缓存（与文字层不共享）。
