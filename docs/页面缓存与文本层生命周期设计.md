## 1. 定位与范围

**页面缓存**指阅读器为“最近访问/正在使用的页”保留的可复用产物。共三类：

| 产物 | 载体 | 释放入口 | 生命周期 |
| --- | --- | --- | --- |
| canvas 像素 | `PageView.canvasElement` | `PageView.releaseCanvas()`（`page-view.ts:756-779`） | 页级 LRU + 像素预算 |
| 文本层 DOM | `PageView.textLayer` 子节点（span） | `PageView.releaseTextLayer()`（**新增**） | 与页同进同退，pin 例外 |
| 页文本数据 | `PageTextState.content` / `rows` | `TextLayerService.handlePagesReleased()`（**新增**） | 随页保留，页淘汰时释放 |

本文回答四件事：

1. 一页的产物何时构建、保留、淘汰；
2. 容量与预算如何分配（页数、滚动 span、pin span、canvas 像素）；
3. 选区在页被保留/淘汰时如何保持正确（**快照负责正确性，pin 只保住原生锚点**）；
4. 与 pdf.js 的取舍对应关系。

## 2. 重构前的现状与问题

> **实施状态**：页级模型已按本文与实施规格落地（t9~t23）。本节保留重构前的缺陷事实与根因，
> 用于解释为什么必须换模型；当前实现以 §4~§7 为准，不再使用行级增删。
>
> **勘误**：v1 本节曾写“二元生命周期（可见即建、不可见即毁）”，那是更早一版实现；到重构前
> 又演变为**行级按需构建**。两种描述都只属于历史，不是当前实现。

### 2.1 canvas：已有正确的页级缓存

```text
renderVisible()                              viewer.ts:3023-3043
  └→ markRendered(index)                     :3283-3287
       └→ trimCache()                        :3393-3412
            ├→ 页数：renderOrder.length > pageCacheSize
            ├→ 像素：已渲染页总像素 > pageCachePixelBudget
            └→ 只淘汰不可见页（isVisiblePage，:3383-3385），最远者优先
```

三条规则：双阈值同时生效；可见页豁免；LRU 顺序由 `renderOrder` 维护（`:460`）。

### 2.2 文本层：行级增删（重构前实现，问题是选区被删）

- 构建窗口：可见区 ± `WINDOW_MARGIN_LINES = 2` 行（`text-layer.ts:53, 908`）。
- 删除窗口：构建窗口 ± `HOLD_LINES = 8` 行（`:56, 929-932`），越界行 `element.remove()`（`:948-953`）。
- 保留窗口 ≈ **10 × bandHeight**。dense 页 `bandHeight = 6.67 px` → 仅 **66.7 px**；普通页约 136 px。
- 不在 `visiblePageNumbers()` 的页直接 `clearPageTextLayer()`（`:303-307`）→ `replaceChildren` 整页删除（`:1132`）。
- `draggingPage` 只在 pointerdown→pointerup 间保护（`:261-283`），松手即恢复删除。

以上是重构前的行级实现。其后果：

| 场景 | 机制 | 用户可见结果 |
| --- | --- | --- |
| 同页选中后滚动 | 锚点 span 被行删除 | 选区消失 / 高亮缺行 |
| 跨页选中后滚动 | 端点页整页清空 | 原生选区折叠；**复制静默少一整页**（`selection.ts:198-201` 的 `continue`） |
| 中间页被清空 | 中间页无 span | 复制静默缺中间页，无任何提示 |
| 缩放/旋转等布局变化 | 重建窗口变化 → 行删除或整页清空（见 §2.3） | 选区消失、高亮清空 |
| 切页/拖选起手 | 整页同步构建 8331 span | 可感知卡顿 |

### 2.3 同源缺陷：布局变化（缩放/旋转）也丢选区

t4 真实浏览器实测（重构前实现，非本设计引入）：

| 操作 | 选区 |
| --- | --- |
| 放大 1 → 1.5 → 2 | **丢失** |
| 旋转 180° / 270° | **丢失** |
| 缩小 2 → 1.5 → 1 | 保留 |
| 旋转 0° → 90° | 保留 |

方向不一致，说明是否丢失取决于**本次重建是否移除了选区锚点所在的 span**，与滚动丢选区属同一根因族：

1. `reflow()` 在刚写完新布局、`visiblePageRange`/滚动位置尚未更新时**同步**调用
   `textLayer.refresh()`（`viewer.ts:2726-2730`）；`refresh()` 用新旧混合的几何求构建窗口，
   可能删除锚点行（`text-layer.ts:948-953`）。
2. 若该页在新旧可见集合之间翻转，则走 `clearPageTextLayer()` 整页清空（`:303-307`），
   锚点随整页 DOM 删除；同一调用还会 `removeSelectionLayer()`（`:1137` → `:594-598`），
   所以高亮会立刻消失，而不是等下一次重绘。
3. 删除锚点文本节点 → 浏览器 Selection 折叠/改锚 → `selectionchange` 把空模型写回 → 高亮清空。

本设计的处置（两条，缺一不可）：

- **结构上消除**：页级构建后，布局变化只改图层 `transform`/尺寸（`applyLayerScale`），
  **不再有行删除**，锚点 span 不会被移除；
- **快照兜底**：布局变化不是“用户取消选择”，**不得触发快照失效**；矩形存 96 DPI 页坐标，
  与缩放/旋转无关（§7.2、§7.5）。

### 2.4 为什么必须换模型

行级删除与浏览器 Selection 的锚点语义根本冲突：锚点是 DOM 文本节点，节点一删，选区即失效。
“钉住选区行”只能缓解同页，跨页与中间页仍会静默丢字。**整页构建 + 页级保留**是唯一与
Selection 语义兼容的最小改动。

## 3. 参考实现：pdf.js

### 3.1 页级 LRU

`PDFPageViewBuffer` 以 `Set` 插入顺序实现 LRU，默认 `DEFAULT_CACHE_SIZE = 10`，按可见页数动态放大：

```js
const newCacheSize = Math.max(DEFAULT_CACHE_SIZE, 2 * numVisiblePages + 1);
this.#buffer.resize(newCacheSize, visible.ids);   // 可见页移到队尾，延迟销毁
```

保留粒度为整个 PageView（canvas + 文本层 + 标注层），产物天然同步淘汰。

### 3.2 不可见页只隐藏

```js
hide() {
  this.highlighter?.disable();
  this.div.hidden = true;      // 只设 hidden，DOM 全部保留
}
```

### 3.3 文本层构建

- 流式分块：`render()` 用 `ReadableStream` 逐块 pump，每块回调 `#processItems`，天然让出事件循环。
- 单字符 div 不做 canvas 测量（源码注释：大量单字符 div 时滚动快很多）。
- 先写样式后挂 DOM。
- **单页节点上限 `MAX_TEXT_DIVS_TO_RENDER = 100000`**。

### 3.4 勘误：pdf.js 有单页上限

v1 §3.4 曾写“文字层没有节点上限”，**错误**。pdf.js 实际以 `MAX_TEXT_DIVS_TO_RENDER = 100000`
作为单页兜底，超限截断并告警。本文采用同量级上限（§5.3）。

### 3.5 采纳与不采纳

| 机制 | pdf.js | 本文 | 理由 |
| --- | --- | --- | --- |
| 页级 LRU 统一淘汰 | 有 | **采用** | 消除两套策略错位 |
| 整页构建、不删单个 span | 有 | **采用** | 选区锚点稳定的前提 |
| 流式/分帧构建 | 有 | **采用（rAF 分帧）** | 我们没有流式文本 API，用分帧等效 |
| `hidden` 隐藏不可见页 | 有 | **不采用** | 页盒是绝对定位、滚动高度由 `layout.totalHeight` 显式给出（`viewer.ts:2700`），不需要 `hidden` 省布局；而 `hidden`= `display:none` 会让该页 span 退出渲染树、Selection 锚点失效并丢失几何，与本次目标相反。离屏 span 本就无绘制开销 |
| 百分比定位 + `--scale-x` | 有 | **不采用** | 现有 96 DPI 绝对 px + 图层 `scale()` 已保证缩放/旋转不重算（`text-layer.ts:108-127`），改动会牵动选区几何 |
| 单页节点上限 10 万 | 有 | **采用** | §5.3 |
| 选区保护 | **无** | **增强：快照 + 端点 pin** | 跨页复制必须正确；pdf.js 接受滚远后选区失效，我们不接受 |
| `content-visibility`/TTL | 无 | **不采用** | `hidden` 都不需要，不引入额外机制 |

## 4. 目标模型

### 4.1 缓存单元与生命周期

**缓存单元 = 一页的 canvas + 文本层 span + 页文本数据**，同一淘汰动作内整页释放（pin 的 canvas 例外，见 §6.4）。

每页文本层状态机：

| 状态 | 含义 | span | `content`/`rows` |
| --- | --- | --- | --- |
| `idle` | 无产物 | 0 | 无 |
| `loading` | 正在 `getTextContent()` | 0 | 无 |
| `splitting` | 生成 span 描述 / 行划分中 | 0 | 有 |
| `building` | 分帧 append 中 | 部分 | 有 |
| `paused` | 构建中离开可见集合（未淘汰） | 部分 | 有 |
| `ready` | 整页建满 | 全部 | 保留 |
| `failed` | 文本提取失败 | 0 | 无 |

**`content`/`rows` 与 span 同生命周期**（页被淘汰时才释放）。不采用“保留 span 但释放
`content`”的方案：快照只解决“已建立选区”的正确性，**新建选区仍要 `getCharQuads()`/`getAxisRowRad()`**，
若保留页的 `content` 缺失，跨过该页的新拖选会拿不到几何而只能清空选区并告警。
内存上并不失控：密集页受 span 预算约束（B=30,000 时只放得下约 3.6 页 dense），
`content` 开销被同一上限兜住；普通页约 0.2~2 MB/页，与 span 同量级。

### 4.2 构建时机

```text
滚动中（距上次滚动 < SCROLL_SETTLE_MS = 150 ms）：
    首次访问页 → 不构建（只登记需求）
    已有产物页 → 直接复用（pin 页同样直接复用）
停止滚动 ≥ 150 ms：
    为可见页启动构建（每页一条流水线，按可见顺序排队）
用户 pointerdown 命中未建页：
    立即启动该页构建（显式交互优先，分帧，不整页同步）
```

- `SCROLL_SETTLE_MS = 150`（单位 ms）为本设计新增常量；当前代码中不存在任何 settle 机制，
  rAF 每帧全量 `refresh()` 正是抖动来源之一。
- 构建流水线：取文本（引擎同步）→ 生成 span 描述 → 行划分 → 分帧 append（约 700 span / 8 ms 预算）
  → `ready`。详见实施规格 §3。

### 4.3 帧循环

```text
refresh()：                                   // 每次 statechange 合并到 rAF
  功能关闭/文档未就绪 → 清理返回
  布局键（surfaceWidth/surfaceHeight/layoutScale）变化 → 仅此时写图层布局
  visible = visiblePageNumbers(state)          // 纯状态读取，无测量
  逐可见页：idle→排队（settle 后启动）；paused→恢复；ready→直接跳过
  无构建、无布局变化、无脏标记 → 直接返回（滚动空转）
  查找高亮仅在 (visibleRange, matchesVersion, current) 变化时重绘
  选区层仅在快照版本或布局键变化时重绘
```

结果：滚动期间 `getBoundingClientRect()` 调用数 = 0，`ready` 页 span 增删 = 0。

## 5. 容量与预算

### 5.1 页数上限

```text
pageLimit = max(1, pageCacheSize, 2 × visiblePages + 1) + pinnedPages.size
```

- `pageCacheSize`：桌面默认 10、移动默认 4（`options.ts`）；实现显式保留用户配置的基数，
  因此公式是 `max(1, pageCacheSize, 2n+1)`，而不是写死 `max(10, 2n+1)`。
- 对齐 pdf.js `Math.max(10, 2n+1)`（默认档等价），并加 `pinnedPages.size` 使 pin 不侵占
  滚动页预算；显式调小 `pageCacheSize` 时以用户配置为准。

### 5.2 span 预算（分账）

```text
总 span 上限 = B（滚动预算） + pinnedSpans（pin 冻结量）
pinnedSpans 硬上限 = P（可配置：selectionPinSpanBudget）
```

| 参数 | 桌面默认 | 移动默认 | 推导 |
| --- | --- | --- | --- |
| B（滚动 span 预算） | 30,000 span | 12,000 span | 普通页 500~1,500 span，10 页约 5,000~15,000；dense 页 8,331 → 约 3.6 页滚动缓存。按 1 KB/span ≈ 30 MB / 12 MB |
| P（pin span 预算，`selectionPinSpanBudget`） | 50,000 span | 20,000 span | 端点 pin 只涉及 2 页。P = 50,000 允许每页 25,000 span（dense 页 8,331 的 3 倍），覆盖超大单页；移动端每页 10,000。 |
| 单页上限（`textLayerMaxSpans`） | 100,000 span | 100,000 span | 对齐 pdf.js `MAX_TEXT_DIVS_TO_RENDER`（§5.3） |

- **移动档判定**（三选一即按移动档，显式选项优先）：
  1. `resolveViewerOptions` 已解析的 `mobile`（`viewer.ts:656` 传入 `detectMobile()`）；
  2. `detectTouchPrimary()` 为真（`viewer.ts:4657-4667`，`pointer: coarse`）；
  3. `navigator.deviceMemory <= 4`（低内存设备）。
  判定结果只影响默认值；宿主显式传 `textSpanBudget` / `selectionPinSpanBudget` 时以选项为准。
- `pinnedSpans = Σ pinnedPages.map(page => pageView.textSpanCount)`（`childElementCount`，O(1)）。
- 耗尽判定发生在**选区变化时以及 pin 页分帧构建增长后**：`pinnedSpans > P` → 清空选区 + `W_SELECTION_UNPINNABLE`（§7.5）。分帧实现每次 pump/finish 都复核，避免“建立 pin 时未超、后续 span 增长才超”的窗口。
- pin **不新增构建**：端点页在建立选区时必然已建（用户是在其 DOM 上选的），P 约束的是“冻结量”
  而非新建；超限时按用户规则**要么宿主调大 `selectionPinSpanBudget`，要么清空并告警**，
  不静默无限冻结。dense 页 2 × 8,331 = 16,662 span，远低于桌面 P=50,000。
- **可见页豁免**：可见页永不淘汰；若可见页 span 总和已超 B，则预算作为软上限（只记录、不裁剪可见内容），
  避免出现“当前屏被裁掉一半”的可见缺陷。

### 5.3 单页节点上限（兜底）

1. 生成 span 描述后若 `spans.length > textLayerMaxSpans`（默认 100,000）：**降级为 item 级**
   （不拆字符），重新生成。
2. 降级后仍超限：按阅读顺序截断，页标记 `truncated`，上报 `W_TEXT_LAYER_CAP`；页面照常显示，
   已建部分可选中/查找。
3. 截断页缺失字符的几何查询返回 null → 选区模型标记不完整（§7.5），不静默错。

> 与 v1 §5.2「不设任何单页兜底」的结论相反：v1 的理由是“页级缓存可自动换入换出”，
> 但无法覆盖“单页本身就超过总预算”的病态文档；pdf.js 的 10 万上限也证明需要兜底。
> 本设计选择“降级优先、截断兜底、必须告警”。

### 5.4 canvas 像素预算

- 沿用 `pageCachePixelBudget`（默认 512,000,000 px，`options.ts:293,401`）。
- canvas 与 span 预算**分账**：pin 只冻结 span 与文本数据，**不冻结 canvas**（§6.4）。

## 6. 淘汰与释放

### 6.1 唯一淘汰入口

`viewer.ts` 的 `trimCache()`（`:3393-3412`）是唯一入口，在 `renderVisible()` 末尾调用（`:3042`）。
文本层不再自行销毁（删除 `text-layer.ts:303-307` 的“不可见即清空”）。

`renderOrder` 语义扩展为 **cacheOrder**：canvas 渲染完成（`markRendered`）与文本层建满都要入队，
使“有文本无 canvas（渲染失败）”的页也能被淘汰。

### 6.2 四条淘汰/释放规则

```text
trimCache():
  1) while cacheOrder.length > pageLimit:             // 页数
       淘汰最远/最久未用的「不可见且未 pin」页
  2) while totalTextSpans > B + pinnedSpans:          // 滚动 span 预算
       淘汰 span 最多的「不可见且未 pin」页（同分取最远）
  3) while totalCanvasPixels > pageCachePixelBudget:  // canvas 像素
       a. 先淘汰「不可见且未 pin」页的整页产物
       b. 若候选全是 pin 页 → 只释放其 canvas，保留 span/content
  4) 对「不可见且 pin」的页：立即释放其 canvas（不等预算），保 span/content
```

第 4 条即“pinned 页只保留 span、释放 canvas”：pin 页可见时 canvas 正常渲染；
一旦滚出可见区，canvas 立刻释放（像素是关键预算），滚回时走既有渲染路径重绘一次。

### 6.3 原子释放

```text
releaseCachedPage(index):
  pageView.releaseCanvas()
  pageView.releaseTextLayer()                 // 新增：清 span、复位 data-*、pointer-events:none
  textLayerService.handlePagesReleased([n])   // 新增：删 pages 记录、content/rows、选区层、查找层
  从 cacheOrder 移除
```

`handlePagesReleased` 必须：
- 删除 `pages` 记录与 `content`/`rows`；
- 移除该页选区层与查找层；
- 若被释放页属于当前 pin 集合（防御分支，正常不会发生）：**保留快照文本与矩形**（复制仍完整），
  标记“原生扩选不可用”，并上报 `W_SELECTION_EVICTED`；仅当该页数据缺失使快照无法保证完整时
  才清空选区（§7.6）。

### 6.4 pin 与 canvas 的边界

| 页状态 | span | content/rows | canvas |
| --- | --- | --- | --- |
| 可见 + pin | 保留 | 保留 | 正常渲染，参与像素预算 |
| 不可见 + pin | **保留** | 保留 | **立即释放**（§6.2 第 4 条） |
| 可见 + 非 pin | 保留 | 保留 | 正常渲染 |
| 不可见 + 非 pin + 在缓存内 | 保留 | 保留（随页淘汰释放） | 保留（受像素预算） |
| 被淘汰 | 释放 | 释放 | 释放 |

## 7. 选区存续：快照负责正确性，pin 保住原生锚点

### 7.1 两条机制的分工

| 机制 | 负责 | 不负责 |
| --- | --- | --- |
| **SelectionSnapshot（快照）** | `getSelectedText()` / 复制 / 块状高亮：跨任意页数、任意淘汰都完整正确 | 原生 Selection 的存续 |
| **pin（仅端点页）** | 保住原生 Selection 的 anchor/focus 节点，使用户还能 Shift 扩选 | 复制正确性（已由快照负责） |

因此 pin 从“保证复制正确”降级为“保证原生选区可继续扩展”，**只需钉端点页**，
跨 5 页选中只需 pin 2 页。中间页被淘汰不会影响快照文本与块状高亮。

> 历史勘误：v1 §8 第 3 条曾写“选区起点/终点所在页强制提升为 `Active`（仅翻转 hidden）”，
> 但该机制在旧实现中**从未落地**（全仓不存在 `Active`/`Retained` 概念，也没有任何 pin/保护逻辑）。
> 本文以“快照 + 端点 pin”重新落地，并把 pin 的职责缩小为保住原生锚点。

### 7.2 快照结构与内存

```ts
/** 选区快照：与 DOM 存活性解耦。 */
export interface SelectionSnapshot extends SelectionModel {
  /** 规范化后的完整选区文本（与 getSelectedText 返回值一致）。 */
  readonly text: string;
  /** 每页的块状高亮矩形（已按行合并、留缝，页坐标 96 DPI）。 */
  readonly rectsByPage: ReadonlyMap<number, readonly SelectionBox[]>;
  /** 每页的行主轴方向，单位弧度。 */
  readonly axisByPage: ReadonlyMap<number, number>;
  /** 选区覆盖的页（升序，1-based）。 */
  readonly pageNumbers: readonly number[];
  /** 选区页区间内不可用的页；非空表示模型不完整。 */
  readonly incompletePages?: readonly number[];
  /** 端点页，用于 pin 与扩选判定。 */
  readonly startPage: number;
  readonly endPage: number;
  /** 建立快照时的原生锚点/焦点节点与偏移；用于识别 DOM 导致的选区变化。 */
  readonly anchorNode: Node | null;
  readonly focusNode: Node | null;
  readonly anchorOffset: number;
  readonly focusOffset: number;
  /** 快照版本号；每次建立/失效递增。 */
  readonly version: number;
}
```

- 几何存**已合并的行矩形**（`RowFlowRect` → `unprojectRect()` 后的 `SelectionBox`），
  不存逐字符 quad：t3 的渲染输入本来就是“行内投影并集 + 反变换”的结果，
  合并结果与 quad 集语义等价，但 dense 页 146 行 → 每页约 146 个矩形，选 5 页仅约 730 个，
  内存比逐字符 quad 少一个数量级。
- 内存估算：矩形 5 个数（left/top/width/height/rotation）× 8 B ≈ 40 B，730 个 ≈ **30 KB**；
  文本 15,000 字符 × 2 B ≈ **30 KB**。合计 **< 0.1 MB/选区**，与 DOM 的 8.3 MB/页相差两个数量级。
- 快照在每次 `selectionchange`（非折叠、在阅读器内）后重建；快照是**唯一**的复制与高亮数据源。

#### 7.2.1 坐标口径：布局不变量（缩放/旋转不重算）

**结论：矩形保留 96 DPI 页坐标，缩放/旋转后不重算、不重建快照。**

依据：文本层与选区层都挂在 `view.surface` 内（`text-layer.ts:539-550`），
两者使用同一套图层尺寸换算 `applyLayerScale()`（`:108-127`）：内容按 96 DPI 绝对坐标写入，
再由 `--scale-factor` 放大；页面旋转由 `surface` 的 CSS `rotate()` 承担（`page-view.ts:408-410`）。

因此：

| 变化 | 需要做什么 | 不需要做什么 |
| --- | --- | --- |
| 缩放（50%~400%） | 更新图层尺寸/变换（一次样式写） | 重算矩形、重建快照、触碰 span |
| 页面旋转 0/90/180/270 | 无（`surface` transform 自动带动选区层） | 重算矩形、重建快照 |
| 手势预览缩放 | 无（预览 transform 作用于页元素，选区层随之缩放） | 重算 |
| 文档 DPI/坐标口径变化 | 重新取文本并重建页（不存在于当前实现） | — |

这与文本层“span 坐标恒定”的既有前提完全一致（单元测试「缩放/旋转由页面容器承担」已覆盖），
也是布局变化不再丢选区的根本原因：**没有坐标重映射，就没有新的破坏窗口**。

**降级边界**：若未来引入“页内坐标重排”（当前实现不存在），必须按以下顺序降级：
① 复制内容必须保留（快照文本与布局无关）；② 高亮在布局稳定后用快照矩形重绘；
③ 原生选区允许失效，下一次点击重建快照。任何情况下都不允许“复制静默少字”。

### 7.3 块状高亮改为快照驱动（修掉 t3 的缺行问题）

- `renderSelectionFromModel()` 不再用 `state.built.has(rowId)` 过滤（`text-layer.ts:480-483`），
  改为直接按 `snapshot.rectsByPage` 绘制。
- 页被淘汰后，页元素与 `view.surface` 仍在（页视图不销毁），选区层可以照常创建并绘制矩形，
  因此**高亮矩形在中间页被淘汰后依然完整**。
- 渐进构建期间建立选区时，快照只包含当时已建行（用户也只能选到已建行），不存在缺行。
- 选区层几何只在布局键变化时同步一次（与文本层同路径），矩形本身不动。

### 7.4 复制拦截（原生 Ctrl+C）

- 在阅读器根文档上以 capture 监听 `copy`：
  1. 拦截条件：**快照存在**，且满足其一：① 当前 Selection 在阅读器内；② Selection 已折叠
     但快照仍有效（中间页淘汰可能把原生选区折叠掉，此时用户仍期望复制完整文本）。
     `pointerdown`/`Escape` 已清空快照的情形不会命中，宿主其它文本的复制也不会命中；
  2. 命中后 `clipboardData.setData('text/plain', snapshot.text)` 并 `preventDefault()`；
  3. 不阻止其余默认行为（`copy` 无其它默认行为）。
- 不依赖 `navigator.clipboard`（受权限/焦点限制）；`copySelection()` 公开方法仍走异步剪贴板，
  内容同样取自快照。
- `getSelectedText()` 与复制必须同源：快照存在时直接返回 `snapshot.text`，快照不存在时回退到
  “从 DOM 现算”的旧路径（仅在没有选区的常规情况发生，不影响兼容）。
- 参考 pdf.js 的隐藏复制元素思路处理 Ctrl+A，但**整本全选不在本次范围**（§9 非目标）。

### 7.5 快照失效、抑制与兜底

**失效条件（必须清空快照）**：

| 事件 | 判定 |
| --- | --- |
| 新选区建立（非折叠） | `selectionchange` 后正常重建快照 |
| 用户点击空白 / 开始新选择 | `pointerdown` 且未按 Shift → 清空（含点在选区内部折叠的情况）；拖滚动条产生的 pointerdown 不清空 |
| 用户按 Esc / 键盘取消 | `keydown Escape`，或方向键/可打印字符的 `keydown` → 清空 |
| 文档切换 / 关闭 | `resetPages()`、`destroy()` → 清空 |
| 功能关闭 | `textLayer`/`selection` 关闭 → 清空 |
| **布局变化（缩放/旋转/容器尺寸）** | **不得清空**（不是用户取消），也不重建快照；只同步选区层几何 |
| `pinnedSpans > P` | 立即清空 + `W_SELECTION_UNPINNABLE` |
| 模型不完整（`incompletePages` 非空） | 立即清空 + `W_SELECTION_EVICTED` |

**selectionchange 抑制**（关键：我们改 DOM 不应清空快照）：

```text
suppressSelectionChange = true
  → 执行会改动选区所在 DOM 的操作（releaseTextLayer、append 构建、淘汰页）
  → queueMicrotask(() => suppressSelectionChange = false)
selectionchange 到达时若 suppressSelectionChange: 忽略（不清快照、不重建）
```

- 抑制窗口必须**只覆盖我们自己改 DOM 的那一帧/微任务**，不能常驻，否则用户真正取消选择会被吞掉。
- **硬约束（实现红线）**：禁止用“无条件忽略 `selectionchange`”来掩盖丢选区问题。
  抑制必须同时满足三个条件：① 由本模块自己改动了选区所在页的 DOM；② 处于该次改动的
  微任务窗口内；③ 有明确的开始/结束边界。任何其它来源（点击空白、Esc、用户新拖选、
  宿主清除选区）都必须正常处理。t12 审查将核对这一点。
- 可靠区分“DOM 导致折叠”与“用户主动取消”，采用**“显式意图才清空”**模型（不靠抑制标志猜）：
  1. 快照记录 `anchorNode`/`focusNode`；
  2. **折叠的 `selectionchange` 本身不作为清空依据**：它可能来自我们淘汰页/改 DOM，也可能来自
     浏览器选区归一化。按以下顺序判定：
     - 抑制标志为真（本模块改 DOM 的微任务窗口）→ 忽略；
     - 折叠且 `selection.anchorNode === snapshot.anchorNode` → DOM 导致，保留快照；
     - 折叠且 `snapshot.anchorNode/focusNode` 任一 `isConnected === false` → DOM 导致，保留快照；
     - 折叠且锚点已换成其它节点 → **仍保留快照**，交由显式意图事件处理（下表）。
  3. **只有显式用户意图/生命周期才清空**：`pointerdown`（无 Shift）、`Escape`、方向键/可打印键
     的 `keydown`、新选区非折叠（替换重建）、`clearSelection()`、文档切换、功能关闭、
     pin 超限、模型不完整。这样“淘汰导致折叠”永远不会误清，“用户取消”也一定能清（不被吞）。
  4. **布局变化不进入抑制窗口**：页级构建后布局变化不改 DOM（§7.2.1），因此无需抑制；
     若未来实现不得不在布局时动 DOM，必须先建立快照再动，且按本条边界处理。
  5. 抑制标志只用于“避免在改 DOM 的同一微任务里重算模型”，**不是**正确性的唯一保障；
     即使标志时序错过浏览器异步派发的 `selectionchange`，第 2 条也能保证快照不丢。

**中间页被淘汰时会发生什么**：

- 原生 Range 的边界节点在端点页（被 pin），中间页 span 删除**不会**改变 Range 的
  `startContainer`/`endContainer`；浏览器可能重绘原生选区（中间页原生高亮消失），并可能派发
  `selectionchange`。
- 我们在抑制窗口内忽略该事件；窗口结束后若 Range 仍非折叠且锚点连通 → 快照保持，块状高亮完整。
- 若浏览器确实折叠了选区（不同内核行为），端点节点仍连通 → 按“DOM 导致”保留快照；
  用户仍可 Ctrl+C 得到完整文本，Shift 扩选可能失效（见 §7.6）。

**模型完整性**：`buildSelectionModel()` 增加 `incompletePages`（选区页区间内无 span/无数据的页）。
正常路径下不会出现（快照在选区建立时已捕获全部已建页）；仅用于“选中后页被淘汰、
快照却未建立”的异常窗口与截断页（§5.3）。一旦非空：清空选区 + 告警，绝不返回部分文本。

**Shift 扩选跨越已淘汰页**：扩选会触发新的 `selectionchange`，模型只能看到当前 DOM；
若中间页已被淘汰，`incompletePages` 非空 → 按上条清空 + 告警（这属于“用户主动建立新选区”
的语义，不是“旧快照被误清”）。想保留旧内容时，应先滚回该页（页级重建完成）再扩选；
纯 Ctrl+C 不受影响，永远取旧快照文本。

### 7.6 端点页被淘汰（防御行为）

- 端点页在 pin 集合内，正常**不会被淘汰**；若因预算/失败被释放：
  1. 快照文本与矩形仍可绘制（正确性不受影响）；
  2. 原生 Range 锚点失效 → Shift 扩选不可用；
  3. 下次用户在任意位置开始新选择（`pointerdown` 无 Shift）→ 旧快照清空、建立新快照。
- 该边界必须在 e2e 中断言“复制仍完整、扩选给出可预期行为”。

### 7.7 无障碍与读屏

- 文本层 span 的 `aria-hidden="false"`（`page-view.ts:208`）保留，屏幕阅读器可直接朗读 DOM 文本；
  淘汰后该页文本对读屏不可用，与视觉一致。
- 复制拦截不影响读屏：读屏的“朗读选区”来自 DOM/Selection，不经过 `copy` 事件。
- 若后续需要“淘汰页仍可朗读”，增加一个 `aria-live`/隐藏可访问文本节点（同步快照文本），
  本次不实施。

## 8. 与 pdf.js 对照（汇总）

见 §3.5 表。核心差异只有两条：

1. **不隐藏离屏页**：`hidden` 在 pdf.js 用于省布局/绘制；我们页盒绝对定位、滚动高度由
   `layout.totalHeight` 显式给出（`viewer.ts:2700`），不需要它省布局，而 `display:none`
   会让文本层的 Selection 锚点与几何一并失效，与本次目标相反。
2. **选区增强**：pdf.js 无选区保护，接受滚远后失效；我们用“快照 + 端点 pin”保证跨页复制与高亮正确。
3. **历史勘误**：v1 §8 第 3 条曾设想“把选区起点/终点所在页强制提升为 `Active`（仅翻转 hidden）”，
   但 `Active`/`Retained` 提升在旧实现中**从未落地**；本文以“快照 + 端点 pin”重新落地该目标，
   并明确 pin 只保原生锚点、不承担复制正确性。

## 9. 非目标

1. **不提供整本全选功能**。Ctrl+A 只能选中已构建页的文本（快照也只覆盖这些页），
   与 pdf.js 行为一致；为本功能加载全部页 `TextContent` 属独立功能。
2. 不修改 `SelectionModel` 的几何算法与块状高亮算法（t2/t3 已验收）。
3. 不修改行划分算法与 `BAND_MERGE_RATIO`（基线抖动合并属独立议题）。
4. 不把引擎 `getTextContent()` 移到 Worker、不做文档级预取。
5. 不新增公开 API；新增选项为构造选项（`textSpanBudget`、`selectionPinSpanBudget`、
   `textLayerMaxSpans`）。`textCachePages` 仅为**设计预留、尚未实现**，不属于当前可用选项。
6. 不改打印/导出路径（不依赖文本层 DOM）。
7. 不把“每页独立选区层”收拢为跨页单一覆盖层：现有实现每页一层、坐标与页同源，
   收拢会引入跨页 transform 与命中测试问题，收益不足（快照已让高亮与 DOM 解耦）。

## 10. 风险与边界

| 风险 | 应对 |
| --- | --- |
| 首次访问 dense 页仍有 `getTextContent` 约 143 ms 主线程长任务 | settle 150 ms 后再构建；引擎文本缓存对齐列为后续（`textCachePages` 为设计预留、尚未实现，当前未透传引擎 `cache.textPages`）；接受并记录，Worker 化列后续 |
| pin 页 canvas 释放后滚回需重绘 | 正常渲染路径，无需特殊处理；仅在 pin 页不可见时释放 |
| 中间页被淘汰后原生选区可能折叠（内核差异） | 快照保留文本/高亮；抑制窗口 + 端点连通性判定；Ctrl+C 仍完整 |
| 快照与原生选区不一致（我们高亮在、原生 Ctrl+C 失效） | 拦截 `copy` 事件，统一用快照文本 |
| **F7 病态行重叠** | 正常文本 1 px 缝隙全部由下行顶边让出；若字形盒本身重叠超过下半行高度，病态情况下相邻行矩形仍可能相交，正常文本不触发；修复需调整行划分/`BAND_MERGE_RATIO`，列为已知限制 |
| **布局变化（缩放/旋转）再次丢失选区** | 结构上：页级构建后布局变化不改 DOM；快照上：布局变化不清空、矩形用 96 DPI 页坐标不重算（§7.2.1）；验收覆盖 1→1.5→2、180°/270° 与回归基线 |
| 抑制窗口被滥用（无条件忽略 `selectionchange`） | 抑制仅在“本模块改选区 DOM”的微任务内；`pointerdown`/`Escape` 显式取消优先；t12 审查核对（§7.5 红线） |
| 内存上限 | B/P 分账、单页 10 万兜底、不可见 pin 页释放 canvas；保留页 `content` 由 span 预算间接约束（密集页 ≤ ~4 页） |
| 滚动中首次访问页的构建时机 | 滚动中只登记需求，停止 150 ms 后构建；pointerdown 显式交互优先 |
| 旋转与竖排 | 整页构建后不再需要可见区换算，90°/270° 的“整页特例”消失；行主轴仍由 `getAxisRowRad` 决定，四向旋转/竖排几何单测保留 |
| 查找定位 | `scrollToMatch()` 基于页坐标，不依赖 span；查找有独立按页文本缓存（`find-controller.ts:103`），不受文本层淘汰影响 |
| 端点页失败 | 快照仍可复制；扩选不可用；下次点击重建（§7.6） |
| 测试全面重写掩盖回归 | 几何/行划分纯函数测试保持不动；先落计数器断言（实施规格 §8.1） |

## 13. 跨页选区下的滚动性能退化（2026-10-29 实测与修正）

### 13.1 现象与复现

样本 `ofd_pdf_match/dense-text-perf.ofd`（2 页，第 1 页约 150 个 TextItem，第 2 页 8,331 个
TextObject / 约 1.5 万字符），在文字选中（尤其跨页选中）后滚动，可感知持续卡顿；取消选区后
恢复正常。白盒 + 浏览器实测（headless Chrome、demo `?file=samples/dense-text-perf.ofd`，
效果倍率 1.5932）得到以下事实：

| 观测 | 无选区 | 有跨页选区 |
| --- | --- | --- |
| 主线程最大阻塞（longtask / setTimeout 心跳） | ≤ 4 ms | ≤ 4.3 ms（空闲态） |
| 一次强制样式+布局刷新 | 0.1 ms | 0.1~0.7 ms |
| 可见页文本层 span 数 | 第 2 页稳定在 700（建满） | 在 557 / 660 / 679 / 691 之间反复 |
| `.ofd-selection-rect` 数量 | 0 | 约 400，且随构建重绘 |

结论：**脚本、样式、布局都没有变慢，`trimCache` 也没有逐个调用**；问题出在
“选区存在 → 每帧一次 DOM 变更 → 每帧重建一次”，以及选区绘制面的扩大。

### 13.2 根因链

```text
pumpPageBuild() 每帧 appendChild(layer, fragment)          text-layer.ts:1179
  └→ 浏览器把选区边界 span 拆分/合并 → selectionchange
       └→ publishSelectionChange()                         selection.ts:460
            ├→ isSameSelectionAsSnapshot() 为假（锚点处理制拆分而移位）
            ├→ buildSelectionModel()：全页 querySelectorAll + 逐 span comparePoint/Range
            ├→ renderSelection() → setPinnedPages() → host.textLayerPinsChanged()
            │    └→ viewer.trimCache()                     viewer.ts:2598, 3431
            │         └→ span 预算分支 → evictCandidate()
            │              → releaseCachedPage() → textLayerService.releasePage()
            │                   → clearPageTextLayer() → cancelPageBuild()   text-layer.ts:1340
            └→ 同时 onDomMutation 打开抑制窗口 → 下一次 selectionchange 被丢弃，
               但 trimCache 不在抑制窗口内，取消动作每帧重复
```

要点：

1. **构建被自我取消**：`trimCache()` 在“可见页永不可淘汰”前提下仍会进入 span 预算分支；
   由于 `cachedPageIndices()` 只认 `textSpanCount > 0` 的页，正在分帧构建的可见页是候选，
   `evictCandidate()` 选中它后 `releaseCachedPage()` 连同文本层一起清空并取消构建。每帧重复，
   于是文字层永远建不满，滚动时持续重建 DOM。
2. **抑制边界不完整**：抑制只用于丢弃 `selectionchange`（§7.5），而 `trimCache()` 由文本层
   主动回调 `host.textLayerPinsChanged()` 触发，不经事件，因此不受抑制影响。
3. **选区绘制面扩大**：选区块层是半透明 CSS 背景（`style.css:831`），含原生选区的文字节点
   每帧都要重绘；第 2 页文本被压缩在 794×1122 的文本层里（96 DPI 后按 1.5932 放大、图层
   `overflow: hidden`），选区覆盖的离屏文字越多，合成/光栅代价越大。该项是次要因素，
   单独把 400 个矩形塞进页面实测布局仍为 0.1 ms。

### 13.3 修正设计

#### 13.3.1 抑制窗口扩到“构建期间的缓存整理”

新增能力：文本层分帧构建期间，对 `textLayerPinsChanged()` → `trimCache()` 的调用**推迟**，
而不是在构建中途执行淘汰。推迟的缓存整理在以下时机补齐：

- 当前可见页全部 `ready` 或 `failed`；
- 构建被外部原因取消、页离开可见集合；
- `documentclose` / 功能关闭 / `destroy()`。

推迟期间**仍执行** canvas 像素预算分支（只释放 canvas，不触碰 span 与页数据），
只把“页数 / span 预算”两类会清空文字层的淘汰推迟。理由：这两类淘汰只会带走
不可见页，而滚动期间真正需要淘汰的时机是“可见集合已经变化”，此时构建任务本身也可能
已经过期；把淘汰放到构建结束后执行不会造成内存超限（上限仍由渲染层的
`pageCachePixelBudget` 与页数上限约束）。

#### 13.3.2 抑制窗口内“比对快照后再丢弃”（保护用户新选区）

§7.5 当前实现为 `suppressDepth > 0` 直接 `return`。修正为：

```text
selectionchange：
  若处于本模块改 DOM 的微任务窗口：
    取当前 Selection；
    若与 lastSnapshot 的 anchor/focus/offset 完全一致 → DOM 副作用，丢弃；
    否则 → 用户真实改选区，立即按正常流程重建模型/快照/块状高亮；
  否则：按 §7.5 原有流程处理
```

由此保证：“程序自己加 span”的事件被吸收，“用户拖选/点击/Shift 扩选/Esc”的事件永远不被吞。

#### 13.3.3 可见页与构建中的页不参与文本层淘汰

`trimCache()` 的页数与 span 预算分支，候选集合排除三类页：

1. 可见页（既有规则）；
2. pin 页（既有规则）；
3. **正在分帧构建的页**（新增，`TextLayerService` 暴露“是否有构建中的页”查询）。

`releaseCachedPage()` 对“文本层处于构建中且即将完成”的页不再清空文字层（新增查询判定），
只释放 canvas。

#### 13.3.4 选区绘制面

- 选区块层改用不透明背景色（或 `mix-blend-mode`），避免半透明文字节点每帧参与逐层合成；
- 建议后续单独核对文本层几何倍数（96 DPI 页宽 vs 96/25.4 换算下的矩形宽度），
  该问题与本次卡顿无因果关系，不在本节范围内。

### 13.4 验收

1. 打开 `dense-text-perf.ofd`，第 2 页文字层在 2 s 内稳定达到上限（当前约 8400 个 item span 受
   单页上限与预取约束，观测值应稳定不再波动）；
2. 跨页选中后滚动与未选中时帧间隔的 p95 差距 ≤ 2 ms；
3. 构建进行中新建选区：模型、快照文本、块状高亮与选区一致；
4. 构建进行中点击空白 / Esc：选区清空，无残留高亮；
5. 构建结束后补执行一次推迟的缓存整理，页数与 span 预算仍按文档约束收敛。
